# Feature Specification: Чистая установка серверного ПО

## Область приложений2026-11-01

- **FR-006-APP-01**: Установка приложений не ограничена PostgreSQL, ClickHouse или
  другим перечнем названий. Название приложения не является критерием допуска.
- **FR-006-APP-02**: Допуск определяется поддержанным способом, рецептом, форматом,
  средой, prerequisites и проверяемым результатом. Неподдержанный вариант получает
  явную причину без remote write; имя приложения не разрешает обход guards.
- **FR-006-APP-03**: Конкретные продукты могут быть первыми практическими целями
  и тестовыми примерами. Их параметры и специальные проверки не распространяются
  на остальные приложения и не блокируют независимые этапы установки.

Приёмка: **AC-APP-01–04** в [контракте области приложений](contracts/application-scope.md).
Уточнение применяется ко всем этапам006; существующие ограничения способов,
схем и исполнения сохраняются. Новые способы установки не вводятся этой поправкой.

## Поправка 2026-11-01 — установка напрямую по SSH

Действуют [требования FR-SSH-001–015](../001-service-foundation/spec.md)
и [контракт прямого SSH](../001-service-foundation/contracts/direct-ssh.md).
Они заменяют прежнюю исполнительную архитектуру 006/021. Установка приложений
выполняется движком приложения через существующий SSH-доступ;
ServerDeck executor, enrollment, supervisor/bridge, Ansible и отдельный Python
runtime не требуются и не устанавливаются. Штатные SSH/systemd/APT-инструменты
и подходящие доверенные репозитории должны уже существовать на цели.

Каталог и preflight выполняют только чтение. Приложение не добавляет репозитории,
не загружает ключи доверия, не обновляет индексы и не меняет sudoers за пользователя.
Каталог показывает доступные точные версии из проверяемых источников и причину
недоступности. План связывает версии, архитектуры, SHA256 пакетов и зависимостей,
источники, исходные пакеты/пути, initial settings и postchecks.
Отсутствующие инструменты/права/метаданные не заменяются пустым успешным результатом.

После подтверждения один host-wide writer выполняет только объявленные действия.
Служебная запись попытки создаётся в рамках apply, а не просмотра; это данные,
не установленный агент. Запущенный шаг может пережить потерю SSH; следующий шаг
требует нового текущего permission check. Нет обещания продолжить всю установку
после выхода из приложения. Unknown блокирует конфликтующую запись до reconcile.
Подробные схемы, пределы, совместимость и восстановление задаёт общий контракт.
Критерии **AC-SSH-04–10** применяются к APT-ветке; version/служба/настройки и
сохранность NetBird/соседних данных проверяются по выбранному рецепту. SQL обязателен

для DB-рецептов, другие рецепты используют свои обязательные health checks.
Текущая реализация и проверки этой поправки ограничены static/unit scope 001;
документ не объявляет реальную установку проверенной.

**Feature**: `006-software-installation`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Каталог и проверка плана (Priority: P1)

Пользователь выбирает приложение, совместимый рецепт, точную поддержанную версию и сервер.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-006-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Каталог и проверка плана», **Then** Неизвестное состояние, существующие данные/ПО, недоступная версия, неподдержанная ОС или отсутствующие полномочия блокируют установку без записей.
2. **AC-006-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-006-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

Обязательные предшественники: [001](../001-service-foundation/spec.md), [002](../002-security-storage/spec.md), [003](../003-design-system/spec.md), [004](../004-server-workspace/spec.md), [005](../005-client-distribution/spec.md) (gate 005.1 Windows; остальные платформы не блокируют).

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

### Место в сервисе и ответственность

**Расширяемые компоненты**: каталог рецептов и job coordinator locald, ограниченный executor и host-side исполнение.

Первый интегрированный путь записей расширяет основу 001. Встроенный engine владеет планом/approval/events и прямыми типизированными SSH-операциями; штатные средства хоста удерживают физическую блокировку и запись результата. Отдельного ServerDeck runtime на сервере нет. Чтение ничего не устанавливает.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-045**: Новая установка и регистрация существующей остаются явно разными процессами. Их название, подготовка и последствия не должны путать пользователя.
- **FR-046**: Каталог должен показывать поддерживаемые программы, точные версии, среды и ограничения. Недоступная версия не заменяется автоматически похожей или более новой.
- **FR-047**: Существующие данные, конфигурация и несовместимое состояние должны блокировать чистую установку. Очистка, понижение версии и преобразование не включаются скрыто.
- **FR-006-LOCAL-01**: Первая среда Ubuntu 24.04 amd64/systemd; приложения устанавливаются по неизменным рецептам с точной версией и проверяемым артефактом. APT-рецепт фиксирует полные package pins; другой поддержанный способ — свой exact artifact pin. Продуктовые особенности относятся к конкретным рецептам, не ограничивают имена приложений.
- **FR-006-LOCAL-02**: План доступен максимум за три действия после входа в ПО; пустой список серверов предлагает добавление профиля. Plan/check не добавляют repository, helper, package либо права.
- **FR-006-LOCAL-03**: Доверенные подписанные repositories, metadata и runtime исполнения должны быть подготовлены администратором заранее. Недостаток подготовки показывается до approval; конкретные упаковка и протокол исполнителя фиксируются в Plan новой реализации.
- **FR-006-LOCAL-04**: Точная версия рецепта и package pins проверяются до approval и перед эффектами. Отсутствующая версия не заменяется автоматически; inputs/review привязаны к fingerprint и credential revision.
- **FR-006-LOCAL-05**: Симуляция dependencies блокирует удаление, downgrade, изменение unrelated packages, неполный dpkg, нерешённые зависимости и любой эффект на NetBird. Существующий package/config/data state блокирует fresh install.
- **FR-006-LOCAL-06**: Неизменные approval, attempt ID и physical-host lock долговечны до эффектов; удалённое подтверждение задания и блокировка переживают потерю клиента. Повтор того же inputs возвращает прежний результат, конфликтующие inputs отклонены.
- **FR-006-LOCAL-07**: Отмена до запуска пишет ноль; после запуска cooperative на безопасной границе операций. Отмена не обещает rollback packages или данных, оставшиеся эффекты видны.
- **FR-006-LOCAL-08**: Успех требует точной версии/артефакта, состояния принадлежащих приложению служб и обязательных health postchecks его рецепта. Для DB-рецептов обязательны active database unit и SQL probe. Unknown/failed/skipped проверки не дают succeeded. Progress исключает secrets и произвольный неочищенный stdout.
- **FR-006-LOCAL-09**: Поддержка реальной установки конкретного рецепта заявляется лишь после его реальных disposable Ubuntu systemd Docker fixture или принадлежащей тесту VM испытаний normal/failure cases. Испытания обеих БД не являются общим gate других рецептов. Mock-only проверки и успешная проверка одних prerequisites gate не закрывают. Container/init restart учитывается отдельно от host kernel reboot; одно не выдаётся за другое. Сохранённые реальные серверы не являются автоматическими test targets.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

- **SC-006-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.

- **SC-006-LOCAL-05**: Пользователь достигает плана/осмотра максимум за три действия после выбора ПО; disposable приёмка выбранного рецепта подтверждает фактическое состояние и сохранность соседних данных.

Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».

## UI-компоненты и приёмка (003.4)

Обязательны [библиотека C01–C30](../003-design-system/component-library.md) и [общий контракт применения](../003-design-system/contracts/feature-adoption.md). C ID задаёт семейство готовых элементов, а не новый backend scope. C01 (токены), C02 (действия), C10–C12 (статусы/сообщения/состояния) и C17 (каркас страницы) применяются там, где соответствующая UI-композиция уже требуется этим пакетом.

| Композиция этого пакета | Готовые элементы | Данные, состояния и ограничения |
| --- | --- | --- |
| Каталог и параметры установки | C03, C04, C05, C06, C07, C13, C18, C30 | ПО/версия/источник/среда и поддерживаемый вариант; credentials скрыты, validation не устанавливает ПО. |
| Preflight и согласование | C10, C11, C14, C18, C19, C24, C25 | Точная цель, параметры, версии, зависимости, эффекты и срок плана; missing prerequisite/drift блокирует apply, новый план требует согласия. |
| Установка, отмена и проверка | C11, C18, C20, C23 | Этапы, результат SQL/health/post-check и причина отказа; pending блокирует повтор; owner определяет исход по send/result proof: после возможной отправки без достаточного подтверждения — unknown, до возможной отправки не предполагаются эффекты, доказанный terminal сохраняется при разрыве связи. |

- **FR-UI-006-01**: Объявленные композиции MUST использовать перечисленные семейства и их применимые варианты; поля/действия сохраняют предметный смысл таблицы. Общая разметка, токены и поведение не копируются в отдельную реализацию экрана. Отсутствующий вариант сначала расширяется в 003 по общему контракту.
- **FR-UI-006-02**: Данные, callbacks, validation, поддерживаемая порция/сортировка и разрешённые эффекты MUST принадлежать owner этого пакета через действующий контракт 001; компонент не выполняет собственные запросы, retries или выдачу полномочий. Loading/empty/no-results/error/unavailable/stale/partial/unknown применяются по смыслу полученного результата.
- **FR-UI-006-03**: План и задачи MUST содержать mapping «композиция → C ID/вариант → данные/событие owner → критерий проверки». UI-работы ограничены объявленными здесь сценариями; существующая история задач сохраняется, реализация будущих backend возможностей приёмкой 003 не подтверждается.

**Проверяемая приёмка UI:**

- **AC-UI-006-01**: Для каждой строки таблицы сопоставлены её данные/действия и C IDs в плане/задачах; новый экран собирается из готовых элементов. Предметные последствия и ограничения строки видны пользователю, без копирования palette/spacing правил из 003.
- **AC-UI-006-02**: В утверждённом gate данного этапа проверены применимые normal/failure/boundary состояния, точная цель/ревизия и отсутствие запрещённого callback. Утрата readiness/authority не оставляет приватный draft или применимые поздние результаты; неизвестный исход записи не запускает повтор. N/A с причиной фиксируется в mapping. Для 006 отдельно проверяются disconnect до возможной отправки, possible send без correlated result и disconnect после доказанного terminal; UI не переименовывает известный исход в unknown и не повторяет запись.
- **AC-UI-006-03**: При UI-приёмке применяются матрица размеров/тем/масштабов, keyboard/focus/semantics и сохранение всех полей из 003. Существующий unit-only или иной ограниченный gate пакета не расширяется этой поправкой: непроведённые UI/native проверки записываются pending с их будущим gate, без заявления UI-готовности.
