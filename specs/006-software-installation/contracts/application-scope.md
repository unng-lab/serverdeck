# Приложения и конкретные рецепты

**Уточнение пользователя 2026-11-01**. [Спецификация006](../spec.md),
[план](../plan.md), [задачи](../tasks.md).

## Продуктовая граница

ServerDeck устанавливает приложения. Название приложения не является ограничением
каталога или критерием допуска. PostgreSQL и ClickHouse могут быть первыми целями
реализации, примерами и тестовыми сценариями; они не определяют назначение продукта
и не образуют закрытый список разрешённых приложений.

Это уточнение имеет приоритет над прежними формулировками «две программы»,
«первый каталог — PostgreSQL и ClickHouse» и общим release gate «обе программы».
Исторические задачи и доказательства сохраняются. Специальные параметры БД,
SQL probes и версии относятся только к соответствующим рецептам.

## Поддерживаемость и расширение

Приложение допускается по совместимости с поддержанным способом и зарегистрированным
рецептом: формат артефакта, среда, prerequisites, доверие к источнику, точная версия,
объявленные эффекты и проверка результата. Это не обещает совместимость с любым
форматом/ОС или право исполнения неизвестного installer.

Текущая APT-ветка описана [контрактом прямого SSH](../../001-service-foundation/contracts/direct-ssh.md).
PostgreSQL16/ClickHouse — первые конкретные bundled recipes и fixtures этой ветки.
Наличие пакета в APT само по себе не даёт права установки. Другой рецепт подключается
к тем же catalog/compiler/job owners с собственной проверенной схемой, prerequisites,
immutable pins, ресурсами и postchecks. Новый способ установки требует отдельного
контракта до реализации; его добавление не входит в эту поправку области продукта.

Существующие закрытые resource IDs и product enum в DB-specific AST/receipts
остаются схемами этих рецептов, не глобальным enum приложений. Добавление имени
не разрешает эффект. Расширение схем вводится явно с codec/compiler/validation tests;
старые plan bytes не переписываются и не получают новых полномочий. Общие API
не принимают произвольные shell, SQL, package-manager arguments или root config.

## Общие требования и результат

Все приложения используют одного owner/engine, существующие SSH credentials/trust,
host-wide writer, exact approval, durable jobs/receipts, отмену и reconcile001.
Источники, лимиты, defaults и runtime prerequisites определяет контракт выбранного
способа. Неизвестный исход блокирует конфликтующие записи без automatic replay/
rollback. Чистая установка не перезаписывает существующие чужие данные.

Успех требует совпадения выбранного pin и обязательных postchecks рецепта:
version/artifact, принадлежащие ему файлы/службы и работоспособность. SQL обязателен
для DB-рецепта; у другого рецепта проверяется его health, без общего SQL requirement.
Loopback/auth, память, порты и SSE4.2 — условия конкретных рецептов.

Регистрация007 также определяется поддержанным inspection adapter и доказательствами
identity, а не названием БД. Она не означает repair/установку или автоматическую
регистрацию неизвестного ПО. Собственные Plan/Tasks007 остаются отдельным этапом.
Обновление014 использует совместимость и политику данных выбранного рецепта;
успешный переход одного приложения не разрешает миграцию данных другого.

## Приёмка

- **AC-APP-01**: Общий catalog/plan path использует зарегистрированные descriptors,
  compatibility и точные pins; имена берутся из данных рецепта для отображения,
  product-name whitelist вне конкретных adapter/schema отсутствует. Два fixture
  descriptors сохраняют свои pins, версии и ресурсы без смешения.
- **AC-APP-02**: Несовместимый prerequisite или неподдержанный recipe даёт причину
  до remote write. Известное имя БД не позволяет обойти этот отказ.
- **AC-APP-03**: SQL probe включается конкретным DB-рецептом, не общим pipeline;
  failed/unknown/skipped обязательный DB postcheck не даёт success. Рецепт без SQL
  требования не получает выдуманную SQL-проверку или success без собственных checks.
- **AC-APP-04**: Каталог/реестр показывают имя из descriptor, exact version,
  compatibility и фактический результат. Отсутствие обеих БД не является общей
  причиной блокировки независимого поддержанного способа установки.

Текущие unit tests используют синтетические descriptors/pins/typed ports;
они не доказывают реальную установку или новый способ исполнения. Native
qualification относится к выпускаемому рецепту и не требует испытать обе БД
перед выпуском любого независимого поддержанного способа.
