# Feature Specification: Основа сервиса ServerDeck

**Область приложений2026-11-01**: ServerDeck устанавливает приложения
по совместимым способам и рецептам; PostgreSQL/ClickHouse — первые APT-примеры
и тестовые цели, не закрытый каталог продукта. [Действующая граница](../006-software-installation/contracts/application-scope.md).

## Поправка 2026-11-01: операции напрямую по SSH

**Scope**: пользователь поручил полностью заменить отдельно устанавливаемый
executor прямым SSH-выполнением, обновив код и спецификации через весь Spec Kit.
Это поправка существующих 001/006/021, а не новый продукт или пакет.
Ни наличие прежнего кода, ни выполненные исторические задачи не доказывают её готовность.
В вопросах исполнения эта поправка и [контракт](contracts/direct-ssh.md)
заменяют прежние требования об executor, Ansible, enrollment, supervisor/bridge
и их release descriptor. Embedded host, schema3, защита данных и права сохраняются.

### Clarifications — 2026-11-01

- Пользователь выбрал прямой SSH без отдельно устанавливаемого executor;
  затем явно включил и код, и спецификации, и полный цикл Spec Kit.
- Существующий подтверждённый SSH-доступ используется повторно. Root либо
  noninteractive sudo — prerequisite системных изменений; приложение не меняет sudoers.
- Одноразовые ограниченные команды, штатные transient units и служебные записи
  допускаются как детали SSH-выполнения; отдельный агент и Ansible не устанавливаются.
- Обрыв связи не подтверждает отмену или успех. Автоматического повторения
  неопределённой операции нет. Текущий static/unit scope проверок сохраняется.

### User Story SSH1 — Изменить сервер без установки агента (P1)

Владелец подключает сервер существующим профилем и запускает поддержанное
изменение без подготовки ServerDeck-компонентов на сервере.
Ценность: для начала работы нужны SSH и объявленные штатные средства ОС.
Независимая проверка: типизированный SSH port в RAM без серверного executor.

- **AC-SSH-01**: При подтверждённом SSH-доверии и достаточных правах чтение,
  план и согласованное изменение доступны без enrollment и установки агента.
- **AC-SSH-02**: Отсутствие прав или обязательной утилиты показывает конкретную
  причину; нет скрытой установки, запроса sudo-пароля или серверной записи от чтения.
- **AC-SSH-03**: Подмена ключа, credentials/target revision или отзыв выбранного
  согласия до авторизованного dispatch блокирует следующий эффект. Авторизация
  одного шага линеаризуется при durable dispatch intent под native authority gate;
  уже отправленный permit может начать только этот шаг в пределах5s и срока
  выбранной authority, даже если после dispatch SSH потерян или grant отозван.
  Поздний worker с истёкшим permit не начинает эффект; следующих permits нет.

### User Story SSH2 — Установить ПО по проверенному плану (P1)

Владелец выбирает приложение, поддержанный способ установки и точную версию,
просматривает эффекты и настройки, подтверждает план и получает проверяемый результат.
PostgreSQL16/ClickHouse — первые примеры APT-рецептов, не ограничение каталога.
Ценность: установка доступна через тот же продукт без отдельного runtime.
Независимая проверка: обе программы и отказные ответы стандартных команд
моделируются в RAM; это не объявляется реальной установкой.

- **AC-SSH-04**: При подготовленных доверенных APT-источниках план связывает
  точные версии/архитектуры/хеши всех пакетов и исходное состояние; неизвестные
  источники, существующие данные, конфликт зависимостей или NetBird блокируют запись.
- **AC-SSH-05**: Повтор подтверждения одного плана возвращает прежнее задание;
  успех требует фактической версии, состояния службы и обязательных postchecks
  выбранного рецепта; SQL-проверка обязательна для DB-рецептов.
- **AC-SSH-06**: План/каталог не обновляют источники или индексы и не устанавливают
  инструменты; отсутствующий репозиторий объясняется до подтверждения.

### User Story SSH3 — Установить результат после разрыва связи (P1)

Владелец возвращается к тому же заданию после разрыва SSH или перезапуска app,
видит подтверждённые эффекты либо явный неизвестный исход.
Ценность: потеря окна/ответа не превращается в повторную установку.
Независимая проверка: RAM clock/transport/store и сценарии lost reply/restart.

- **AC-SSH-07**: Потеря ответа после возможной отправки сохраняет unknown и
  занятость цели; reconnect/restart не отправляет изменение повторно.
- **AC-SSH-08**: Отмена останавливает следующие шаги; уже запущенная пакетная
  транзакция не убивается и не объявляется отменённой до проверки результата.
- **AC-SSH-09**: Reconcile читает записи исходной попытки и фактическое состояние,
  не запускает новый эффект. Отсутствующая/повреждённая запись не означает «не выполнено».
- **AC-SSH-10**: Два профиля одного физического хоста и два workspace не могут
  одновременно выполнять конфликтующие изменения. Unknown сохраняет блокировку.
- **AC-SSH-11**: Обновление сохраняет профили, секреты, trust, grants, ревизии,
  задания и receipts; старый план/enrollment не разрешает новый SSH-эффект.
- **AC-SSH-12**: После direct install и restart отдельный config/service plan
  использует durable qualified resource provenance и свежие probes. Посторонний
  existing ресурс, historical executor installation или изменённые parent/unit/
  package/managed-file baselines не получают автоматическое adoption.
  DB config в direct плане явно объединяет file write/syntax/restart/postchecks
  в один согласованный effect. Interruption/failed activation не создаёт успешную
  provenance; reconcile не повторяет запись и не запускает скрытый restart.
- **AC-SSH-13**: Для обеих БД successful stop → app restart → отдельный start plan
  работает по сохранённой provenance и offline inactive proof без SQL до старта;
  после старта обязательны live checks. Failed/unknown/cgroup mismatch и изменённый
  offline baseline блокируют запись. Config из inactive явно blocked до отдельного
  запуска; повтор одного ресурса в source AST по-прежнему запрещён.

### Functional Requirements поправки

- **FR-SSH-001**: Engine MUST выполнять поддержанные изменения напрямую по SSH,
  без отдельного установленного ServerDeck-компонента, Ansible и control node.
- **FR-SSH-002**: UI/MCP MUST использовать единый coordinator, SSH pool, текущие
  credentials/trust и permissions. Raw shell, paths, SQL и scripts не становятся входом API.
- **FR-SSH-003**: Engine MUST проверять среду и права без записи при чтении/плане;
  root/noninteractive sudo не подменяют согласие владельца или grant.
- **FR-SSH-004**: Перед каждым эффектом MUST повторно проверяться точная цель,
  выбранное согласие, отмена, исходное состояние и неизменный план. Граница
  разрешения шага — durable authorized dispatch; permit ограничен5s, исходным
  boot/step/authority/target и не продлевается автоматически после потери связи.
- **FR-SSH-005**: Один физический хост MUST иметь одного writer, включая aliases,
  разные процессы/workspace и unknown. Нет очереди ожидания на сервере.
- **FR-SSH-006**: Job/attempt/step и отправка MUST фиксироваться до возможного
  эффекта; повторные запросы не создают повторный эффект.
- **FR-SSH-007**: При потере proof/связи после возможной отправки MUST сохраняться
  unknown без автоматического replay, reset или снятия occupancy.
- **FR-SSH-008**: Отмена MUST различать отсутствие эффектов, частичное выполнение
  и неизвестный исход; detach/закрытие окна не равны отмене.
- **FR-SSH-009**: Reconcile MUST проверять ту же попытку на той же цели,
  подтверждать остановку и результат без повторного выполнения.
- **FR-SSH-010**: Установка MUST сохранять требования 006 к точным пакетам,
  доверенным источникам, данным, NetBird и фактической работоспособности приложения
  по postchecks выбранного рецепта. SQL обязателен только для DB-рецептов.
  Qualified resource provenance MUST сохраняться как данные проверенного direct
  install/result; последующее управление не допускает автоматического adoption.
- **FR-SSH-011**: Обновление MUST сохранять текущие данные schema3; прежние
  executor bindings и планы остаются историей без полномочий нового исполнения.
- **FR-SSH-012**: Интерфейс MUST убрать подготовку/подтверждение executor и
  показывать доступность SSH-операций с причиной отказа и следующим действием.
- **FR-SSH-013**: Поставка MUST исключить обязательные executor-release,
  server installer, Python/Ansible runtime и отдельные серверные entry points.
- **FR-SSH-014**: Команды, stdout/stderr, время, записи и временные артефакты
  MUST быть ограничены; недостоверные/усечённые данные не означают успех.
- **FR-SSH-015**: Секреты MUST оставаться в существующей custody; SSH-пароль
  не передаётся в sudo, argv, shell text, receipts, events или диагностику.

### Success Criteria поправки

- **SC-SSH-01**: Во всех AC-SSH-01–13 отсутствует потребность установить
  ServerDeck-компонент на целевую машину; оба интерфейса используют один путь.
- **SC-SSH-02**: Все duplicate/lost-reply/cancel/restart/alias сценарии имеют
  не более одного эффекта каждого подтверждённого шага и честный исход.
- **SC-SSH-03**: Все сохранённые объекты из AC-SSH-11 сохраняют IDs и содержимое;
  ни один прежний план или enrollment не даёт нового права исполнения.
- **SC-SSH-04**: Обязательные static/unit проверки, ссылки, Analyze, Converge и
  независимый review/fix loop завершены с фактическими результатами; нативная
  работоспособность не приписывается RAM-проверкам.

### Key Entities и границы

Сохраняются Profile/Trust/Grant/AutomationRevision/Plan/Approval/Job/Event/Receipt.
SSH-попытка связывает один immutable plan с целевым host, boot, step и результатом.
Запись результата на хосте — данные восстановления, не API/служба или источник прав.
Вне scope: новые серверные функции 007–020, backend, публикация, изменение реальных
серверов, автоматическая миграция старого сервиса до ServerDeckNext и production rollout.

**Последнее указание пользователя — unit only**: все прежние собственные тесты,
fixtures и harness удаляются; пишутся только unit-тесты под эту задачу. Дизайн,
widget/visual/integration/native/реальные SSH/container проверки сейчас не выполняются.
Исторические результаты ниже остаются историей, не текущим gate. Изменение не
разрешает потерять функции, данные, права или проверки целевого поведения в новых units.

**Уточнение2026-10-30, без обратной совместимости**: действующий
[контракт](contracts/embedded-migration.md) исключает legacy runtime/API/bootstrap,

в этой же задаче после переноса используемой логики, а не остаётся «на переход».
Поддерживается только целевой schema3; несовместимые файлы не изменяются.

## User Scenarios & Testing

### User Story 1 — Запустить собственное рабочее пространство (Priority: P1)

Владелец серверов запускает ServerDeck на Windows. Приложение запускает встроенный движок в своём процессе. После проверки версии и готовности защиты появляется пустое рабочее пространство. Пользователь создаёт профиль, сохраняет его и снова видит после закрытия и повторного запуска. Ручной запуск второго процесса и аккаунт в облаке не нужны.

**Why this priority**: Это первый исполняемый сервис, на котором можно строить все последующие функции.
**Independent Test**: Чистый Windows-профиль, отсутствие интернета, два окна клиента и отказ защищённого хранения. SSH-сервер и последующие пакеты не требуются.
**Acceptance Scenarios**:

1. **AC-SVC-1A Given** чистое новое пространство, **When** пользователь запускает клиент, **Then** он видит готовое пустое пространство, один принадлежащий ему встроенный движок, доступные Серверы и Настройки и понятные недоступные будущие функции; демонстрационные профили не появляются.
2. **AC-SVC-1B Given** готовая защита, **When** пользователь создаёт профиль, закрывает клиент и открывает снова, **Then** поля и ссылка доступа восстановлены; обычные поля сохраняются без шифрования приложения, а пароль, приватный ключ и passphrase отсутствуют в открытом виде в постоянных файлах, обычном ответе API и диагностике.
3. **AC-SVC-1C Given** одновременный запуск двух окон, **When** оба обращаются к одному пространству, **Then** данные обслуживает один владелец хранения; подтверждённая правка видна обоим, конфликт не теряет другую правку.
4. **AC-SVC-BOOT Given** отказ защиты ОС, повреждённый credential blob/хранилище либо неподходящая версия службы, **When** клиент запускается, **Then** обычные запросы блокируются с отдельной причиной, исходные данные не сбрасываются и другой процесс не завершается автоматически.

### User Story 2 — Пройти первый законченный серверный сценарий (Priority: P1)

Пользователь создаёт профиль → подтверждает идентичность сервера → сохраняет доступ → подключается → получает сведения об ОС, ПО и ресурсах → открывает ограниченный журнал. Он понимает, к какому серверу относятся данные, когда они получены и почему некоторые сведения недоступны. Сервер не меняется.

**Why this priority**: Это минимальная практическая ценность продукта, а не демонстрация интерфейса над fixtures.
**Independent Test**: Одноразовый Ubuntu 24.04 amd64/systemd сервер, новый host key, ограниченный пользователь и разрыв связи; нет установочного исполнителя, backend, каталога расширений или UI пакета 004.
**Acceptance Scenarios**:

1. **AC-SVC-2A Given** доступный поддержанный сервер, **When** пользователь проходит полный маршрут, **Then** показаны фактическая идентичность, ОС, версии обнаруженных пакетов и службы, CPU/RAM/корневой диск и выбранный журнал; не выполняется ни одной команды изменения сервера.
2. **AC-SVC-2B Given** неизвестный либо изменённый host key, **When** запрошено подключение, **Then** неизвестный требует явного подтверждения, изменённый блокирует чтение и запись; отмена не принимает доверие и не удаляет профиль.
3. **AC-SVC-2C Given** отказ прав, таймаут, неподдержанный источник или разрыв, **When** показан результат, **Then** сохранены цель и прежнее наблюдение с ошибкой/устареванием, оно не выдаётся за текущий здоровый ноль; доступный второй сервер продолжает работать. В отдельном многоконном варианте окно A читает журнал, окно B меняет connection/access revision или отзывает доверие: с момента подтверждённой правки прежний транспорт закрывается, подписки прекращаются во всех окнах, поздние ответы отбрасываются. Старые наблюдения сохраняют прежнюю идентичность и отметку неактуальности; новая цель не получает их как свои данные. Повторное чтение требует явного подключения и действующего доступа/доверия.
4. **AC-SVC-READ Given** журнал больше лимита и метрики с разрывом, **When** пользователь переключает экран, окно и тему, **Then** действуют общие лимиты службы, видны потери и разрывы; новый клиент не умножает подключения или скрыто расширяет буфер.

### User Story 3 — Понимать жизненный цикл и безопасно восстановиться (Priority: P1)

Пользователь различает недоступный сервер и недоступную локальную службу. При перезапуске службы клиент повторно проверяет её идентичность и готовность, получает сохранённое состояние и явно восстанавливает нужное подключение. Он может закрыть окно без потери сохранённых данных. Основа будущих заданий проверяется изолированным исполнителем; реальные серверные изменения остаются выключены до 006.

**Why this priority**: Последующие функции обязаны использовать один устойчивый сервис, а не создавать собственные процессы, базы и способы доступа.
**Independent Test**: Прерывание старта, сохранения и чтения; перезапуск локальной службы; fixture-задание с неизвестным итогом, повтором подтверждения и отменой. Установка настоящего ПО не нужна.
**Acceptance Scenarios**:

1. **AC-SVC-3A Given** готовая служба и сохранённые данные, **When** процесс службы завершается и пользователь выбирает восстановление, **Then** клиент проходит новый handshake, восстанавливает данные и показывает разрыв чтения; старое состояние транспорта не считается живым.
2. **AC-SVC-3B Given** чтения и последнее окно, **When** окно закрыто, **Then** UI interests снимаются, приложение остаётся в tray с тем же engine; MCP/jobs interests продолжаются. При недоступном tray окно не скрывается.
3. **AC-SVC-3C Given** изолированное задание, **When** повторены подтверждение, потеря ответа, отмена и перезапуск, **Then** существует одно задание, события упорядочены, unknown сохраняет запрет конфликтующей записи, успех подтверждён результатом; реальный серверный executor недоступен в обычном запуске этого пакета.
4. **AC-SVC-CLOSE Given** unresolved job, **When** пользователь закрывает окно, **Then** app остаётся в tray без cancel/снятия occupancy; explicit exit предупреждает о remote работе, закрывает observer и сохраняет unknown/reconcile после restart.

### Edge Cases

- Второе окно, одновременный старт и сбой первого запуска не создают второго владельца базы.
- Служба другого пользователя, пространства, поколения продукта или несовместимой версии не обслуживает этот клиент.
- ОС не разрешила защиту или credential blob повреждён: нет открытого режима сохранения секретов, подмены доступа или автоматического нового пустого пространства.
- Ответ сохранения потерян после записи: интерфейс не объявляет успех и сначала сверяет прежний запрос/ревизию; повтор не создаёт второго профиля.
- Отказ локальной службы не означает, что удалённый сервер выключен; потеря SSH не означает, что локальное сохранение перестало работать.
- Удаление последнего профиля оставляет пустое пространство; отмена настройки не подключается и не принимает ключ.
- Профили одного хоста, другое окно и другое устройство не дают параллельных конфликтующих writers.
- Выход UI, штатное завершение службы, аварийное убийство процесса и перезагрузка ОС имеют разные последствия; forced shutdown не обещает отмены удалённого эффекта.

### Что представляет собой сервис

**ServerDeck — локальный продукт управления уже существующими Linux-серверами:** пользовательский клиент и принадлежащая текущему пользователю локальная служба. Он объединяет подключения, наблюдения, диагностику и поддержанные управляемые изменения независимо от провайдера сервера. Пользователь приносит собственный SSH-доступ. Сервис не создаёт облачные машины, не является обязательным облачным control plane и не требует устанавливать полный агент на каждый сервер ради чтения.

Основные пользователи — владелец серверов, оператор чтения и администратор изменения. Эти роли описывают сценарии и реальные права на хосте; первая реализация не добавляет корпоративную систему RBAC. Одна установленная локальная среда принадлежит одному пользователю ОС. Совместный доступ разных людей через один системный daemon не входит в этот пакет.

Первый результат — реальный запускаемый Windows-клиент и его локальная служба с защищённым сохранением и полным read-only маршрутом. Пакеты 002–020 расширяют этот результат. Нельзя признать 001 выполненным только по экрану fixtures, библиотеке хранения или схеме компонентов.

**Технологическая базовая линия проекта** установлена [конституцией](../../.specify/memory/constitution.md): Flutter/Dart UI и встроенный доменный Dart-движок, авторизованный контракт и Isar под исключительным владением движка. Здесь описаны продуктовые обязанности и границы этих компонентов; точные API-схемы, layout кода и механизмы реализации оформляются Plan до соответствующих Tasks. Стек не меняется этим документом.

### Запуск, обмен и завершение

1. App проверяет bundle/runtime, берёт общий writer lease и открывает нынешнее
   пространство с прежними credentials/trust. Занятый lease не даёт второго store.
2. EngineHost создаёт services и host-owned owner sessions. Ready после local
   recovery, без требования сети/backend. Deadline30s, безопасный failure.
3. UI использует in-process gateway. Optional MCP использует app-verified IPC
   и отдельный grant, без owner authority из caller payload.
4. SSH запускается явно с текущими access/trust revisions и общими budgets.
5. Close последнего desktop окна сохраняет app/engine/MCP в tray/menu bar.
   Если tray недоступен, окно остаётся. Явный «Выход» закрывает весь host.
6. Sleep/mobile suspend прекращает observer. Crash не требует callback. Accepted
   remote job не становится cancelled/success. Resume/restart сверяет ту же attempt
   при действующих permissions, без повторного apply.

### Владение данными и минимальная защита

До **первого** сохранения доступа средствами ОС текущего пользователя защищаются приватные SSH-ключи, пароли и passphrase. Профиль содержит непрозрачную ссылку на защищённый набор доступа. Имена, адреса, порты, SSH-пользователи, теги, fingerprints, ссылки, настройки, наблюдения, планы, история и индексы хранятся как обычные данные без шифрования приложения. База и рабочие файлы доступны только владельцу и системным компонентам по правам ОС. Приватность этих метаданных требует контроля доступа и состава экспорта, но не обещает конфиденциальности скопированной базы.

Секреты допустимы временно в памяти для ввода и разрешённого действия; обычное чтение профиля их не возвращает. Backup/temp/diagnostic файлы не создают открытых копий секретов. Отказ защиты ОС, неизвестный формат и обнаруженное повреждение блокируют обычные запросы с сохранением исходных данных; повреждённый доступ не заменяется новым и не превращается в открытый пароль. Защита секретов обязательна в 001, а не отложена до 002.

Модель защиты секретов первой реализации — копия файлов приложения без полномочий текущего пользователя, другой пользователь ОС и повреждение защищённых записей. Конфиденциальность обычных метаданных в скопированной базе не обещается. Активный вредоносный процесс с полными правами вошедшего пользователя, память и согласованный откат всех файлов вне гарантий. 002 расширяет аудит защиты секретов, проверку привязок, recovery и независимую платформенную приёмку этой работающей основы.

Профили/настройки/наблюдения/задания сохраняются в пространстве; raw journal buffers живут только в текущей сессии службы. Диагностический результат не подменяет профиль. База не является хранилищем скачанных файлов либо резервных копий удалённого приложения — соответствующие пакеты определяют явные цели, а locald сохраняет их приватные метаданные. Изменение цели или доступа инвалидирует review. Удаление профиля не удаляет сервер, но блокируется его активным/unknown заданием.

### Functional Requirements

#### Общие требования, которыми владеет основа

- **FR-001**: Профили, сохранённые наблюдения и история должны открываться без облачного аккаунта и интернета. Живые сведения требуют достижимости самого сервера; эти два условия не смешиваются.
- **FR-002**: Пользователь должен видеть отдельно поддержку клиентской платформы и удалённой функции. Успешная установка клиента не должна показывать недоступную операцию как готовую.
- **FR-007**: Пользователь должен создавать, редактировать и удалять профиль с именем, адресом, портом, пользователем и тегами. Секреты не являются обычными полями профиля.
- **FR-008**: Первое подключение должно объяснять последовательность идентичности, доступа и соединения. Сохранение без соединения и отмена сохраняют профиль без удалённых изменений.
- **FR-009**: Подготовленный профиль должен подключаться одним основным действием без повторного подтверждения уже проверенной идентичности и неизменного доступа.
- **FR-010**: Неизвестная идентичность требует подтверждения; изменившаяся блокирует подключение. Автоматическая замена доверия или продолжение чтения после такой ошибки запрещены.
- **FR-012**: Ошибка или медленный ответ одного сервера должны сохранять доступность остальных профилей, их данных и пользовательских действий в пределах действующих лимитов подключений.
- **FR-013**: На экране объекта и в подтверждении изменения должны быть видны имя и адрес целевого сервера. Навигация не должна незаметно подменять цель подготовленного действия.
- **FR-014**: Пустое пространство должно предлагать добавление сервера без автоматически появляющихся демонстрационных профилей, программ и измерений.
- **FR-035**: Перед изменением должны быть видны цель, исходное состояние, параметры, ожидаемые эффекты, предварительные условия, возможный перерыв и критерий результата. Неизвестные существенные эффекты блокируют запуск.
- **FR-036**: Согласие относится к неизменному плану. Изменение сервера, доступа, версии, параметров или существенного исходного состояния требует нового просмотра и подтверждения.
- **FR-037**: Просмотр и проверка готовности не выполняют эффекты плана и не исправляют условия автоматически. Пользователь различает проверку, подтверждение и фактический запуск.
- **FR-038**: Конфликтующие изменения одного физического сервера не выполняются одновременно даже через разные профили. Причина ожидания или отказа должна быть понятна.
- **FR-039**: Повторное подтверждение возвращает прежнее задание. Потерянный ответ и повторное нажатие не дают основание заново выполнить уже начатые эффекты.
- **FR-040**: История сохраняет цель, согласованный план, начало, этапы, завершение и причину ошибки после закрытия клиента. Сохранение истории не должно раскрывать секреты.
- **FR-041**: Отмена до запуска не изменяет сервер; после запуска означает запрос остановки в допустимой точке. Пользователь видит разницу между запросом отмены, остановкой и сохранёнными эффектами.
- **FR-042**: Потеря связи или подтверждения сохраняет неизвестный исход до проверки прежнего задания. Автоматический повтор записи и освобождение конфликтующей цели без проверки запрещены.
- **FR-043**: Успешный итог требует повторного чтения фактического состояния и применимой проверки работоспособности. Завершение исполнителя без проверки не считается успехом.
- **FR-044**: Запрещено менять NetBird и его клиенты: пакеты, службы, конфигурацию, данные, доступ и зависимости с такими эффектами. Ограничение действует и для дополнительных модулей.
- **FR-124**: Действия соответствуют фактическим правам пользователя; просмотр не повышает их скрыто. Текущий уровень полномочий понятен до запуска изменения.
- **FR-121**: Пароли, приватные ключи и защитные фразы сохраняются в защищённом хранилище пользователя. Его отказ не создаёт открытой копии или запасного незащищённого доступа.
- **FR-122**: Шифрование средствами ОС применяется к секретам доступа — приватным SSH-ключам, паролям и passphrase — до их первой записи. Обычные данные рабочего пространства хранятся без шифрования приложения с ограничением доступа по правам ОС. Общего ключа шифрования базы и зашифрованного агрегата рабочего пространства нет. Пакет 002-security-storage расширяет аудит и восстановление защиты секретов.
- **FR-123**: Обычная история, ошибки и стандартный экспорт исключают секреты. Включение приватных сведений в экспорт требует явного выбора состава и назначения.

#### Уточнения первоначального сценария

- **FR-002-LOCAL-01**: Профиль содержит устойчивый локальный ID, имя, адрес, порт 1–65535 (по умолчанию 22), SSH-пользователя, теги и ссылку доступа. Поддержаны пароль и приватный ключ с необязательной passphrase; секрет не возвращается обычным чтением профиля.
- **FR-002-LOCAL-02**: После установки пространство пусто. Максимум 250 профилей; превышение отклонено с сохранением существующих данных. На старте нет соединений, заданий и синтетических наблюдений без явного действия.
- **FR-002-LOCAL-03**: Изменение полей подключения отзывает прежнее доверие к этой цели и инвалидирует reviews. Удаление профиля удаляет локальные связи/кэш, но не сервер; активное или unknown задание блокирует изменение/удаление его цели до проверки.
- **FR-002-LOCAL-04**: Новый ключ показывается с адресом и fingerprint до принятия. Изменённый ключ требует отдельного явного пересмотра доверия; соединение не продолжает ни чтения, ни записи. Отмена не подтверждает ключ.
- **FR-002-LOCAL-05**: Не более двух одновременно активных SSH-транспортов; превышение явно отклоняется. Предельное время подключения 15 секунд, отдельного базового чтения 30 секунд, отмена ожидания доступна; один отказ не останавливает интерфейс.
- **FR-002-LOCAL-06**: Базовое чтение Ubuntu 24.04 amd64/systemd показывает ОС, software packages/units, CPU/RAM/root disk и journald. Недоступные custom binaries, containers и workloads не выдаются за подтверждённо отсутствующие; расширения принадлежат 008/017.
- **FR-002-LOCAL-07**: Журналы: история 100 записей по умолчанию, допустимо 1–1000; буфер текущей сессии 500 на сервер, запись максимум 64 KiB. Overflow, parse error, duplicate и gap учитываются явно. Постоянное хранение raw logs не включено.
- **FR-002-LOCAL-08**: Метрики получают реальные timestamps; stale после 15 секунд, инвентарь — после пяти минут. Неизвестные значения отсутствуют, а не равны нулю. Failed refresh сохраняет прежнее наблюдение с ошибкой.
- **FR-002-LOCAL-09**: Задания имеют состояния queued, preflight, awaiting-approval, running, cancel-requested, cancelled, succeeded, failed, unknown, reconciling. План и события сохраняются до первого эффекта; порядок событий устойчив после перезапуска.
- **FR-002-LOCAL-10**: Review действует пять минут и привязан к цели, доступу, версии рецепта, параметрам и значимому исходному состоянию. Изменение привязки или срока требует новой проверки и согласия.
- **FR-002-LOCAL-11**: Один writer координируется по подтверждённой идентичности физического хоста, в том числе через разные профили/устройства. Невозможность доказать уникальность цели блокирует запись; локальная блокировка сама по себе недостаточна.
- **FR-002-LOCAL-12**: Исполнитель имеет минимальные права и только объявленные действия; его отсутствие/неподходящая версия видны до approval. Подключение и чтение не устанавливают его и не расширяют полномочия.
- **FR-002-LOCAL-13**: Платформа может проверяться на test-only executor до включения первого рецепта. Fixtures никогда не показываются реальными результатами нормального запуска; первая настоящая запись проходит отдельный gate 006.
- **FR-002-LOCAL-14**: Локальная история новых заданий обязательна для отказоустойчивости; запрет сохранять историю старых документов не отменяет её. Unknown и его конфликтующая блокировка не очищаются по таймеру либо окончанию страницы истории.

#### Обязательства целостного сервиса

- **FR-SVC-001**: Продукт MUST поставлять одно приложение со встроенным движком без обязательного locald/локальной службы. Первый этап Windows, прочие платформы по capability matrix. Удалённое чтение — Ubuntu24.04 amd64/systemd.
- **FR-SVC-002**: UI MUST использовать in-process EngineGateway; только движок владеет БД, SSH и coordinator. MCP использует app-verified IPC bridge; UI не получает прямого доступа к storage.
- **FR-SVC-003**: Bootstrap MUST проверять bundle/app identity и исключительное владение engine. Второй процесс не открывает БД, проверенный activation-only channel может показать существующее окно.
- **FR-SVC-004**: Local API MUST быть авторизованным и локальным, отклонять чужого пользователя/пространство/версию и недоверенный клиент. Наличие сетевого endpoint не заменяет готовность защиты; read-only capability не разрешает privileged запись.
- **FR-SVC-005**: Readiness MUST различать перечисленные состояния; обычные запросы допускаются только в ready. Startup deadline 30 секунд; повтор присоединяется к той же живой попытке, не подменяет ключ, данные или процесс.
- **FR-SVC-006**: Исторический hard cutover исключает импорт сервиса до ServerDeckNext. Нынешние данные ServerDeckNext MUST сохраняться по embedded-migration contract без plaintext fallback и двух писателей. Старые процессы не завершаются автоматически.
- **FR-SVC-007**: До первой записи секрета MUST действовать защита средствами ОС текущего пользователя; атомарное сохранение MUST охватывать профиль, ссылку, защищённый набор доступа и результат операции. Отказ/повреждение не разрешает открытого сохранения секрета. Метаданные и индексы не шифруются приложением; их хранение ограничено правами ОС.
- **FR-SVC-008**: Первый готовый сценарий MUST включать фактическое подключение, ОС, обнаруженные пакеты/units, CPU/RAM/root disk и ограниченный journald. Недостаток прав и несовместимость источника видны, а не заменены synthetic наблюдениями. Чтения и подписки связаны с profile ID, connection/access/trust revision и поколением службы. Подтверждённое изменение любой из этих ревизий либо отзыв доступа/доверия немедленно запрещает прежнее чтение: locald закрывает соответствующий транспорт, прекращает подписки во всех окнах и не принимает ответы в полёте после границы изменения. Сохранённые наблюдения остаются привязаны к прежней идентичности с отметкой неактуальности и не смешиваются с новой целью. Правка только имени/тегов не отзывает транспорт. Для возобновления необходимо явное подключение с повторной проверкой действующих credentials и доверия; автоматического принятия нового ключа нет. Активные/unknown задания сохраняют отдельный запрет смены цели по FR-002-LOCAL-03; остановка чтения не означает отмену либо успех такого задания.
- **FR-SVC-009**: Один locald MUST обеспечивать глобальные бюджеты всех своих окон: 250 профилей, максимум два SSH-транспорта, connect deadline 15 секунд, одно базовое чтение максимум 30 секунд. Превышение не открывает третий транспорт и не блокирует UI.
- **FR-SVC-010**: Journald MUST сохранять default 100/range 1–1000, максимум 500 записей на сервер и 64 KiB на запись; общий текст буферов службы не более 64 MiB. При вытеснении старых записей/буферов пользователь видит потери; raw logs не сохраняются в основной БД.
- **FR-SVC-011**: Метрики MUST собираться раз в пять секунд только для явного активного подключения, с не более 120 точками/10 минут на сервер. Stale после 15 секунд, inventory stale после пяти минут; данные старше окна не рисуются текущими. Первое подключение делает ограниченное чтение inventory; дальнейшая перепроверка явная.
- **FR-SVC-012**: Close последнего desktop окна MUST оставлять app/engine в tray; снимаются только UI interests. Explicit exit закрывает admission, дренирует до10s и завершает host; remote accepted jobs не считаются отменёнными.
- **FR-SVC-013**: После аварии службы MUST сохраняться уже подтверждённые записи и история; новое поколение требует handshake и явного восстановления чтения. Unknown задание остаётся заблокированным до проверки прежнего исхода; startup не запускает новый write attempt.
- **FR-SVC-014**: Нормальный startup MUST показывать только реальные сохранённые данные либо пустоту. Fixture injection и тестовый executor отделены от обычного запуска; реальные write recipes отсутствуют до gate 006.
- **FR-SVC-015**: Mutation профиля/настроек MUST использовать устойчивую идентичность запроса и ожидаемую ревизию; потеря reply после commit сверяется с прежним результатом, конкурентная правка даёт конфликт. Сбой сохранения не считается успешной правкой в памяти UI.
- **FR-SVC-016**: Ошибка MUST указывать локальную/удалённую границу, категорию и безопасный следующий шаг. Credentials, ключи, auth material и приватные значения не попадают в обычные логи/errors; намеренный экспорт следует FR-123.
- **FR-SVC-017**: Backend, privileged helper, provider API и Docker/runner MUST NOT требоваться для bootstrap, профилей и SSH-чтения. Preconditions write executor вводит 006, синхронизацию и backend — 020.
- **FR-SVC-018**: Базовый UI MUST иметь пять основных разделов, текущую цель, различимые readiness/connection/data состояния, обе темы и клавиатурную доступность. Future actions объясняют недоступность; нет скрытой замены реального экрана demo.
- **FR-SVC-019**: Dev/production entry point MUST запускать единое приложение с native libraries без locald. MCP stdio mode того же serverdeck.exe лишь соединяется с app. Prerequisites/совместимость определяет Plan, поставку расширяет005.
- **FR-SVC-020**: Реальные read-only adapter и fixture job coordinator MUST проверяться независимо: disposable Linux для фактов чтения; изолированный executor для recovery/locking. Нельзя засчитать одну форму проверки вместо другой или использовать реальный сохранённый сервер автоматически.

### Key Entities

- **Пространство**: собственная идентичность продукта/пользователя, обычные данные, защищённые секреты доступа и формат; один обслуживающий владелец.
- **Сессия клиента и поколение службы**: полномочия Local API, текущие подписки и readiness; после перезапуска прежняя сессия недействительна.
- **Профиль и доступ**: стабильный ID, name/address/port/user/tags, защищённая credential reference и revision; не сами секреты.
- **Доверие к хосту**: подтверждённая цель и fingerprint, версия доверия и явный отзыв; изменённый ключ не заменяется наблюдением.
- **Наблюдение**: цель, источник, время, значение, полнота и ошибка; кэш не доказывает текущую доступность.
- **Подписка чтения**: выбранный источник, lifecycle/лимиты, cursor и потери; принадлежащий окну интерес, разделяемый транспорт locald.
- **План, approval и задание**: неизменные входы/цель/доступ/версия, review expiry, события и состояние; полномочия исполнения отдельно от права чтения.
- **Идентичность физического хоста и writer**: связывает конфликтующие задания разных профилей/устройств; unknown удерживает запрет до reconciliation.

## Success Criteria

### Measurable Outcomes

- **SC-SVC-001**: На чистом Windows-профиле без интернета два запуска дают один готовый сервис и одно пространство; повторный запуск восстанавливает подтверждённые профили. Нормальная и отказная startup попытки выходят из неопределённого ожидания за 30 секунд.
- **SC-SVC-002**: Не менее 4 из 5 участников без подсказки проходят создание профиля → доверие → доступ → подключение → сведения; без ошибок определяют целевой сервер и отличают локальную ошибку от недоступности сервера. Проверка выполняется на подготовленном disposable стенде, не на demo UI.
- **SC-SVC-003**: Во всех successful/rejected базовых чтениях ноль host-write actions; изменённый ключ, отказ прав и неподдержанный источник не дают здорового нуля. Одно сломанное соединение не прекращает доступное второе.
- **SC-SVC-004**: Синтетические маркеры пароля, приватного ключа и passphrase отсутствуют в открытом виде в постоянных файлах и диагностике после save/restart; обычные поля профиля сохраняются без шифрования приложения. Отказ защиты не создаёт открытого секрета или нового пустого пространства. Windows reboot и другой пользователь проверены до приёмки полной основы.
- **SC-SVC-005**: В duplicate-start, concurrent-edit, reply-loss-after-save и process-restart сценариях сохраняется один владелец, одна правка либо явный конфликт; ни одна подтверждённая запись не теряется молча.
- **SC-SVC-006**: Fixture job проверки подтверждают одно задание/набор эффектов, устойчивый порядок событий, честную отмену и сохранение unknown/lock; обычный запуск 001 не может включить настоящий executor.
- **SC-SVC-007**: При двух окнах, excess connect, большом журнале и закрытии последнего окна не превышаются все лимиты FR-SVC-009–011; потери видны, ресурсы без владельца освобождены. При незавершённом задании штатное shutdown для update блокируется.
- **SC-SVC-008**: Базовые сценарии доступны в обеих темах на 1100×760, 800×600, 360×800 и 390×800 без перекрытия действий; подробная композиция 003/004 не является условием существования самого маршрута.

- **SC-002-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-002-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-002-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-002-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.

### User Scenarios & Testing

#### User Story 1 — Одно приложение вместо обязательного демона (Priority: P1)

Пользователь запускает ServerDeck и управляет профилями/SSH через встроенный движок.
Закрытие окна оставляет desktop-приложение в трее, «Выход» завершает процесс.

**Independent Test**: unit модели lifecycle/ownership и widget bootstrap с fake adapters.

- **AC-SVC-EMB-01**: запуск, второй запуск, второе окно и два MCP-клиента используют
  одного владельца workspace и sampler каждой цели; ни один путь не запускает locald.
- **AC-SVC-EMB-02**: скрытие окна сохраняет работу/MCP; «Выход», suspend и crash имеют
  различимые результаты по [lifecycle](contracts/embedded-engine.md). После выхода MCP недоступен.
- **AC-SVC-EMB-03**: невозможность открыть секреты/БД/блокировку даёт безопасный отказ,
  сохраняет файлы и не создаёт пустую замену. Отсутствующий tray не скрывает окно молча.

#### User Story 2 — Обновить приложение без потери состояния (Priority: P1)

Пользователь сохраняет профили, секреты, настройки, trust, grants, историю,
планы и задания текущей реализации; возвращается к совместимой сборке без двух писателей.

**Independent Test**: unit orchestration с синтетическим workspace и отказами на границах.

- **AC-SVC-EMB-04**: новый движок видит те же ID, ревизии, bindings, защищённые blobs
  и host keys; автоподтверждение ключа запрещено.
- **AC-SVC-EMB-05**: живой legacy locald блокирует adoption до штатного завершения;
  не убивается и не открывается конкурентно. Ошибка/перезапуск не сбрасывают состояние.
- **AC-SVC-EMB-06**: схемы1/2/unknown и legacy migration residues отвергаются до
  writable open; исходные файлы нетронуты. Поддержки старых binary/API или rollback
  нет. [Целевой storage contract](contracts/embedded-migration.md).

#### User Story 3 — Сохранить MCP, права и достоверность заданий (Priority: P1)

ИИ использует прежние tools и grants через минимальный stdio-мост к приложению.
Обрыв наблюдения не выдаётся за успех, отмену или разрешение повторить apply.

**Independent Test**: unit MCP/engine через fake IPC и executor, widget подтверждения.

- **AC-SVC-EMB-07**: tool schemas, IDs и permission-сценарии 021 сохранены; старый
  мост отклонён явно; отзыв grant запрещает следующие эффекты, owner права
  недостижимы из DTO MCP. Credentials/raw SSH не выдаются.
- **AC-SVC-EMB-08**: потеря ACK submit, сети или процесса после отправки оставляет
  unknown и host occupancy; повторный apply запрещён до авторизованной сверки
  той же attempt. Поздний ответ старого поколения не меняет актуальную цель.
- **AC-SVC-EMB-09**: принятая удалённая работа отделена от локального наблюдения;
  возобновление наблюдения не отправляет submit заново и не восстанавливает согласие.

#### User Story 4 — Переносимое ядро с честными платформенными границами (Priority: P2)

Одно доменное ядро обслуживает приложения; доступные функции определяет платформенный
адаптер. Неподдерживаемая функция объясняется, а не эмулируется успехом.

**Independent Test**: unit capability matrix, fake vault/lifecycle, static import boundary.

- **AC-SVC-EMB-10**: ядро не импортирует Flutter/Windows; UI не импортирует Isar/SSH
  напрямую. Не-Windows hosts не импортируют Windows FFI транзитивно.
- **AC-SVC-EMB-11**: mobile background не обещает непрерывный SSH/MCP, resume сверяет
  состояние; отсутствие vault блокирует secrets без plaintext fallback.
- **AC-SVC-EMB-12**: Web не предлагает прямой SSH или мнимое локальное соединение;
  обычный desktop/mobile работает без backend, облака и отдельной службы.

#### Edge Cases

Одновременный start; старый locald жив; DB close завис; повреждённый manifest;
vault locked; смена SID; revoke между планом и apply; host key изменён в полёте;
tray отсутствует; sleep/force-stop без callback; submit без ACK; remote supervisor
перезапущен; cursor устарел; диск заполнен. Безопасные состояния заданы контрактами.

### Requirements

#### Functional Requirements

- **FR-SVC-EMB-01**: Desktop/mobile MUST поставляться одним приложением со встроенным
  движком; locald/локальная служба/backend MUST NOT быть условием обычной работы.
- **FR-SVC-EMB-02**: Доменное ядро MUST владеть профилями, trust/credentials, SSH,
  наблюдениями, планами, jobs, правами и восстановлением; UI/MCP используют общий
  авторизованный вход. Рабочая логика нынешнего locald переиспользуется.
- **FR-SVC-EMB-03**: Один владелец workspace MUST обеспечивать одну БД, один sampler
  на identity цели, общие бюджеты и последовательность мутаций всех клиентов.
- **FR-SVC-EMB-04**: Desktop MUST оставаться в трее после закрытия окна; явный выход
  закрывает движок/MCP. Mobile suspend/kill не равнозначен штатному выходу.
- **FR-SVC-EMB-05**: Обновление MUST сохранять данные нынешнего ServerDeckNext, включая
  секреты, host-key trust, настройки, историю, права, подтверждения и jobs; secrets
  защищены ОС. Сессии и одноразовые согласия не становятся повторно используемыми.
- **FR-SVC-EMB-06**: Реализация MUST поддерживать только целевой schema3, без
  legacy API/bootstrap/upgrade1/2/rollback/fallback. При несовместимости файлы
  сохраняются нетронутыми; второй writer/автоматический reset запрещены.
- **FR-SVC-EMB-07**: MCP MUST сохранить tools и permissions 021 через минимальный мост
  к работающему приложению; закрытое приложение даёт понятный отказ. Постоянный
  удалённый endpoint относится к будущему необязательному узлу.
- **FR-SVC-EMB-08**: Удалённый job MUST быть отделён от наблюдения; unknown сохраняет
  блокировку записи, авторизацию и reconciliation. Автоповтор apply запрещён.
- **FR-SVC-EMB-09**: Поколение движка, ревизии цели/доступа/trust/grant и порядок событий
  MUST ограничивать поздние ответы; отмена наблюдения не отменяет удалённый эффект.
- **FR-SVC-EMB-10**: Каждая платформа MUST иметь capability matrix, защищённое хранение
  и lifecycle adapter. Непроверенная платформа не заявляется поддержанной.
- **FR-SVC-EMB-11**: Web MUST NOT выполнять прямой TCP/SSH. Future management node
  необязателен, не реализуется и не развёртывается этой задачей.
- **FR-SVC-EMB-12**: План MUST разделять extraction, Windows cutover и последующие
  платформы; сохранять границы 003, историю задач и поведенческие проверки.
- **FR-SVC-EMB-13**: Подготовка/реализация MUST использовать только static/unit/widget
  локально/CI; адресные тесты — после падения полного набора. Native/integration/
  real-SSH/container/manual native dispatch/UI automation запрещены; это
  ограничивает доказательства, но не меняет требуемое поведение.

#### Key Entities

EngineHost, WorkspaceLease, OwnerSession, GrantedSession, CapabilitySnapshot,
TargetIdentity, ObservationSubscription, RemoteAttempt, LocalJobObservation.
Постоянные сущности сохраняют модели 001/021; детали — [data model](data-model.md).

### Success Criteria

- **SC-SVC-EMB-01**: Во всех тестируемых startup/exit/second-client ветках нет запуска
  отдельного locald, двух владельцев или двух sampler одной цели.
- **SC-SVC-EMB-02**: Во всех synthetic migration/refusal/restart сценариях нет потери
  подтверждённого состояния, нового доверенного host key или открытого секрета.
- **SC-SVC-EMB-03**: Все tools и положительные/отказные permission-сценарии 021 имеют
  соответствие тестам через встроенный движок, без расширения полномочий.
- **SC-SVC-EMB-04**: Во всех loss/late-response сценариях неопределённый исход видим
  и блокирует повтор; ни один такой сценарий не выдаёт ложный успех.
- **SC-SVC-EMB-05**: Все шесть платформенных строк имеют статус и ограничения;
  Windows этап не заявляет проверенную поддержку остальных платформ.

### Assumptions and Scope

Это архитектурный пакет и последовательность последующей реализации. Не меняет
backend, не устанавливает сборки и не публикует релиз. 003 — отдельная поставка;
его checkout/процессы не меняются. Первая реализация сохраняет schema3 текущего
ServerDeckNext; импорт сервиса до ServerDeckNext не добавляется.
Приоритет над обязательным locald в прежних документах задаёт
[изменения основы](contracts/embedded-migration.md), без стирания истории.

### Уточнение единого executable и tray — 2026-10-30

Пользователь потребовал один app executable, включая MCP, и полноценный tray.
Отдельного mcp.exe нет. MCP stdio — режим serverdeck.exe; отдельный bridge процесс
того же файла не содержит engine/БД и живёт только ради stdin/stdout клиента ИИ.
Режим не создаёт окно/tray и не выдаёт owner rights по argv. Полномочия — grant
и MCP-only endpoint. [Точный контракт](../021-mcp-control/contracts/embedded-host.md).

FR-SVC-EMB-04 включает tray menu: открыть app, Серверы, Настройки, безопасные
status движка/MCP, явный Выход. FR-SVC-EMB-07 требует MCP в том же executable.

- **AC-SVC-EMB-13**: app package/manifest/client config не требуют mcp.exe/locald.exe;
  dispatch --mcp-stdio не создаёт engine/окно/БД и не может получить owner IPC.
- **AC-SVC-EMB-14**: tray actions открывают существующее окно/разделы без нового host;
  status отражает движок/MCP без secrets; Выход использует единый shutdown;
  tray failure не оставляет приложение скрытым без возврата.

### Полный рефакторинг без остаточного legacy — 2026-10-30

- **FR-SVC-EMB-14**: Никакой обратной совместимости runtime/API/старых форматов;
  engine принимает только целевой storage format, сохраняя его данные и secret/trust
  bindings. Отказ не уничтожает несовместимые файлы.
- **FR-SVC-EMB-15**: В этой же задаче MUST удалить старый runtime/entry/bootstrap/
  compatibility wrappers и неиспользуемые helpers/tests/scripts/workflows. Рабочая
  доменная логика переиспользуется только из нового engine, без старых facades.
- **AC-SVC-EMB-15**: target imports/package manifests/build/CI inputs не содержат
  serverdeck_locald, standalone mcp/locald executable или legacy-mode/upgrade/rollback
  paths. Сохранённые функции/permissions/trust/jobs проверяются в новом engine;
  тесты только удалённых возможностей отсутствуют, Git/task history сохранена.

## UI-компоненты и приёмка (003.4)

Обязательны [библиотека C01–C30](../003-design-system/component-library.md) и [общий контракт применения](../003-design-system/contracts/feature-adoption.md). C ID задаёт семейство готовых элементов, а не новый backend scope. C01 (токены), C02 (действия), C10–C12 (статусы/сообщения/состояния) и C17 (каркас страницы) применяются там, где соответствующая UI-композиция уже требуется этим пакетом.

| Композиция этого пакета | Готовые элементы | Данные, состояния и ограничения |
| --- | --- | --- |
| Готовность, недоступность, recovery | C10, C11, C12, C17, C30 | Этап запуска, причина блокировки и допустимый следующий шаг; local readiness отличается от доступности SSH. |
| Профили, доступ и доверие | C02, C03, C04, C06, C07, C13, C14, C18, C24 | Имя/адрес/порт/пользователь, fingerprint и ревизии; save-only и connect различимы, секрет скрыт, changed key блокирует продолжение. |
| Наблюдения и долговечные задания | C18, C20, C21, C22, C23, C24 | Источник/время/полнота; метрики без фиктивных нулей, unknown job без повторного запуска, отмена не обещает откат. |

- **FR-UI-001-01**: Объявленные композиции MUST использовать перечисленные семейства и их применимые варианты; поля/действия сохраняют предметный смысл таблицы. Общая разметка, токены и поведение не копируются в отдельную реализацию экрана. Отсутствующий вариант сначала расширяется в 003 по общему контракту.
- **FR-UI-001-02**: Данные, callbacks, validation, поддерживаемая порция/сортировка и разрешённые эффекты MUST принадлежать owner этого пакета через действующий контракт 001; компонент не выполняет собственные запросы, retries или выдачу полномочий. Loading/empty/no-results/error/unavailable/stale/partial/unknown применяются по смыслу полученного результата.
- **FR-UI-001-03**: План и задачи MUST содержать mapping «композиция → C ID/вариант → данные/событие owner → критерий проверки». UI-работы ограничены объявленными здесь сценариями; существующая история задач сохраняется, реализация будущих backend возможностей приёмкой 003 не подтверждается.

**Проверяемая приёмка UI:**

- **AC-UI-001-01**: Для каждой строки таблицы сопоставлены её данные/действия и C IDs в плане/задачах; новый экран собирается из готовых элементов. Предметные последствия и ограничения строки видны пользователю, без копирования palette/spacing правил из 003.
- **AC-UI-001-02**: В утверждённом gate данного этапа проверены применимые normal/failure/boundary состояния, точная цель/ревизия и отсутствие запрещённого callback. Утрата readiness/authority не оставляет приватный draft или применимые поздние результаты; неизвестный исход записи не запускает повтор. N/A с причиной фиксируется в mapping.
- **AC-UI-001-03**: При UI-приёмке применяются матрица размеров/тем/масштабов, keyboard/focus/semantics и сохранение всех полей из 003. Существующий unit-only или иной ограниченный gate пакета не расширяется этой поправкой: непроведённые UI/native проверки записываются pending с их будущим gate, без заявления UI-готовности.
