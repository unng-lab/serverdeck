## Ownership and construction

OperationalSessions.withNativePublicationGate in packages/serverdeck_locald/lib/api/operational_sessions.dart is an asynchronous trusted locald composition factory. It requires a real locald-side OperationalPipePeer, validates the generation UUID and derives a gate for that registry generation through the peer's native bundle proof. It returns only after the generation keeper exists; the caller retains its peer. Failed construction does not return a registry or mutate targets, observes any late gate creation and closes the late gate. The factory has the existing5second RPC budget and fixed TIMEOUT/SERVICE_UNAVAILABLE failures; a wrong native self role fails UNAUTHORIZED before creating a gate. No caller-supplied role, transport, lock or authority provider can replace native proof.

The existing ordinary OperationalSessions constructor remains useful for bootstrap components that have no mutation gate. Its beginTargetChange fails NOT_READY before admitting a mutation; it never falls back to an unlocked mutation. Runtime activation must use the native factory before MCP intake. Wiring installed startup and every target/credential/trust mutator remains T109/T110 and original service tasks; this component alone enables no readiness feature.

## Intent, acquisition and mutation

beginTargetChange returns Future<OperationalTargetChangeLease>. It synchronously reserves one workspace open-fence interest before starting native acquisition. At most16 admitted interests include pending acquisition, held mutation ownership, late physical cleanup and releasing leases. Excess fails RESOURCE_LIMIT before more work starts. The trusted owner adapter may pass its remaining RPC Duration; positive deadlines are capped at the original5seconds, and a nonpositive deadline fails TIMEOUT without admitting an interest. There is no wire timeout override. targetChangeInterests and targetChangesBlocked expose observations, never authority or release handles.

Each admitted mutation independently acquires the same generation's real native publication gate. Overlapping changes serialize rather than share native mutex ownership; their synchronous open-fence interests overlap, so protected opens cannot slip between successive mutations. No FIFO order is promised. An earlier publication may finish while intent waits, and no mutation may start before its future returns an opaque lease. After acquisition the registry detaches every existing MCP session, including an unbound/opening one, before returning. Every matching session is detached even if a trusted notification listener throws; that failure prevents mutation admission. Owner sessions remain valid. Final stopping/deadline checks run after listener work and before ownership transfer.

The service retains the lease until actual commit/rollback and all identity/cache/read-interest invalidation settle, then calls close in finally. Each lease close is idempotent and shares the actual native release completion, including fixed SERVICE_UNAVAILABLE on failed cleanup. It removes its open-fence interest only after that physical release settles. Another overlapping intent/lease keeps opens blocked; neither release nor a failed mutation revives old sessions.

An acquisition error completes the caller's logical future with its fixed TIMEOUT/RESOURCE_LIMIT/UNAUTHORIZED/SERVICE_UNAVAILABLE code. Its interest stays charged and opens stay blocked until actual acquisition-worker cleanup has settled. The private registry gate can have other bounded mutation acquisitions: failure cleanup conservatively waits for its currently active acquisitions to settle, retires all MCP sessions and releases any unexpectedly acquired lease before dropping the interest. New requests can fail their own deadlines during this wait; no detached late mutator is started. Native cleanup failure keeps the generation fail-closed through the gate's poison lifecycle. No gate is forcibly unlocked.

## Protected open and shutdown

OperationalSessionRequest._openRemaining checks the fence after checking session liveness. It is used before protected-open work, after every native proof wait, before grant-key read/decryption and immediately before grant binding. A blocked initial open first records its one-attempt state, then fails UNAUTHORIZED using the existing sealed OperationalOpenFailure publication path. It does not read/decrypt the grant key. If an open was already decrypting when a change began, retirement makes its logical result fail; actual key work remains charged to the authority and clears its late key without binding, even if the fence has since been released. An explicit fresh bootstrap is needed after final release.

stop synchronously stops admission and all sessions, starts gate retirement and never releases a mutation-owned lease. close synchronously invokes stop and shares one completion that waits for the real gate cleanup and every admitted mutation interest, including after a listener failure. Active services still own their returned leases and must settle their work/release them; a caller's logical shutdown timeout cannot force their physical completion. The registry owns the generation keeper until this barrier. Failed cleanup is SERVICE_UNAVAILABLE, never successful reuse of a poisoned generation.

## Acceptance and delivery boundary

Actual format2 AOT PE/native bootstrap fixtures use schema2 Isar, CurrentUser DPAPI and the real generation gate. They qualify synchronous intent, old MCP retirement with unchanged grant/usable owner, zero grant-key decryption while blocked, fresh protected open after release, serialized overlapping leases with no open gap, default real5second contention timeout/reuse,16/17 bounded admission, in-flight actual key work retiring without binding, and close retaining held ownership. The blocked-wire case uses the actual OperationalServerChannel/ApiServer and native protected-open client: require exact UNAUTHORIZED, terminal channel completion, zero additional server key decryptions and zero tool-service calls. Test-owned native probes/leases are always closed on failed expectations.

These fixtures do not perform a real target mutation or prove automatic acquisition by every production service. T109 additionally retains queued completed target-dependent stdout and failure/overlap integration; T110 retains every actual target/credential/trust/storage/grant mutator, poison recovery/readiness and installed generation startup. Executor/SSH effects, installed external MCP clients and full product acceptance remain their original gates.
