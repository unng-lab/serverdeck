# Authorable profiles v1

[Spec](../spec.md), [MCP](mcp.md), [executor](executor.md).

## AST and parameter validation

Body is strict JSON `{format:1, environment:"ubuntu24.04-amd64-systemd", parameters:{<name>:<definition>}, steps:[...]}`. Name/description stored in profile metadata, not interpreted by Ansible. Body≤128KiB UTF8, depth≤12, ≤32 parameter names, ≤32 steps, unique step IDs. Identifiers match `[a-z][a-z0-9_]{0,31}`; resource ID matches `[a-z][a-z0-9_.-]{0,63}`. Parameter definition union: `{type:"boolean",default:boolean}`; `{type:"integer",minimum:int,maximum:int,default:int}` with bounds within0..1000000 and default within bounds; `{type:"enum",values:[string1..64chars] unique1..32,default:member}`; `{type:"string",maxLength:1..4096,default:string}`. Definitions have exactly listed fields. No secret-bearing types/defaults. Strings reject NUL/control chars except LF/TAB for public text, and tokens `{{`, `{%`, `{#` everywhere in executable inputs. Cannot reliably detect arbitrary user-pasted secrets: API labels these fields non-secret and owner/AI must use credential custody, not profile bodies. Known credential field names/objects are not part of grammar and rejected.

Step fields exact union below. Every step includes unique id; values are either literal of required type or `{param:<declaredName>}`, exactly one key. Resolve references once in locald and executor, validate same schema and canonical digest; no expression evaluation/interpolation/coercion. Parameters map rejects unknown keys, missing filled only explicit default. Profile revision contains entire validated body including defaults. Effects/post-checks derived by trusted compiler/resource catalog, never declared by AI as free text.

| kind | Exact fields in addition id/kind | Effects and checks |
| --- | --- | --- |
| service | resourceId, state:started/stopped/restarted, enabled?:boolean | Only allowed transitions from root registry. Check canonical ActiveState and UnitFileState; restarted additionally records actual service start timestamp/PID change. No arbitrary unit names or daemon_reload/force/mask. |
| config_file | resourceId, values:object mapping registered field names to typed values | Renderer/schema/path/mode/owner fixed by registry. Compare base file digest and allowed source syntax before atomic replace. Check exact rendered digest/parse plus related service health if registry requires activation. No arbitrary path/raw template/file bytes/validation shell. |
| install_recipe | recipeDigest64hex, version:exact catalog version string | Qualified PostgreSQL/ClickHouse recipe only. Package/dependency pins/hash/repository roots/post-checks from immutable recipe. Fresh only; detects preexisting package/config/data and blocks. No free package name/repo/URL/options. |

Profile may reorder/add/remove supported steps and declare/rebind parameters. Same resource may occur at most once per profile; install recipe owns its service/config resources and conflicts with explicit duplicate steps on them. Cross-step effects flattened before plan so dependencies/NetBird checked over whole profile. New step type/schema is incompatible format2 and requires explicit future design; never interpret unknown as generic Ansible task.

## Administrator resource registry v1

Root-owned `/etc/serverdeck-executor/resources.json`, protocol format1, schema-validated immutable per-plan digest, no user-writable symlink parents. Content part of executor package plus explicit administrator-created qualified recipe descriptors; MCP cannot write registry. Entries contain id,kind,canonical target,allowed fields/transitions,compiler/renderer version,pre/post-check IDs,declared effects and prerequisite evidence. Registry is not a general plugin loader. Only packaged renderer/check IDs are accepted; adding ID cannot introduce executable strings. Unknown IDs/versions→UNSUPPORTED. Any change requires new plan/review and invalidates exact resourceRegistryDigest.

Initial resources:

- `system.motd`: config_file, canonical regular `/etc/motd`, root:root0644; only `text` string≤4096 characters with template tokens rejected. Renderer UTF8 text with one trailing LF. No activation; post-check exact digest. Symlink/directory or existing file>64KiB blocks, no replacement of target through link.
- `postgresql.service`: canonical `postgresql@16-main.service`, allowed started/stopped/restarted and enabled true/false only after recipe-qualified installation or explicit owner qualification of existing supported unit. Verify unit file, drop-in and dependency manifest digest against recipe/qualified registry; unqualified override blocks. Check active and local peer `SELECT 1` when started/restarted; stop requires inactive. Never accept netbird/alias/dependency effects.
- `clickhouse.service`: canonical `clickhouse-server.service`; same restrictions, versioned recipe evidence and local read-only SQL probe. Dependency/unit override changes invalidate plan.
- `postgresql.settings`: PostgreSQL16 managed fragment in registered `/etc/postgresql/16/main/conf.d/serverdeck.conf`; fields `max_connections` integer10..1000, `shared_buffers_mb` integer16..16384. Renderer fixed keys only, no includes/hooks/listen settings. Both required fields after param resolution. Registry preflight checks parent config includes fragment once and resource budget permits requested shared buffers. Activation is separate compiler-derived service restart within same job/approval, safe step boundary. Preflight/save-check use trusted PostgreSQL parser in no-start mode; post-check runtime settings/SQL. Cannot author executable config/paths.
- `clickhouse.settings`: registered `/etc/clickhouse-server/config.d/serverdeck.xml`; fields `max_connections` integer10..10000 and `max_server_memory_usage_mb` integer128..1048576 and≤80percent actual MemTotalMiB. Fixed XML renderer, no include_from/dictionaries/functions/listen changes. Both required. Activation/check as above with fixed SQL settings probe and server health.

Config resources only available after qualified ownership/expected baseline, no automatic adoption/repair. Baseline digest includes parent/unit effective dependency inputs, not just managed fragment. Service-only profiles require exact same qualified resource evidence. `system.motd` supports first generic file configuration independent of DB installation. Future resource types must add schemas, tests and reviewed package resources; arbitrary local files/units not promised.

## Qualified installation recipes

Recipe immutable descriptor fields: format1,id(postgresql16|clickhouse),version,revision,digest,environment,packagePins{name,architecture,version,sha256}[],dependencyTransactionDigest,repositoryFingerprints[],aptIndexDigests[],expectedAbsentPaths[],ownedResources[],prechecks[],postchecks[],licenseNotices. Top-level version is the exact selected catalog product version, independent of individual package versions; it must equal the source install_recipe.version and derived effect.version. Exact structural form/hash/bounds in the [plan contract](plans.md). Exact versions are required selected catalog inputs, no default latest/coercion. Catalog derives only from administrator-prepared signed apt metadata and registered supported program recipe major. Resolve all package/dependency pins before approving plan; materialize descriptor with digest and show it. New candidate/version has new descriptor digest and requires own qualification; never label merely available candidate qualified.

First PostgreSQL recipe requires `postgresql-16`, `postgresql-client-16` and exact dependency closure from prepared Ubuntu24.04 signed sources. ClickHouse recipe requires `clickhouse-server`, `clickhouse-client`, `clickhouse-common-static` at same exact available vendor version with amd64/SSE4.2 and prepared signed vendor source. No repository addition/cache refresh in recipe. Catalog lists unqualified available candidates as unavailable with reason; owner/developer qualification on disposable VM produces supported descriptor included in release bundle. Package version and dependency closure are deployment metadata, not developer-chosen automatic upgrades. Release cannot claim install support until at least one real qualified descriptor for each program exists and is tested. Those descriptors/hash-locks are explicit T028 deliverables.

Before effect compare full installed package snapshot, apt index digests, no dpkg lock/incomplete state, simulated transaction equals frozen install-only additions, no installed package alteration (including dependencies), no held/NetBird package, known data/config absent. Any delta→PLAN_STALE. Download only package hashes bound to signed prepared indexes, no latest fallback; unavailable file→failed no effect. Never hold an outer dpkg/frontend lock while launching Ansible apt. The apt child owns native locking; packaged Pre-Install-Pkgs gate revalidates baseline/transaction under apt frontend lock before dpkg; any mismatch aborts. Contention returns HOST_BUSY within1s; no lock disabling/inheritance workaround. Package maintainer scripts are trusted signed package code within qualified recipe, not static sandbox proof; qualification and dependency/effect verification mandatory.

## Compiler

No caller YAML is parsed. Use JSON serialization to generate Ansible playbook; values inserted as literal non-templatable typed values after rejection. One typed effect per invocation, hosts localhost only, connection ansible.builtin.local, gather_facts false, become false, explicit interpreter /usr/bin/python3, no handlers/async/retries/loops/roles/imports/custom plugins. Compile service operation/enabled changes and config activation as separate individually authorized effects. Ansible exit + trusted post-check determines outcome, no_changed output not sufficient. Fixed apt options and resource checks in executor contract. Every generated artifact contains only declared non-secret fields, root0700 work directory, no private SSH/SQL passwords.

Package membership/installed-version preservation excludes only declared qualified maintainer-script/trigger/cache effects needed by approved additions; no unrelated installed package upgrade/downgrade/removal/config changes or NetBird effects. These trusted package-code effects must be enumerated and tested in recipe qualification. External root bypassing locks is outside guarantee.

Revision permission identity is `(profileId,revision,bodyDigest)`, never digest alone. Equal canonical bodies deliberately have equal digests for comparison but do not share execution permissions. Authoring a new revision/profile, including a metadata-only revision, requires a new matching tuple in owner delegation or one-plan approval.
