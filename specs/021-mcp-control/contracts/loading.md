## Responsibility and boundary

### Owned operational open increment (T075)

Add internal `StateStore.openOperational` for an existing, fully published schema2 workspace. It shares StateStore's synchronous process reservation with legacy opens and refuses an existing Workspace/StateStore/migration reservation or native `workspace` instance before opening. It receives the existing caller-owned held lease and live receipt-key material, plus localAppData/appRoot/custody. The caller retains key and lease ownership. No directory argument, initialization, migration, repair or creation is available. The fixed protected active path is `ServerDeckNext/v1/workspaces/default`; validate each existing ancestor's owner-only ACL and no-reparse custody. Require absence of `default.creating` and `default.upgrading-1-2` (even empty); migration recovery/cleanup belongs to WorkspaceMigration before this call.

Verify the existing native runtime bundle before native loading, then strict schema2/format2 manifest identity against actual live receipt key/current SID, exact persisted receipt-key wrapper, protected DB and existing lock file, and full read-only native registry schema2 before `Isar.open(automationWorkspaceSchemas)`. Schema1 must fail INCOMPATIBLE without a writable open or file changes. Corrupt custody/identity fails STORAGE_BLOCKED. Recheck owner/lease/liveness across asynchronous boundaries and immediately before opening; no fake validation callback. Native options remain name workspace, maxSizeMiB64, relaxedDurability:false, inspector:false. After opening invoke the complete T074 composition and return the owned store only on success. `operational` exposes its immutable snapshot under the normal readiness guard; `state` returns the foundation compatibility state. This low-level opener is not called by existing production bootstrap: verified1.1 image/role/bundle activation remains T006/T008, and the current native-runtime verifier alone does not establish that activation.

Until common schema2 mutations are implemented in T070/T007, legacy `commit(WorkspaceState)` on an operational store must fail STORAGE_BLOCKED before enqueue/native writes, without poisoning valid reads. Otherwise its schema1 metadata writer would corrupt the physical schema2 marker. No arbitrary raw Isar handle is exported by the store. Successful close clears its reservation only after confirmed native close, never closes the caller's key/lease, and closes read access. Any failed open after an attempted native open, including pointer reconciliation failure, attempts confirmed native close. If close is unconfirmed, retain reservation so Workspace.hasOpenReservation prevents caller lease release until process exit; if native close succeeds release the store reservation and propagate the safe failure. Pre-open refusal releases only its own reservation, preserves files, and does not close an existing foreign instance. The next opener revalidates from committed DB; it never rolls a pointer back.

Acceptance requires actual temporary protected schema2 Isar/DPAPI and synthetic held lease, complete nonempty graph preserved through owned open/close/reopen; stale/missing/revoked pointers; shared reservation refusal for legacy open/migration and a second operational open; exact legacy-commit refusal with unchanged DB; caller key/lease still live after close; malformed/foreign manifest, wrapper mismatch, unsafe ancestors/DB/lock, pending creation/migration stage, schema1 read-only refusal, logical/credential prepublication refusal, and injected unconfirmed native close retaining reservation. Bundle fixtures verify actual hashes/native loading but are not product image/1.1/client/systemd Docker/VM acceptance. T071 remains open until its production integration and all startup gates are met.

### Native composition increment (T074)

Implement `OperationalSnapshot` and `readOperationalSnapshot` in the shared `storage/foundation_snapshot.dart` library, reusing a private full foundation row reader. The existing public `readFoundationSnapshot(expectedSchema:2)` keeps its mandatory empty-automation check unchanged before delegating to that reader. The new composition calls the private reader with physical schema2, then reads all ten real Isar collections with count/limit gates and the shared graph loader; no boolean/callback can waive graph or credential validation. Foundation's returned compatibility model remains schema1, while the actual metadata/registry stays2; no storage writes are performed by this read.

Arguments are an already-open Isar instance, live receipt key/KeyCustody, localAppData and the caller's held MutexLease. Validate current owner/key identity, lease, instance name `workspace` and normalized instance directory equal the fixed credential workspace directory. Opening/native registry preflight, validated schema2 manifest/key file and protected DB/lock custody remain mandatory caller gates in T071; the composition neither opens/closes Isar nor acquires/releases the caller's lease. Product activation still requires the compatible operational store and verified1.1 bundle. A standalone composition cannot claim those gates. The caller serializes it before accepting writes; count→read is therefore stable. Bound each native query at the collection quota+1 rather than eagerly materializing an unlimited table; graph quotas/64MiB still apply.

Order is mandatory: (1) complete foundation validation including all server DPAPI; (2) snapshot/validate all ten automation collections and references; (3) bounded credential inventory check, then open/close every current grant blob against its exact workspace/grant/secretRef/current owner/issuedAt, including revoked grants; (4) read/validate every existing current lookup before any pointer write, accepting missing or valid stale same-workspace/grant/owner and refusing malformed/foreign/unsafe lookups; (5) recheck live receipt key and lease, then publish/recheck each current DB-derived lookup with revoked flag from the row; (6) final key/lease check and return the complete immutable snapshot. A failure returns no snapshot or service readiness. Never keep a key handle open between grants, and close it if a later liveness check fails. Postpublication IO failure may leave some correctly DB-derived lookups, so T070/T071 still retain ownership and enter blocked recovery; no rollback to an old credential.

The shared file layer adds read-only `validateInventory()` and nullable `readLookupForRecovery(grantId)` to support these phases. They create nothing, use the same bounded/strict custody checks and map persistent inventory/lookup failures to STORAGE_BLOCKED (unsupported formats remain INCOMPATIBLE). Recovery lookup exposes only immutable internal binding/revoked metadata, never raw key bytes or public MCP output. Missing current lookup is nullable only after validating its existing workspace/root/grant directories; a missing referenced credential hierarchy is corrupt. Public bridge read continues its existing refusal/missing behavior.

T074 acceptance uses real temporary protected schema2 Isar, CurrentUser DPAPI and an owned synthetic lease, with nonempty representatives of every collection, actual native IDs and reopen preservation. Require the old migration reader to reject the same nonempty DB. Include wrong key/owner/directory/lease/schema, malformed foundation/graph/native keys, second grant missing/corrupt blob and second malformed/foreign lookup; all these prepublication failures leave the first grant's lookup absent/unchanged. Test missing/stale/revoked lookup reconciliation and no revival, history retained after reopen, inventory corruption with no grants, and immutable returned maps. These tests prove the composition only; actual store opening/reservation, mutation CAS, crash/receipt/publication and verified bundle/client/systemd Docker/VM remain T070/T071 and original tasks.

T007 adds a locald `automation/snapshot.dart` validator for the complete retained logical automation graph. It receives workspace identity, validated foundation state and all ten automation collection rows under the sole-writer reservation. It returns immutable typed maps only after every row and reference passes; no partially usable result, pruning, row repair or skipping unknown collections. It never turns historical data into current permission. T004 operational startup composes this with the existing full foundation/DPAPI validation, native registry/schema checks and T005 client credential validation. Neither the pure graph validator nor a schema2 marker alone permits normal startup. Migration's existing empty-automation view remains restricted to migration verification.

Collection input rows are `{nativeId,entityId,payload}`; nativeId positive int64, unique within collection, entityId exactly the repository key below, payload strict UTF8 JSON with existing duplicate/depth/size checks. Parse every collection, including empty ones. No caller-selected collection/schema name. Ordinary UUID keys are exact entity IDs; revision key is `profileId:revision` (canonical positive decimal); event key `jobId:sequence` (canonical positive decimal). Unknown/missing collection or duplicate native/key/logical identity fails STORAGE_BLOCKED. Foundation loading remains its existing shared validator; the graph never substitutes a weaker foundation model. In-memory test inputs must be snapshotted before asynchronous digest validation.

## Quotas and historical references

Apply quotas before materializing unbounded inputs: grants32, delegations1000, profile IDs250, revisions20 per profile/5000 total, plans1000, approvals100, receipts10000, terminal jobs1000. Delegation count is a fixed workspace metadata budget, including revoked/pinned rows; no silent eviction, admission at quota returns RESOURCE_LIMIT. Active/unknown jobs are never evicted: one occupied job per physical host and per server profile, with at most250 active/unknown entries because target mutation/delete cannot erase occupied identity. Events at most10000 per retained job and10000 total workspace audit rows; each at most4KiB. Desired rows are limited to the five supported resources per known server identity (including retained deleted identities), not an unrelated arbitrary resource namespace. Total automation payload UTF8 budget64MiB is checked incrementally before async DTO parsing; this is a metadata memory/admission bound in addition to the existing physical64MiB store. Implementations may stream native rows rather than eagerly copying the whole native file.

Every non-null grant origin/author/object reference resolves an actual retained grant in the same workspace, including expired/revoked grants. Current grant scope, target list, expiry or credential revision may have changed since creation of a historical object; do not reject history by re-running current admission. Delegations retain their immutable target/tuple/predicate/expiry payload on revoke and only change revision/revokedAt. Historical authority revisions may be less than the current delegation revision, never greater. No delegation replacement/edit endpoint exists. Actual new admission separately validates current grant/delegation and target policy.

Server identity reference resolves either an existing foundation profile or an existing foundation `profiles.delete` receipt whose deleted result and entityId/profileId agree. Delete does not erase referenced automation history. Absence of both is an unresolved reference. Live operations require an existing current profile, current host/trust/counters and authority. T007 integration preserves these deletion receipts; existing permanent foundation receipts already do so. Foundation profile creation rejects UUID reuse when that ID has a retained deletion receipt, preventing old explicit server grants from attaching to a recreated target. This extends the existing future-coordinator mutation guards without changing foundation schema or deleting its receipts. Delete/update with active or unknown admitted jobs respects host writer/unknown protection, never erases recovery identity or unlocks a host; target connection/access/trust changes are refused while occupied, while public name/tag changes may proceed and conservatively stale outstanding plans.

## Validation order and immutable links

### Shared foundation transaction in an operational workspace

Keep legacy `StateStore.commit` refusing schema2 unchanged. Add explicit trusted internal `commitOperationalFoundation(next)` and `WorkspaceRecords.fromOperationalState`: physical metadata stays schema2 while the foundation compatibility model stays schema1. The new path joins StateStore's existing durable queue; foundation and grant mutation interests share a total32 cap including running work. The upstream owner service must acquire the actual publication/target lease before this queue; this primitive is not a session authorization or a product activation gate. The shared owner service/coordinator integration remains T109/T110, and ordinary legacy coordinator calls must not silently switch schemas.

Under that queue, require exactly the next foundation store revision, unchanged workspace/key/owner, one new durable foundation receipt and byte-equivalent canonical retained receipts. A stale prepared foundation revision returns REVISION_CONFLICT without changing or blocking the ready store. Preserve retained foundation native IDs; never write automation collections. Refuse new profile UUIDs with a retained deletion receipt using ALREADY_EXISTS. For every nonterminal job (including unknown/reconciling), resolve its exact plan server and refuse deletion or changes to its connection, credentials, trust or other identity using HOST_BUSY; only name/tags/revision/updatedAt may change. Compare referenced credential contents as well as counters. These refusals precede any write and keep the previous state usable.

Before writing, validate all new foundation credentials and the entire retained automation graph against the candidate foundation. Commit foundation rows and the new receipt atomically using physical schema2 metadata. Before returning success, reread the full operational snapshot with the existing native/DPAPI/lookup validation, verify the exact expected foundation and every retained automation native ID/entity ID/payload, then publish the new in-memory snapshots together. A postcommit readback failure blocks storage and returns no successful ACK; permanent receipt recovery/replay remains the coordinator's responsibility. For native capacity failure, wait for the actual transaction abort, reread/verify the unchanged old foundation and automation graph before RESOURCE_LIMIT; uncertain abort/readback blocks storage. Binding cleanup prerequisites and actual commit-time failure acceptance are fixed in [native-transactions](native-transactions.md).

Actual protected schema2/Isar/DPAPI acceptance covers settings writes/reopen, deletion preserving nonempty history and blocking UUID reuse, active and unknown job connection/delete refusal with allowed public metadata changes,32 pending foundation admission and stale-candidate rejection, and real64MiB native capacity abort/readback/retry. Tests must preserve the old legacy-commit refusal and physical marker2.

1. Parse all grants/profiles/delegations/revisions using strict shared DTOs and validate workspace/key/native identity. Each grant has a distinct secretRef; actual protected secret binding/availability is additionally validated by T005 custody, never by a fake envelope or JSON parser. A profile has exactly revisions1..headRevision, no gaps or revisions beyond head, at most20; each parent is the preceding retained revision, timestamps nondecreasing. All revision authors resolve retained grants. Archived profile metadata remains loadable and does not invalidate old plans/jobs.
2. Each delegation resolves its grant and every exact profile tuple. Compare full profileId/revision/bodyDigest. Its server identities resolve as above. At load do not call issuance-time `validateForGrant` against a replaced/revoked current grant; that helper belongs to issuance. Predicate structure is checked on load; actual selected revision parameter compatibility is checked when issuing/delegating/applying, not inferred from a mutable head.
3. Load each plan with the actual resolved immutable AutomationRevisionRecord. Shared Plan parser recomputes complete parameter/body/capsule/program hashes and coverage. Resolve original grant and server identity. Foundation current counters/host and time may differ: that makes a plan stale/expired for admission, not corrupt history.
4. Each approval resolves its plan and validates full digest/origin/workspace/time window. Each job resolves its runnable plan, original grant and authority; exact plan digest/profile tuple/origin must match. job.createdAt is within plan's admission lifetime; an admitted job may finish after expiry. Exactly one job per plan and unique hostAttemptId. Each retained outcome check summary references an actual plan.checks ID with matching effectId as its stepId; summary is bounded and need not contain all full executor evidence. A delegation authority resolves the same grant, selected exact tuple/server and predicates matching complete plan parameters, with authorityRef.revision<=retained delegation.revision. An approval authority resolves a consumed approval with jobId==job.id and matching plan/origin; authority revision is1. Conversely every consumed approval references that exact job/authority. Historical expiry/revoke does not release writers or authorize continuation.
5. Each desired row resolves a succeeded job and its plan, matching server/body/input digest and a compiled owned resource. Derive owned resources from ordinary effect.resourceId plus each selected recipe descriptor's ownedResources. Exactly one desired row per(serverId,resourceId), immutable row ID across future updates. Actual executor evidence for succeeded was required at the transaction that committed it; startup structural links are not renewed attestation.
6. Events resolve their job, exact workspace and sequence<job.nextSequence. Sort by sequence per job for nondecreasing timestamp checks. Referenced step IDs are actual compiled effect IDs in the immutable plan. Gaps are permitted because bounded progress can be dropped; row duplication, dangling step and timestamps before job.createdAt or after job.updatedAt fail. No requirement that an old state event equal current job.state. Current status/outcome is durable independently of progress retention.
7. Receipts resolve origin/object grant and every closed result identity using the records contract. Grant/delegation/profile mutable current revision may be newer than acknowledged revision, never older. profile.create/update resolves the exact retained revision/digest; profile.archive requires current archived metadata and retained head>=acknowledged revision. Plan receipt resolves exact digest/origin; approval/job receipts use the shared identity checks, preserving approved->consumed/expired acknowledgement. Where the referenced immutable creation timestamp exists (grant, revision, plan, approval, job), receipt.createdAt cannot precede it; a later receipt need not match its current update time. delegation.create receipt supplies issuance time for the5min..24h expiry interval and revokedAt>=issuance check; current replaced grant scope/expiry is not historical issuance evidence. Do not reconstruct a receipt response from mutable state. Mutation request digest is checked for syntax at load; only the trusted coordinator, which has the original validated operation/input, can compute it at admission.

Creation coverage is mandatory because these rows are created by atomic mutations with permanent receipts: one grant.create per grant, one delegation.create per delegation, one profile.create/update acknowledgement for every retained immutable profile revision, one plan.create per plan, one approval.request per approval and one job.apply per job. grant.create is owner initiated; revision author and plan.originGrantId equal their creation receipt initiator. Approval/job creation instead checks objectGrantId==approval/job.grantId; initiator may be that same grant or authenticated owner null, as allowed by the records contract. An owner creates a new plan only with owner origin, but may request approval/apply for an existing grant-origin plan while preserving its original grant and all current checks. Never require owner initiator null to equal object grant G. Creation timestamps equal object's original createdAt where present. Grant.createdAt is immutable original creation; its distinct issuedAt anchors the current credential validity interval. Every currently archived profile has a profile.archive receipt; revoked grant/delegation has its revoke receipt. System-derived desired/events/outcomes are covered by their parent admitted job rather than fabricated user mutation receipts. This does not require every progress change to consume a receipt. Missing creation/revoke/archive evidence fails whole graph loading; no synthesizing acknowledgement on startup.

Grant replacement retains id/workspace/createdAt, increments revision and rotates secretRef, sets issuedAt to the explicit owner replacement time and expiresAt to issuedAt plus the validated5min..30day lifetime (default8h). It may explicitly renew an expired nonrevoked grant even after30days from original creation; revoked grants cannot be renewed and require a new ID. Parsing/status reads never renew. Revoke increments revision and records revokedAt while preserving issuedAt/expiry/secretRef and other metadata. For every grant revision1..current there is one canonical create/replace/revoke receipt. Revision1 is create at original createdAt; subsequent revisions are exactly successive replace operations followed by at most one terminal revoke, with nondecreasing timestamps (same millisecond permitted), no new create and no later revision after revoke. For every grant, including revoked, current issuedAt equals the timestamp of its last create/replace receipt; if there was no replacement it still equals original createdAt. Revoke receipt time equals revokedAt and must be at or after that last issuance. Revoke is terminal. These receipts preserve revision/time provenance without storing old secrets or reconstructing old policy from the current grant. T005 mutation helpers enforce transitions; T007 loader checks full receipt history/order and current timestamp anchors. Tests cover renewal at day29/day31 and rejection of revoked renewal, missing/extra issuance field, future issuance, lifetime boundaries and original creation receipt preservation. Otherwise-valid create->revoke and create->replace->revoke graphs with shifted issuedAt must both fail, even if their recomputed expiry interval still satisfies the DTO range.

Owner decision coverage is additionally mandatory: approved/consumed approval requires an owner approval.decide acknowledgement with decision approved; denied requires denied; pending permits no decision receipt. Expired may have come from pending (no decision) or approved (approved evidence); denied evidence cannot describe expired. Every decision acknowledgement matches exact approval/plan/digest/object grant and has owner initiator null; contradictory decisions fail. At least one canonical decision receipt timestamp is within [approval.createdAt,approval.expiresAt), and for consumed no later than its job.createdAt. Removing all decision evidence from an otherwise linked approved/consumed/denied graph fails STORAGE_BLOCKED. This is required permanent evidence of an existing explicit owner mutation, not a receipt for automatic progress/expiry.

Successful repeated approval.decide/job.apply calls with a different requestId may return the original decision/job without another state transition or server effect, while committing an additional stable acknowledgement receipt for the new request identity (subject to quota/current authorization). Their canonical request digest still prevents changed-input reuse. Repetition never extends timestamps or acquires new authority; contradictory decisions cannot replace the original decision. The original creation receipt is identified by Plan.requestId/Job.requestId where present and exact original createdAt; approval/grant/delegation creation is identified by exact createdAt/issuance and identity. Later consistent acknowledgement aliases are not creation/decision-time evidence and may be after lifetime expiry. For decision time use the earliest consistent approval.decide receipt, which must satisfy the preceding canonical decision window/order. Every alias must match the same retained object/result and be no earlier than canonical creation/decision. Loader does not reject a valid later acknowledgement as a second creation. Tests include repeated IDs after consumption/expiry and receipt deletion, missing canonical requestId, contradictory result and late-only evidence.

Graph checks reject a dangling reference even if a self-consistent payload digest was recomputed. No graph helper can make an untrusted fabricated row authoritative: OS custody, actual Isar commit integrity, current role/session authorization, root evidence and compiler/catalog membership remain required at their boundaries.

Historical admission additionally lies within the original authority interval, not merely the plan lifetime: approval.createdAt<=job.createdAt<approval.expiresAt; delegation.create receipt time<=job.createdAt<delegation.expiresAt. A retained delegation.revokedAt cannot be before admission (same millisecond is permitted because timestamps do not encode transaction ordering). This checks immutable historical facts, without rerunning today's grant expiry/scope or extending authority after restart. A completed job may outlive either interval; updatedAt is not its admission time. Tests independently keep the plan lifetime valid while crossing the shorter approval/delegation boundary.

The retained delegation revision bound above is necessary but not sufficient: authorityRef.revision must identify its issued create revision1, never revoke-only revision2. A later retained revision2/revokedAt preserves valid revision1 admission history but did not itself issue authority; delegation replacement/edit is unsupported. For both approval and delegation jobs, including owner-initiated apply for object grant G, terminal grant.revokedAt must not precede job.createdAt. Equality of milliseconds is permitted; job completion may be later. This checks the immutable terminal-revoke fact and does not reconstruct past replaced grant scopes/expiry. Tests require rejection of a fully linked revision2 authority and admission strictly after grant revoke, while accepting revision1 before later delegation revoke and completed jobs admitted before/same-millisecond grant revoke.

## Integration and acceptance

Every non-null initiating grant receipt also obeys its immutable terminal revoke bound: receipt.createdAt<=grant.revokedAt when revokedAt is present (equal millisecond allowed). This includes profile author mutations and prevents a valid-looking profile/revision/receipt graph from claiming a grant authored after its permanent revoke. It does not deny later owner-initiated history/cancel/reconcile acknowledgements merely because objectGrantId G was revoked; owner initiator null and original object G remain distinct. Current grant scopes/expiry after replacement are not substituted for these historical facts.

Canonical owner-issued delegation creation and initial approval request still require a then-current G: delegation.create receipt time<=G.revokedAt and approval.createdAt<=G.revokedAt, where G has a terminal revoke. These initial issuance checks apply even with owner initiator null and no jobs. Do not blanket-reject later owner-origin revoke/cancel/reconcile or stable acknowledgement aliases by their objectGrantId; only canonical issuance/admission and actual non-null grant initiators use these bounds. Tests isolate zero-job delegation issuance and pending approval request, each before/at/after G's terminal revoke.

The earliest canonical positive owner approval.decide also requires createdAt<=G.revokedAt when G has terminally revoked, even with no admitted job. Apply this to approved, consumed and expired-after-approved history; same millisecond is permitted. Later consistent acknowledgement aliases do not replace this original consent time and may follow revoke/expiry. Owner denial/cleanup does not issue authority and is not rejected by this positive-consent bound. Tests independently cover before/equal/after canonical approved consent, expired-after-approved and permitted later aliases/denial.

Known latest issuance expiry is also an immutable historical bound: for the canonical delegation issuance, approval request, positive consent, job admission and each non-null initiating grant receipt above, if operationTime>=G.issuedAt require operationTime<G.expiresAt. Equality at expiry rejects. If operationTime<G.issuedAt it may belong to a prior replaced credential: do not add today's lower issuance bound or reconstruct prior scope/expiry from current policy. Later owner cleanup/consistent acknowledgement aliases are not blanket checked by objectGrantId. Tests include never-replaced expired G, exact admission expiry and admission1ms before expiry, preserving older history across later replacement.

The existing delegation.expiresAt<=grant expiry rule is verified on load when that grant issuance is provably applicable at delegation.create: latest grant.issuedAt is strictly before delegation issuance, or equal and the complete grant history has no replacement (create-only revision1 or create/revoke revision2). When a replacement and delegation issuance share a millisecond, their order is unknown; do not use a possibly later shortened lifetime to corrupt earlier delegation history. If current grant.issuedAt is later than delegation issuance, old grant expiry is unknown and current expiry cannot replace it. Actual issuance transaction always validates against its actual current grant regardless timestamp ambiguity. Tests include un-replaced grant overrun and valid old delegations before/same-ms later shortened replacement.

When this same latest issuance epoch is provably applicable, its scope/explicit targets are also known historical facts. Canonical delegation issuance needs apply and its server subset; approval request/positive consent/job admission need apply on their plan server (read/plan dependencies follow strict GrantScopePolicy). Grant-initiated profile mutations need author, plan.create needs plan on server, approval.request/job.apply/job.cancel need apply on server, job.reconcile needs read on server. Do not use these latest scope/target values for earlier or same-ms ambiguous replaced epochs; no old policy is reconstructed and later owner cleanup/ack aliases are not blanket objectGrantId checked. Tests reject a never-replaced read-only grant's plan/author mutations while preserving earlier authorized history after later scope replacement.

Preserve expired/revoked/replaced-grant and completed-after-plan-expiry history. Include consumed approval/delegated job, terminal desired state, event ordering/gaps and later-mutation receipt replay identities. Test exact server deletion receipt resolution and UUID reuse refusal in the actual shared foundation mutation transaction, not just a set-membership helper.
