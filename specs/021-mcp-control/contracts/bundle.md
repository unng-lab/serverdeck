## Actual bundle and peer verification

Verify Windows amd64/current native prerequisites, normalized local absolute root and no reparse paths, bounded16KiB+1 strict duplicate-safe manifest bytes, exact root binding, and actual SHA256 of all four files using existing bounded-buffer native hash. Retain immutable metadata and digest of the exact manifest bytes. Malformed/unsupported/root/hash mismatch is INCOMPATIBLE; IO/path/native prerequisites failure is PREREQUISITE_UNAVAILABLE, with no provider messages/paths in public errors. No file creation or repair.

A verified bundle alone may construct a private-constructor retained peer proof by checking a caller-owned RetainedProcessIdentity and expectedOwnerSid equal currentUserSid. Fixed exact root-relative paths determine role: serverdeck.exe=owner, mcp.exe=mcp, locald.exe=locald. A same hash or filename outside the verified root does not qualify. DLLs and unknown images have no role. No JSON role, requestedCapabilities or process-supplied PID is input to role selection; actual named-pipe PID acquisition remains the transport caller's mandatory T006 gate. Before issuing proof and on every proof revalidate/role access, require current owner, same unchanged manifest bytes/safe paths, live retained process SID/path/hash/creation identity through existing native verifyProcessImage and repeated native checks. A closed retained handle, exited peer, changed manifest/hash/path or foreign SID returns fixed UNAUTHORIZED. Caller owns/closes identity on the same pipe worker; proof does not transfer handle ownership or resurrect a closed handle. Proof role is immutable and has no public constructor.

T006 must accept only owner/mcp roles on the server and only locald on UI/bridge client, revalidate before/after handshake awaits and before session grant, and bind immutable role to session. The locald proof is never a client owner role. Bootstrap possession alone does not expand mcp authority; live grants/current policy still required for MCP invocation. These are mandatory adapter gates, not established by an isolated image verifier.

## Native pipe worker integration

T083 adds explicit PipeWorker.createOperationalServer/openOperationalClient factories with fixed name, expected owner SID, appRoot and optional exact testOnly selection captured at creation; no per-request root/role/PID/hash override. Inside the worker, verify the format2 bundle and retained self image before creating/opening a native pipe: server must be locald, client must be owner or mcp. Retain/close self identity in that worker. Legacy factories remain legacy and cannot construct an operational peer handle. Safe startup INCOMPATIBLE/PREREQUISITE_UNAVAILABLE/UNAUTHORIZED are returned through the private worker channel; do not lose them as an apparent successful startup or fallback. Native startup failure must close its own worker resources.

Operational worker verifyOperationalPeer() obtains the peer solely from NativePipe.peerIdentity (actual kernel-derived PID/retained handle). Server accepts owner/mcp and rejects locald as client; client accepts only locald. Both self and peer proof must revalidate for each operational verification and each read/write/drain before and after native await. Failure latches the current connection unavailable until a successful native disconnect/drain followed by legal reaccept (or client close), never silently relabels an existing session after restoring files. A legacy verifyPeer(sid,image,hash) call cannot bypass operational verification. Raw operational worker read/write/drain are refused; only the private-constructor OperationalPipePeer returned by successful verification can perform them. Its immutable role/buildId are verified worker results, never JSON caller claims. API1.1 session adapters must hold this peer per accepted connection and call its revalidate around handshake awaits; creation of this handle alone is still not session/grant authentication.

The worker owns a monotonically increasing positive int64 connection epoch: increment/reset proof before accept, disconnect and close; startup client starts at1. Pending verification/IO snapshots the expected epoch and rejects a changed epoch after await before returning data/result. An OperationalPipePeer embeds that epoch and cannot read/write/revalidate/drain a reused slot, even when the next peer has the same role or same image. Failed verification invalidates the binding, but only native disconnect drains/closes NativePipe-owned peer identity; do not directly close it early. Epoch exhaustion permanently refuses further slot use; no wrap/reuse. Preserve existing three pending owner calls, native cancellation/drain and8slot pool budgets; T006 later selects these operational slots only with the full1.1 bootstrap. No handles cross isolates.

T083 tests use actual compiled own named-pipe server/client PE processes and retained kernel peer identity, not callbacks. Cover locald server with owner then mcp client on reused slot, immutable role/buildId, raw/legacy bypass refusal, old epoch revalidation/read/write/drain refusal while a new peer is connected, native echo through the verified peer, client proof of locald, invalid self-role startup, identical unknown/outside image, changed manifest after connection and failed-binding latch, startup bundle failure and deterministic cancellation/disconnect/close. Isolate namespace uses owned synthetic pipe names; do not disturb the current user's canonical live service. Existing legacy/native teardown suites must remain green.

### Operational slot lifecycle

The operational server begins idle; accept is legal only in idle. Check this state before changing epoch, proof or failure latch. Set listening before starting native accept; success becomes connected, failure becomes needsDisconnect. Both a successful and an unsuccessful accept attempt require a confirmed native disconnect/drain before another accept. Repeated/concurrent accept while listening/connected/needsDisconnect/disconnecting/failedDisconnect refuses SERVICE_UNAVAILABLE without changing latch/binding/epoch. A verification or actual operational IO failure latches the connected binding; restoring files and calling accept cannot recover that same physical connection. Caller quota/argument/raw/stale-epoch refusals do not poison a different healthy connection.

Disconnect may cancel listening or clear connected/needsDisconnect: advance epoch and make IO unavailable before native cancellation, then become idle only after NativePipe.disconnect confirms completion and closes its own retained peer. Concurrent/repeated owner disconnect shares the existing operation. If native disconnect fails, remain failedDisconnect with no new accept/verification/IO until close; never reset a failed drain into an available slot. Closing is terminal and invalidates epoch before cancellation. Client workers have no accept/disconnect reuse and close after a failed connection. After-await handlers update slot state only if their captured epoch is still current, so an old accept completion cannot reopen a newer/disconnecting slot. Actual tests must restore a mutated manifest and attempt accept without disconnect, proving the existing latch persists, then demonstrate legal disconnect/new physical client/reaccept.
