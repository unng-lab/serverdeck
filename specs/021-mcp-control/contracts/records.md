# Durable automation records v1

[Model](../data-model.md), [MCP](mcp.md), [executor](executor.md), [tasks](../tasks.md).

This fixes the storage/wire representation of existing job/approval/history requirements for T002/T007/T021–T027. Individual DTO parsing never grants live permission, admits a job, updates desired state or proves a host outcome. The schema2 loader and coordinator must additionally validate all references, exact plan/body digests, current admission policy, quotas and atomic transitions. No generic JSON payload is an executable or an authority object.

## Common fields and trust boundary

Objects have exactly the fields listed below, including explicit nulls. Every persisted record has workspaceId UUIDv4. IDs use lowercase UUIDv4, digests lowercase SHA256, public text the model's NFC/control rules, timestamps exact UTC milliseconds. Unknown fields/types, coercion, non-finite values and invalid Unicode reject. Revisions are int1..2147483647; sequence/count fields explicitly use int0..9223372036854775807 (event sequence starts1). Each record is at most256KiB/depth16 except JobEvent at most4KiB. Parsers copy before asynchronous work and return immutable state; toJson returns independent values. No caller exception/input/raw subprocess/config text appears in validation errors or structured outcomes.

`originGrantId` / `grantId` null denotes an authenticated owner UI operation, consistent with authorGrantId:null for owner-authored revisions. Non-null is the original ClientGrant ID, never a requested current replacement identity. Null is not accepted as a caller-selected owner capability: locald supplies origin from its verified immutable session role. MCP reads/cancel/reconcile match the original non-null grant and permitted target; null-owner records are visible to owner UI only. Live policy is checked separately even when a historical record parses successfully.

`authorityRef` is exactly `{kind:"delegation"|"approval",id:UUID,revision:int}`. Revision is the immutable Delegation revision or1 for the immutable one-plan approval decision. A null-grant job requires kind approval: the authenticated owner explicitly approves the same immutable plan through the same one-plan admission path; owner actions never manufacture a ClientGrant or acquire implicit delegation. Non-null grant jobs may use either kind after current scope checks. Approval substitutes only the delegation, never target/grant/trust checks. Revoke/current revision/plan binding must be rechecked on admission and each new effect.

## Safe outcome vocabulary

Only these optional safeCode values are permitted in job outcomes/events: `VALIDATION`, `FORBIDDEN`, `REVISION_CONFLICT`, `RESOURCE_LIMIT`, `TIMEOUT`, `STORAGE_BLOCKED`, `INTERNAL`, `TRUST_REQUIRED`, `TRUST_CHANGED`, `APPROVAL_REQUIRED`, `PLAN_EXPIRED`, `PLAN_STALE`, `HOST_BUSY`, `EXECUTOR_UNAVAILABLE`, `RUNTIME_INCOMPATIBLE`, `UNKNOWN_OUTCOME`, `UNSUPPORTED`, `CHECK_FAILED`, `CANCELLED`, `DISCONNECTED`. They are fixed protocol categories, never remote messages. Detailed private observations/logs have their own bounded read channel; they are not copied into history fields.

Check result enum: `passed|failed|unknown|unsupported|denied|timeout`. A check result object is exactly `{checkId,stepId,result,safeCode}`. checkId/stepId use profile identifier grammar; safeCode nullable. At most32 check results per outcome with unique (stepId,checkId). This is a bounded summary, not raw SQL or all progress: fixed compiled checks determine required success independently, and executor receipts preserve their full relevant evidence.

Job outcome is exactly `{effects:"none"|"confirmed"|"uncertain",checks:[...],safeCode:null|enum}`. Effects describe known change evidence, not success. `succeeded` requires effects none/confirmed, all summary checks passed and safeCode null. A successful no-change job may have effects none. `failed` requires a non-null safeCode and effects none/confirmed; any ambiguous effect is unknown instead. `cancelled` requires safeCode CANCELLED and effects none/confirmed; previous partial effects are retained. `unknown` requires effects uncertain and safeCode UNKNOWN_OUTCOME. An empty check summary is not independent proof of successful acceptance: coordinator/executor must compare against the exact plan's required postchecks before writing succeeded. Observational reconciliation may prove none/confirmed effects and a terminal state; it never executes a step to learn the result.

## Job

Exactly `{workspaceId,id,requestId,immutablePlanId,planDigest,profileId,profileRevision,profileDigest,grantId,authorityRef,hostAttemptId,state,nextSequence,cancelRequested,createdAt,updatedAt,outcome}`. grantId nullable as above, hostAttemptId is generated/persisted at local admission even while queued. State enum `queued|running|cancel-requested|succeeded|failed|cancelled|unknown|reconciling`; nextSequence1..int64max, cancelRequested boolean, createdAt<=updatedAt. No caller clock is accepted for admission.

Queued requires cancelRequested false; cancel-requested requires true. Running requires false (recording a cancel transitions to cancel-requested atomically). Terminal succeeded/failed/cancelled and unknown require the corresponding non-null outcome; queued/running/cancel-requested/reconciling require outcome null. Reconciling preserves previous unknown evidence in immutable events/host receipt until its observational result is committed. cancelRequested may remain true on terminal/unknown/reconciling records after a late cancel; it never promises rollback or no effect. nextSequence is the next unallocated event sequence, not array length; overflow blocks allocation, never wraps.

Allowed state edges: queued→running/cancelled; running→cancel-requested/succeeded/failed/cancelled/unknown; cancel-requested→succeeded/failed/cancelled/unknown; unknown→reconciling; reconciling→succeeded/failed/cancelled/unknown. Terminal states never restart. Updating sequence/progress/cancel metadata may retain a state, preserving its previously recorded outcome unchanged; refining unknown evidence follows the reconciling transition and never silently rewrites a same-state outcome. All other edges reject. Cancel flag never goes true→false. Same job preserves all immutable identity fields, origin, authority and createdAt; updatedAt/nextSequence never decrease. Transition helpers are structural checks only: existing executor-safe-boundary/no-replay rules still gate committing an edge. Snapshot parsing does not substitute for checking a transition against the previous durable record.

The loader resolves immutablePlanId and requires matching workspaceId, planDigest, exact (profileId,profileRevision,profileDigest), original grant and server/host identity through the plan; grant/authority/revision records must exist and bind this plan/tuple. Exactly one job per immutable plan, even with different requestId. A current expired/revoked grant is retained as history, never treated as current execution permission. An admitted job may outlive its plan's five-minute admission expiry. This does not renew authority for a new effect.

## ApprovalRequest

Exactly `{workspaceId,id,planId,planDigest,grantId,createdAt,expiresAt,state,jobId}`. grantId nullable owner origin; state `pending|approved|denied|expired|consumed`; createdAt<expiresAt, expiresAt<=createdAt+5min. Loader requires same workspace/planDigest/origin and plan.createdAt<=approval.createdAt<approval.expiresAt<=plan.expiresAt. Admission rejects expired/currently unauthorized plan regardless historical parsed state.

jobId is non-null only when consumed, required then. Allowed edges pending→approved/denied/expired; approved→consumed/expired; terminal denied/expired/consumed cannot change. Same-state reads/idempotent responses preserve the decision/job. approved→consumed and one job admission occur in the same transaction, after policy recheck; approval and job mappings must agree. Identity/plan/origin/timestamps immutable. Repeat decisions return the original decision/job through durable receipts, never consume twice.

## DesiredState

Exactly `{workspaceId,id,serverId,resourceId,desiredRevision,bodyDigest,inputDigest,lastJobId,observedRevision}`. resourceId matches `[a-z][a-z0-9_.-]{0,63}`; desiredRevision positive31-bit revision, observedRevision nullable positive revision<=desiredRevision. A non-null observedRevision associates the observation with that previously confirmed desired version; it does not claim current freshness or lack of drift. Latest observations remain bounded in-memory records with their own quality/time.

Loader/coordinator requires lastJobId to reference a succeeded job in the same workspace/server and plan, bodyDigest to match exact job profileDigest and inputDigest to match the canonical resolved complete parameter map of that immutable plan. The resource must be one of that plan's compiled owned resources. There is at most one current row per (serverId,resourceId); updates increment desiredRevision atomically, retain id and never wrap. Failed/cancelled/unknown attempts cannot overwrite it. Recording drift/last attempt is separate from changing confirmed desired state.

## JobEvent

Exactly `{workspaceId,jobId,sequence,timestamp,kind,stepId,state,safeCode,checkResult,droppedCount}`. sequence1..int64max, timestamp UTCms. kind `state|step|check|progress|dropped`. stepId nullable profile identifier; state nullable job-state enum; safeCode nullable safe enum; checkResult nullable check-result enum; droppedCount0..int64max.

kind state requires state non-null, stepId/checkResult null and droppedCount0; kind step requires stepId non-null, state/checkResult null and droppedCount0; kind check requires stepId/checkResult non-null, state null and droppedCount0; kind progress requires state/checkResult null and droppedCount0, stepId optional; kind dropped requires droppedCount>=1 and state/stepId/checkResult null. No free text/value/module stdout field. Loader checks workspace/job exists and sequence<job.nextSequence, unique jobId:sequence and ordered nondecreasing timestamps per job. Event rows are immutable. Progress overflow emits bounded dropped summary while retaining state/outcome; mandatory status outcomes remain durable even when progress retention is exhausted.

## MutationReceipt

Exactly `{workspaceId,requestId,originGrantId,objectGrantId,canonicalDigest,operation,result,createdAt}`. originGrantId identifies the initiating verified session (null owner), while objectGrantId identifies the referenced plan/job/approval/delegation's original grant. These identities are intentionally distinct: an owner approvals.decide receipt has originGrantId null and objectGrantId G when approving an MCP grant G's plan. Owner actions never relabel that plan/approval/job to owner origin. An owner may act on a grant-origin object only under the same current object policy; owner approval does not resurrect revoked/expired G. For workspace-owned profile catalog and grant-management objects, objectGrantId is null. A delegation object always has its non-null grantId as objectGrantId. All fields are derived by trusted coordinator, never accepted as caller authority.

Result is a closed stable acknowledgement union below, at most4KiB; no arbitrary response/input/result blob. Receipt is at most8KiB. Every result has exactly listed fields, UUID/digest/revision/authority validation as elsewhere. These same result objects are returned as mutation success data to owner UI/MCP. The full immutable result is committed atomically with mutation/receipt and replayed verbatim after current authorization, including after a restart or subsequent object changes. It intentionally contains no mutable labels, profile bodies, current grant/job/approval state, expiry/freshness assertion or configuration path; clients read those through current read methods. Revision/digest identify the operation's committed version, not the latest head. Replay never reconstructs from current mutable metadata.

| operation | Exact result |
| --- | --- |
| grant.create / grant.replace / grant.revoke | `{grantId,revision}` |
| delegation.create / delegation.revoke | `{delegationId,revision}` |
| profile.create / profile.update | `{profileId,revision,digest}` |
| profile.archive | `{profileId,revision,archived:true}` |
| plan.create | `{planId,planDigest}` |
| approval.request | `{approvalId,planId,planDigest}` |
| approval.decide | `{approvalId,planId,planDigest,decision:"approved"|"denied"}` |
| job.apply | `{jobId,planId,planDigest,authorityRef}` |
| job.cancel / job.reconcile | `{jobId}` |

Operation names are internal canonical domain methods; MCP tool/owner API adapters map to the same method, not a second mutation implementation. Owner automation save maps profile.create/update. Only committed successful mutations have receipts; a rejected pre-admission APPROVAL_REQUIRED/validation/policy request does not reserve a job or fabricate success. Same request ID can be retried with identical validated input after policy prerequisites change, but it cannot replay an admitted effect. Terminal jobs never restart. Existing foundation profile/settings receipts keep their original schema and response contract.

grant.*, delegation.* and approval.decide are owner-only (originGrantId null). grant.* and profile.* require objectGrantId null. delegation.* requires objectGrantId non-null. For a non-null initiating grant, plan/approval/job objectGrantId must equal originGrantId; profile catalog operations have objectGrantId null and require author scope. An owner origin may reference either owner or grant-origin plan/approval/job as above. Loader checks referenced workspace, exact immutable plan/profile tuple and objectGrantId against the actual retained entities; authorityRef on a job.apply result matches admitted job. Owner decisions on grant-origin approval are positive required cases, while G cannot read/replay another grant's or an owner's receipt even if it can see the same object through its normal read API.

Request digest is computed by coordinator from exact validated operation/initiator/input canonical representation; it is not a caller-authorized hash. Same requestId with different canonical input conflicts within authorized original origin. An out-of-origin receipt lookup/replay is FORBIDDEN before returning result/conflict/existence information. GC retains receipt and referenced identity/authorization history for promised retention, but mutable response snapshots are unnecessary because the result above is already durable. No result contains secretRef/blob/credential material. Grant create/replace returns no config in its receipt: owner-only read `grants.configuration{grantId}` generates current verified executable/args from current bundle and current public grant. It never exports the client secret and remains separate from replay.

Retention is explicitly the same fail-closed policy as foundation receipts: new StoredAutomationReceipt has its own limit10000 records per workspace, no expiry, no eviction and no receipt-delete/reset API. Time passage, revoke, restart and publication of another executable never forget a consumed requestId or allow replay as new. Admission at10000 returns RESOURCE_LIMIT before changing an entity, staging an active credential, allocating an event or contacting a write executor. Existing receipt lookup/replay remains possible under current authorization at quota. Rejecting a mutation does not consume a receipt slot. Retained receipts pin their actual referenced entity/revision/approval/plan/job and authorization-origin identity history; referenced plan/job/evidence is not GCed merely because30days elapsed. Atomic safe GC applies only to terminal unreferenced records after30days and their unreferenced related records, never breaks a retained receipt reference. This deliberately bounds lifetime admissions: if receipts or pinned plans1000/approvals100/history reach their respective quotas, new admission blocks even after30days. The feature does not promise a rolling capacity window, automatic history erasure or unlimited lifetime jobs. Current workspace budgets must be visible as RESOURCE_LIMIT rather than a hidden history reset. These bounds preserve the existing no-replay guarantee rather than inventing an expiry after which UUID reuse becomes a new write.

Reference validation distinguishes immutable result version from latest mutable state: a retained grant/delegation/profile metadata revision may be newer than acknowledgement revision, but not older; profile revision/digest still resolves to its exact retained immutable revision. An approved decision receipt remains approved when that approval is later consumed/expired, not rewritten to current state; denied is terminal. Job/plan/authority identity in result remains exact. Historical current-policy changes do not corrupt the record or authorize a new effect; live policy is separate.

## Implementation and acceptance

Full retained graph validation additionally enforces creation and owner decision evidence from the [loading contract](loading.md). Consistent repeated approval.decide/job.apply calls with different request IDs may commit stable acknowledgement aliases for the original object without a second decision/admission/effect; aliases do not extend lifetime or replace the canonical original creation/decision receipt. Current authorization and receipt quotas still apply. Creation/owner-consent provenance uses the original timestamps/request IDs, never a later acknowledgement time.

Shared immutable structural DTOs and transition checks live in packages/serverdeck_protocol/lib/automation/job_records.dart (T002); complete reference resolution, live policy, atomic CAS/event allocation/receipt/admission and safe GC are locald automation/store.dart and jobs/authority services (T007/T021–T027). Full Plan/Desired input/resource derivation belongs to trusted plan/compiler validation; the partial identity fields above are never enough to admit an effect. No automation collection may be loaded as opaque or discarded by schema2 startup because its validator is missing.

Tests must cover exact fields/enums/ranges/timestamps, owner/null initiator vs object grant origin (including owner approval of G), authority tuple/reference mismatch, state/outcome/cancel combinations and every allowed/forbidden edge, same-plan single job, ordered/unique event sequences and overflow, blocked/expired/stale/current-policy separation, cross-workspace references, immutable input/output copies, byte/depth limits and rejection of private free text in structured history. Stable acknowledgement replay after later profile labels/head/archive, grant replacement, approval consumption and job completion must preserve the original result across restart; current state is read separately. T007 tests must prove no expiry at30days or later, exactly10000receipt admission boundary/no partial commit, retained replay at quota, pinned reference refusal to GC and RESOURCE_LIMIT at pinned entity quotas. DTO tests prove structural validation only; actual Isar transaction/restart/concurrency and executor/VM acceptance remain separately required.
