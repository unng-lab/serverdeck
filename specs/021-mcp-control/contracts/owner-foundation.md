## Scope and composition

Implement explicit `MutationCoordinator.operational` for a ready schema2 StateStore. The existing constructor remains schema1 and continues to refuse operational writes. The operational constructor uses the same ProfileService, validation, custody, receipt digest, foundation storeRevision, immutable input capture and stable acknowledgements. It selects commitOperationalFoundation explicitly; no caller-selected storage mode or runtime fallback is accepted from a wire request. Retained automation data is never reconstructed by this coordinator.

`OperationalFoundationOwnerApi` supplies exactly profiles.list/get/create/update/delete, settings.get/update and mutations.get/recent through OperationalApiServer. Its constructor requires the operational coordinator, its identical store and the actual native-bound registry. Missing native composition fails NOT_READY; unavailable operational storage fails STORAGE_BLOCKED. Every preparation and execution checks same-registry live owner and exact admitted method before inspecting method-specific input or data. MCP or foreign registry calls fail FORBIDDEN. Unknown methods fail UNSUPPORTED. This does not install the application startup or supply SSH/trust/automation/executor services.

The trusted OperationalOwnerApi.prepare interface receives required named `requestId`, populated from the already validated Local API envelope id by OperationalApiServer. Preparation is synchronous and returns a bounded, request-bound OperationalOwnerInvocation; execution is separate as defined below. Foundation mutations retain their existing API1.0 parameter shapes and use this envelope UUID as their durable ID. Grant operations continue to use their explicit body requestId, independently of their transport id. No wire fields, protocol version or acknowledgement shape change. Update all implementations and native fixtures; no optional missing-ID fallback. A trusted immutable OperationalOwnerApiGroup composes grant and foundation adapters: exactly one supporting adapter may dispatch, zero means UNSUPPORTED, multiple means INTERNAL with no dispatch. The server still performs ordinary role/readiness/publication checks. Trusted direct fixture/service dispatch uses an extension that prepares and executes only an already initially proved request, with the same cleanup rules.

## Admission and execution

OperationalSessions separates initial admission concretely: synchronous reserve(channel,sessionId,method) performs existing live-session identity/role/method and per-session16 quota checks, reserves its ordinary request interest, and returns the opaque request without native IO. completeAdmission(request) owns and shares one initial-proof future: revalidate the actual peer within the request remaining5second budget, renew the session lease only on successful proof, and set a private initial-proof-success marker on that exact live request. Foreign/completed/stopped requests fail; no caller can set the marker. Existing begin remains a compatibility wrapper over reserve followed by completeAdmission, preserving all existing callers' initial-proof guarantee. Late proof after timeout/disconnect cannot set the marker or activate an invocation.

OperationalApiServer uses reserve synchronously after envelope validation. For an owner route it then checks owner role/exact method and readiness and calls the supporting adapter's synchronous prepare before invoking completeAdmission or any other asynchronous/native wait. prepare may validate/copy/canonicalize/register a reservation, but cannot prepare credentials, write, acquire a native gate or read a method result. The subsequent completeAdmission must succeed before invocation execution. Builtin/MCP routes still complete native admission before accessing their payload/object data; denied role/method never calls owner preparation. An unsupported or validation-failed call retains the existing authenticated safe-error response path without effects.

OperationalOwnerInvocation is bound to its exact request and adapter and owns only trusted static service callbacks plus captured immutable command/reservation. It exposes execute and idempotent close, never a wire token or role provider. execute refuses unless initial-proof-success is set on that same current native owner request; it runs at most once and shares its actual result. close before execution removes this caller's reservation interest; after activation it never cancels a running write. Server finally closes the invocation on initial-proof error, timeout, disconnect, readiness/error or completion, and retains the channel's existing final publication proof/request-interest lifetime. If preparation throws after reserving, it must release its own reservation before rethrowing. Adapter group selects exactly one preparer before invoking it. No permissive default preparation or proof bypass is allowed for grant adapters or fixture implementations; convert them to the explicit prepare/execute interface.
Capture normalized mutation inputs synchronously before awaiting a gate, using existing strict method validation and the receipt-key canonical digest. Neither caller map changes nor an asynchronous gate wait may change the admitted command. Foundation reads retain their existing strict validation/results and owner-only status/recent semantics; mutations.get must not use the current transport id as its queried ID. Foundation status/recent remain foundation-only and never disclose automation receipt payloads.

All profile creates/updates/deletes conservatively acquire beginTargetChange, including public metadata-only changes and exact durable replay. This reserves the synchronous open fence, acquires the actual native publication gate and retires old MCP sessions before any coordinator execution admission. Settings updates acquire runAuthorityMutation without retiring unrelated MCP sessions. Both use the request's original remaining5second budget, revalidate actual native owner proof after acquisition within the remaining budget, and check that budget immediately before reservation activation. Reads revalidate native owner proof within the remaining budget before accessing results. Do not hold the StateStore queue while waiting for a publication gate.

Retain the real lease until coordinator preparation, native commit/rollback, full readback and callback completion settle. Timeout or disconnect cannot unlock an admitted write; publication remains subject to the existing channel's final owner proof. Physical release failure returns SERVICE_UNAVAILABLE, never successful ACK; durable receipts remain available for recovery. Close the coordinator before closing its store; registry close waits its actual gate-owned effects. No automatic retry or force release.

Before the first asynchronous/native wait, the owner adapter uses a synchronous bounded coordinator reservation: validate/capture normalized command, compute the private receipt digest, register requestId/digest/requester interest and return an opaque coordinator-bound token plus its shared result future. Reservation does not join StateStore._tail, run ProfileService.prepare/custody replacement or acquire a native lease. A fresh unactivated reservation is visible as queued through mutations.get. An identical duplicate attaches to the same pending result; changed input conflicts synchronously before gate acquisition. A persisted exact receipt remains committed in status but its wire acknowledgement still passes the gate/proof path. An automation-consumed ID conflicts before reserving. Every pending distinct ID, including reserved and running, counts against the operational coordinator32 cap.

Each live caller owns a distinct bounded requester-interest token associated internally with its actual native owner session. Its adapter invocation acquires the appropriate gate before activating the opaque reservation; activation may enqueue preparation only once, and later activations observe the shared result or stable receipt. Gate acquisition remains independently bounded by16 and the original caller budget; a duplicate does not start a second durable operation. No caller-supplied token, digest or requester/session identity is accepted on the wire. Adapter session-detach subscription removes only that session's caller interests; a failed/timed-out preactivation invocation removes only its own interest. Removing the last interest cancels a reserved/queued operation (status becomes not-found), never a running effect. Another live session's duplicate survives the original session disconnect and may activate after its own native proof. A cancelled/stopped/foreign coordinator token cannot later activate when delayed gate acquisition completes. A caller whose own gate/proof fails gets its fixed failure, regardless of a duplicate's later successful result.

Coordinator close stops new reservations and cancels all reserved/queued interests, drains running writes and completes; registry close separately owns and waits actual in-flight native acquisition/lease cleanup. Adapter close unsubscribes detach listeners and stops reservations before coordinator/store teardown. Cancellation does not force a native lock release or erase a committed receipt. These reservation/activation rules preserve the inherited synchronous inflight/status contract while keeping gate acquisition outside the store queue.
The operational coordinator checks the current automation receipt registry before either replay or new foundation admission, and again inside its serialized drain before preparation. Any automation-consumed requestId fails IDEMPOTENCY_CONFLICT, without returning its payload or performing custody work. Grant writers already symmetrically reject foundation IDs. Production writers serialize under the common native gate before either queue; internal trusted primitives do not constitute a separate wire entry point. Exact foundation duplicates keep existing shared-future/changed-input conflict semantics. Enforce the coordinator32 admission limit including its running operation; StateStore retains its independent combined32 grant/foundation cap. Queue cancellation/close retain existing requester-interest semantics and drain real running writes.

Operational admission, status and reads fail STORAGE_BLOCKED if the operational snapshot is unavailable; they cannot fall back to cached schema1 state during grant publication. Preserve fixed HOST_BUSY from the native occupied-identity guard as a domain refusal that does not poison storage. Floor commit timestamps by retained foundation and automation receipt timestamps so clock rollback cannot produce a new foundation timestamp earlier than already committed automation activity. Existing UUID reuse, CAS, quotas, DPAPI and graph readback remain the storage primitive's responsibility.

## Acceptance

Use actual schema2 Isar/CurrentUser DPAPI with a nonempty retained graph. Prove coordinator settings/profile commit/reopen and stable replay, changed-input and automation-ID conflict without writes, immutable input/duplicate/queue/close behavior and legacy refusal. Prove occupied running/unknown target HOST_BUSY preserves readiness and permits public metadata changes. Preserve every automation native ID/payload.

Actual format2 AOT/native owner/MCP clients exercise the ordinary OperationalApiServer/Channel/ApiClient with the composed adapters. Verify owner reads/writes/status/recent; MCP and foreign/method mismatch refusals before object access; actual independent gate blocking prevents preparation/commit; input mutation while blocked cannot alter command; queued status and immediate changed-input conflict while either the initial native proof is delayed or an independent publication gate is held; identical duplicates share one durable write, another owner session can activate after the first disconnects, last-interest disconnect/close and initial-proof refusal cancel before gate without effects or late activation; target writes retire old MCP sessions while settings writes preserve them; fresh protected opens observe committed target identity. Include failed CAS/occupied target lease release and graceful close retaining a real durable write until actual callback settlement. Existing grant owner and gateway suites must keep passing after dispatch-interface changes.

T109 additionally requires queued completed target-dependent stdout ordering through actual target writes; T110 retains other mutators, poison recovery and installed startup. This component does not enable readiness flags or establish full 021 acceptance.

The typed OperationalApiClient.call accepts optional caller-created requestId for the unchanged transport envelope. Omission retains the ordinary random read/grant transport ID behavior; a provided ID must be UUIDv4, is copied before asynchronous work, and a duplicate currently pending ID fails local IDEMPOTENCY_CONFLICT without a second frame. Completed IDs may be reused for explicit stable foundation replay. UI foundation mutation callers create and retain the ID before the first call and use a different envelope ID for mutations.get; no automatic new-ID effect retry. Body grant requestId remains independent.

Native acceptance may use SERVERDECK_TEST_OWNER_SERVICE_PROBES only as an explicit compile-time test build. The ordinary build rejects installation with OWNER_PROBE_UNAVAILABLE; there is no runtime/wire setting. Its fixed boundaries beforeInitialProof and afterFoundationCommit expose only the method name and may delay/fail scheduling around the actual native proof or committed transaction; they cannot supply roles, credentials, input, peer identity or a successful proof. Real Isar/DPAPI/native checks still execute. Qualify the disabled ordinary variant separately and retain actual physical process cleanup. These hooks do not enable product readiness.
