# Workspace migration1→2

[Model](../data-model.md), [plan](../plan.md), [tasks](../tasks.md).

## Atomic publication rather than in-place schema open

Pinned Isar3.3.2 changes its native collection registry during `Isar.open`, before an application write transaction. Even an identical-schema open/read/close can change physical DB bytes. Therefore no Isar open occurs on the active file while migration source/target hashes bind recovery. All semantic validation uses protected copies; only read-only native snapshot inspection/hash reads access active DB until migration cleanup completes. Actual synthetic native probe evidence is recorded in [verification](../../../docs/development/mcp-verification.md). Adding native collections and the application version marker cannot be one in-place Isar transaction.

Supported failure model: locald process termination, including hard kill at each named boundary, failed native/application operations and storage/DPAPI/path errors while Windows/filesystem remain running. Native DB uses relaxedDurability:false, protected file contents are flushed and every Isar close confirmed. Publication uses existing retained-handle `promoteProtectedPath(replace:true)`/FileRenameInfoEx with REPLACE_IF_EXISTS|POSIX_SEMANTICS after confirmed close, checks success and revalidates resulting file. It does not provide a write-through rename flag. No OS crash/power-loss ordering guarantee is inferred from this primitive or ordinary process-kill tests. After an OS/storage crash all normal integrity checks still apply and ambiguous states block without reset/automatic rollback; power-failure recovery is not a qualified acceptance claim of this feature. No copy/delete or weaker replacement fallback is allowed if required atomic same-volume rename semantics are unsupported.

The sole locald writer owns the existing workspace mutex throughout migration and all native handles must be confirmed closed before file publication or lease release. Same-build1.1 startup only, old UI/locald stopped first; no hot upgrade. Schema1 has no automation jobs; later schema2 upgrades must refuse active/unknown jobs. No remote server or credential rotation occurs during migration.

Paths below are relative to the protected `workspaces/` parent. Active workspace stays `default/`, with existing `workspace.isar`, `workspace.isar-lck`, `workspace.manifest.json`, `receipt-key.dpapi`. Staging is exactly `default.upgrading-1-2/`, owner-only ACL, same volume. Reject reparse points, unsafe parents, foreign ACLs and unknown stage entries before any writable open/delete/replace. Only these stage names are allowed: `migration.json`, `migration.json.new`, `workspace.isar`, `workspace.isar-lck`, `original.isar`, `manifest2.json`. Temporary `.new` is only for atomic journal replacement. Stage files contain private workspace data and never enter bundle/logs/source control.

Schema1 manifest remains the exact existing object `{product:"serverdeck-next",schema:1,workspaceId,receiptKeyId,ownerSid}`. Schema2 manifest is exactly `{product:"serverdeck-next",format:2,schema:2,workspaceId,receiptKeyId,ownerSid}`. Native `StoredWorkspace.payload` retains existing identity/storeRevision fields and uses `schemaVersion:2`, not a second alias field. Public foundation revisions keep existing decimal-string encoding.

## Preparation and commit sequence

1. Verify original manifest/key/ACLs/read-only native registry schema1 with no active DB native handle. Capture active DB/manifest/key-wrapper SHA256. Open the receipt key through existing custody but perform no Isar open on active. Never load legacy/import data in this migration.
2. Require at least144MiB available on the workspace volume before staging: two bounded64MiB files plus16MiB reserve. Recheck16MiB reserve before writes/publication; actual disk-full errors fail closed regardless estimates. DB maximum stays64MiB in this feature; logical quotas do not guarantee space for all maximum-size records. Future admissions must enforce actual native capacity and return RESOURCE_LIMIT without partial commits.
3. Create/validate protected stage. Flush journal `preparing` before creating any stage DB/backup. Journal exact fields: `format:1,fromSchema:1,toSchema:2,migrationId:UUIDv4,workspaceId,receiptKeyId,ownerSid,sourceDbDigest,sourceManifestDigest,sourceKeyWrapperDigest,phase:"preparing"`. Digests SHA25664lowerhex. Bind identities/hashes to the read-only validated active source; journal is not authority to load arbitrary paths. Create `original.isar` as verified byte-identical source backup and `workspace.isar` as another protected copy; create protected empty stage lock file. Before schema change, open only staged workspace.isar using schema1 definitions and existing full row/reference/DPAPI validation, capture immutable old row payloads/native IDs, then confirm close. Opening this copy may change its physical DB metadata; do not compare its post-open hash with original source hash. Active source and original.isar must still retain sourceDbDigest.
4. Open only the staged DB with complete schema2 definitions. Isar may commit its native schema here. In one application transaction change schemaVersion1→2 and establish empty new collections/initial metadata. Preserve byte-for-byte every existing server profile/settings/credential/receipt payload and native ID, workspace/key IDs and counters; no credential decrypt/re-encrypt or ID allocation for existing rows. If the transaction/open/close fails, active DB is still untouched schema1; return STORAGE_BLOCKED and keep source/key intact.
5. Confirm staged native close, validate exact schema2 native registry and complete schema2 row/reference/DPAPI invariants using the staged DB. Compare every old row/payload/ID with the captured validated source rows; all newly introduced collections must be empty. Confirm native close after the final semantic validation and only then compute targetDbDigest. Later snapshot/hash reads must not open Isar on this frozen candidate. Create/flush strict canonical `manifest2.json`. Atomically replace journal with `phase:"prepared"` and additional required `targetDbDigest,targetManifestDigest,sourceRowsDigest`; no optional caller fields. sourceRowsDigest is computed from the validated source and must also match staged target old entities using the preservation digest below. Verify original.isar digest and active DB/manifest/key-wrapper source hashes again.
6. Atomically rename the verified stage `workspace.isar` over active `workspace.isar` using the retained-handle same-volume primitive and process-crash model above. No native handle is open. This single file replacement is the DB publication commit; prior to it active is entirely1, after it entirely2. Never overwrite the receipt-key wrapper or old entities separately. Keep original.isar until manifest publication/verification finishes.
7. For post-publication/recovery full target validation, copy active DB (requiring targetDbDigest before/after copy) into the now-vacant stage workspace.isar; any old verification copy there is checked as a safe known stage path then removed/rebuilt. Open/validate only that copy with schema2, require its preservation digest to match prepared sourceRowsDigest, validate references/DPAPI/new-collection expectations, and confirm close. Its physical hash may change and is never republished. The source backup is hash-checked only, never opened in Isar during journal-bound recovery. Active target hash must remain targetDbDigest. This reuses one64MiB stage slot, so backup+verification copy stay within the two-file staging bound. Atomically replace active manifest using staged manifest2. Verify manifest2 hash, active read-only native snapshot/hash and unchanged key wrapper; complete deterministic stage cleanup before service readiness or admitting any mutation/native open on active. Delete only known stage files after ACL/path/hash checks and remove the empty stage directory last. Backup is solely migration recovery data; automatic rollback after DB publication is forbidden. Cleanup failure blocks readiness, retaining recovery files. Active original lock path remains and is checked before later normal open.

Preservation digest is SHA256 of foundation canonical JSON `{workspace,settings,profiles,credentials,receipts}`. workspace is `{nativeId,payload}` with payload the validated workspace metadata object excluding only schemaVersion (which must be exactly1 for source or2 for target); no other field normalization/removal. settings is the sole `{nativeId,payloadBase64}` row. profiles/credentials/receipts are lists of `{nativeId,entityId,payloadBase64}` sorted by nativeId ascending. payloadBase64 is standard padded base64 of the exact persisted payload string UTF8 bytes, so canonical NFC processing cannot hide a byte/escaping difference. Existing loader validation still applies; do not invent a new canonical-source requirement or rewrite valid old payloads. IDs never reallocated. This digest binds old business rows across a process crash without opening/modifying the source backup. New collections are separately required empty; workspace metadata gains no new fields besides changed schemaVersion. Hashing may stream canonical bytes to avoid duplicating a64MiB aggregate.

## Startup recovery table

Classification reads/validates native snapshot and manifest before writable open. While a journal exists, full semantic integrity validation uses the copied-DB protocol in step7; never an active Isar open that would invalidate hash bindings. For committed normal2/2 without journal, ordinary existing service open/validation may update native metadata normally. Structural corruption takes precedence over compatibility. Missing/foreign/mixed collections or partial native schemas are never interpreted as an empty workspace.

| Active DB / manifest / stage | Required result |
| --- | --- |
| 1 / 1 / absent | Normal migration preparation. |
| 1 / 1 / empty protected stage directory | Recreate preparing journal and start preparation. |
| 1 / 1 / valid preparing or prepared journal | Verify active source identity and all three source hashes. Stage DB may be partial and is never opened as active. Safely remove only known stage artifacts and rebuild from intact source. Journal replacement residue must match validated preparing/prepared identity; unrelated/corrupt journal blocks. |
| 2 / 1 / prepared journal | Only recognized commit gap: verify active target digest, old manifest/source key hashes, backup source digest, full target native/row/DPAPI integrity and exact workspace identity. Publish manifest2, then verify/cleanup before readiness. No rollback/re-run of source migration. |
| 2 / 2 / prepared journal | Both active target/manifest hashes and full integrity must match journal; finish remaining cleanup. Backup may already be deleted during cleanup. No mutations were admitted before cleanup, so changed target DB hash is corruption, not a reason to accept arbitrary state. |
| 2 / 2 / absent or empty stage directory | Validate full schema2 identity/integrity; remove only empty protected stage directory if present; normal open. |
| 1 / 2, 2 / 1 without valid prepared journal, unknown/future/partial schema or malformed journal | INCOMPATIBLE for unknown schema/manifest combinations, STORAGE_BLOCKED for corrupt data/identity/hash/ACL. Preserve files, never initialize/reset/auto-rollback. |

During cleanup remove `migration.json` last among files. If crash occurs after its deletion, only an empty directory may remain; this is the normal2/2 recovery case. If staged manifest2 is missing after a crash, reconstruct its canonical strict schema2 bytes only from fully validated workspace/key identity and require exact targetManifestDigest from the prepared journal before publication; never synthesize from unverified staging input. Before DB publication original backup must exist; after manifest2 publication it may be absent only as part of cleanup.

Failure/crash tests must kill separate owned child processes before/after source validation, journal flush, stage native schema open, uncommitted/committed stage transaction, staged close/verification, prepared journal replace, active DB replace, manifest replace and each cleanup boundary. Prove source DB/manifest/key and existing row/ID/credential bytes preserved before commit; prove schema2 complete and no reset after commit gap recovery. Include future/partial native registry, malformed journal, source/target/hash mismatch, reparse/ACL, unavailable DPAPI, insufficient disk/native capacity, failed close and repeat recovery. Actual Isar and Windows atomic file publication tests are required; a pure decision table/mock does not qualify T004.
