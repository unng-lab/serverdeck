# Feature Specification: Установка и обновление нового клиента

**Feature**: `005-client-distribution`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Windows: самостоятельный пакет и hard cutover (Priority: P1)

Пользователь устанавливает новую реализацию одним пакетом без SDK и ручного запуска локального сервиса.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-005-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Windows: самостоятельный пакет и hard cutover», **Then** Новый клиент использует отдельную область данных и идентичность локального сервиса; старые данные и процессы не импортируются и не завершаются автоматически.
2. **AC-005-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-005-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

## Requirements

### Scope и зависимости

Обязательные предшественники: [001](../001-service-foundation/spec.md), [002](../002-security-storage/spec.md), [003](../003-design-system/spec.md), [004](../004-server-workspace/spec.md).

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

Нельзя мерджить все три этапа одним большим MR. Неизвестная совместимость нового варианта блокирует его включение, но не уже принятые независимые функции.

### Место в сервисе и ответственность

**Расширяемые компоненты**: упаковка клиента и locald, клиентский updater, readiness/shutdown службы.

Поставляет вместе совместимые компоненты 001; не заменяет их разработку installer-ом. Startup и состояние базы принадлежат locald; update проверяет его безопасный shutdown. Production Windows gate требует защиты 002; другие платформы имеют собственную приёмку.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-127**: Последующие обновления новой реализации ServerDeck сохраняют её профили, настройки, доступы и историю заданий. Переход со старого сервиса не импортирует их и не инициирует изменения серверов.
- **FR-005-LOCAL-01**: Первый production gate — Windows x64. macOS Intel/Apple Silicon, Ubuntu Desktop x64 и Android 7+ идут отдельными платформенными этапами; поддержка SSH и защиты заявляется по проверенной матрице, а не по наличию пакета.
- **FR-005-LOCAL-02**: Пакет включает клиент, локальный сервис/хранилище, шрифты и assets; после установки SDK или developer runtime не требуется. Platform prerequisites перечислены до установки.
- **FR-005-LOCAL-03**: Первый запуск создаёт пустое новое пространство. Старый сервис не обслуживает новый клиент: несовместимая identity/version отклонена. Installer не импортирует старые БД/credentials, не завершает старые процессы и не удаляет старые пользовательские файлы.
- **FR-005-LOCAL-04**: Последующие update/uninstall новой реализации сохраняют её профили, настройки, доступы и историю вне каталога замены приложения; удаление пользовательских данных — только отдельное действие.
- **FR-005-LOCAL-05**: Версия установлена из одного источника. Ручная проверка обновлений, проверка на старте и раз в шесть часов имеют постоянный opt-out. Проверка завершается за 30 секунд даже при неотвечающем источнике.
- **FR-005-LOCAL-06**: Предлагается только более новая stable версия подходящих OS/architecture. Prerelease, downgrade, отсутствующий пакет и несовместимая версия не устанавливаются автоматически.
- **FR-005-LOCAL-07**: Проверка, актуальная версия, доступность, непубликация, неподдержанная платформа, скачивание, готовый download и ошибка имеют разные состояния. Ошибка update не блокирует локальные серверные функции.
- **FR-005-LOCAL-08**: Desktop получает пакеты из доверенного проекта GitHub Releases; metadata задаёт точный размер и digest. До открытия проверяются размер, digest и предусмотренная платформой подпись издателя; подмена источника отклонена.
- **FR-005-LOCAL-09**: Скачивание и открытие установщика требуют отдельных действий пользователя. Открытие не считается установленным обновлением; работающий клиент не подменяется незаметно.
- **FR-005-LOCAL-10**: Android использует приватный сервис внутри жизненного цикла приложения, RuStore и increasing versionCode. Store error/cancel не заменяется скачиванием произвольного APK; доступна официальная страница магазина.
- **FR-005-LOCAL-11**: Release связывает версию, tag, commit, окончательные packages, hashes, notes и evidence. Сборки воспроизводимы с зафиксированными SDK/dependencies; CI проверки и платформенные gates обязательны.
- **FR-005-LOCAL-12**: Production gates включают Windows подпись, macOS signing/notarization, Linux clean-account install и Android production-signing/RuStore update. Review builds явно помечены; неподтверждённая платформа не объявляется production ready.

Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-005-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-005-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-005-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-005-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.

- **SC-005-LOCAL-05**: Установка одной заявленной платформы требует один пакет и не требует SDK; manual update check завершается за 30 секунд; все corrupted/older/wrong-platform fixtures отклонены.

Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».
