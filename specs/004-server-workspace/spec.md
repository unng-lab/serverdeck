# Feature Specification: Подключение и рабочее пространство сервера

**Feature**: `004-server-workspace`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Добавление и единое подключение (Priority: P1)

Пользователь сохраняет и подключает сервер одним маршрутом либо выбирает сохранение без соединения.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-004-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Добавление и единое подключение», **Then** Отмена сохраняет профиль; повтор Connect не создаёт параллельного подключения и не обходит host-key confirmation.
2. **AC-004-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-004-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-004-2A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Компактные карточки и метрики», **Then** Не больше 120 точек за 10 минут; метрики старше 15 секунд stale, старше 10 минут исчезают, пропуски не рисуются нулями.
2. **AC-004-2B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-004-2C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 3 — ПО и переход к связанному журналу (Priority: P2)

Пользователь просматривает компактные строки ПО и переходит к журналу выбранной службы.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-004-3A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «ПО и переход к связанному журналу», **Then** Цель и выбор сохраняются в двух темах на desktop и телефоне; детали не требуют чтения протокольных идентификаторов.
2. **AC-004-3B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-004-3C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

## Requirements

### Scope и зависимости

Обязательные предшественники: [001](../001-service-foundation/spec.md), [003](../003-design-system/spec.md).

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

Нельзя мерджить все три этапа одним большим MR. Неизвестная совместимость нового варианта блокирует его включение, но не уже принятые независимые функции.

### Место в сервисе и ответственность

Для совместного owner/MCP сценария конкретные хранение trust, schema3 migration, owner-only probe/confirm/revoke и пределы challenge определены в [контракте021](../021-mcp-control/contracts/host-trust.md). Guided connect вызывает тот же авторизованный locald; UI не хранит pin/SSH-доступ отдельно и MCP не подтверждает ключ. Принятый транспорт021 сам по себе не закрывает004.1 либо001.2.

**Расширяемые компоненты**: пользовательский клиент, connection orchestration и наблюдения locald.

Развивает уже работающий маршрут 001: компактные карточки, guided connect и контекстные переходы. Использует существующие авторизованные запросы/подписки, не создаёт второй транспорт или новую БД.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-022**: Обзор должен показывать известные сведения об ОС, архитектуре, ядре, имени и продолжительности работы. Недоступность отдельного поля не делает остальные поля неизвестными.
- **FR-023**: CPU, занятая память и заполнение корневой файловой системы должны иметь разные понятные подписи и единицы. Заполнение диска не называется нагрузкой ввода-вывода.
- **FR-024**: Карточки сохраняют максимум десять минут и 120 реальных точек истории. Нет данных, устаревание и разрыв не создают нулевой замер или линию до текущего времени.
- **FR-004-LOCAL-01**: Основное действие добавления — сохранить и подключить; вторичное — сохранить без подключения. Все недостающие шаги identity/access/connection выполняются последовательно, уже подтверждённые пропускаются.
- **FR-004-LOCAL-02**: На desktop графики CPU/RAM/root disk стоят одной строкой без отдельных рамок и больших процентов; действия внизу слева, графики внизу справа с общей нижней линией. Ошибки размещены выше и расширяются без перекрытия.
- **FR-004-LOCAL-03**: Общая ширина блока графиков 300 px при ширине desktop 1100 и 270 px при 800; высота plot 25 px. Подписи и значения компактны, единицы доступны текстом.
- **FR-004-LOCAL-04**: На phone меню и тема находятся сверху, Добавить сервер занимает ширину, статус расположен под адресом; три графика идут перед основной кнопкой подключения и двумя равными кнопками навигации. Цели касания не меньше 44 px.
- **FR-004-LOCAL-05**: График содержит только реальные точки последних десяти минут, максимум 120 на сервер. Stale curve пунктирная, разрывы не соединяются, данные старше десяти минут скрываются. Latest scalar тоже скрывается при таком сроке.
- **FR-004-LOCAL-06**: Соединён, подключается, отмена, offline/cached, отказ доступа, key mismatch, нет первого замера и expired имеют отдельные представления. Объяснение метрики доступно касанием, focus и accessible text.
- **FR-004-LOCAL-07**: ПО показано searchable/paginated компактными строками: имя, версия, тип, состояние, время наблюдения. Не менее двух строк помещаются вместо одной карточки высотой около 100 px; диагностические детали открываются намеренно.
- **FR-004-LOCAL-08**: Журнал службы открывается сразу с выбранной службой. Неизвестная связь не превращается в случайный выбор другой службы; raw logs сохраняются только в ограниченном текущем буфере.

### Приёмка требований

Все перечисленные FR применимы к назначенному ниже этапу; AC соответствующего этапа проверяет весь этот состав, включая отрицательные случаи. Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

- **004.1**: FR-022; FR-004-LOCAL-01; AC-004-1A/B/C.
- **004.2**: FR-023, FR-024; FR-004-LOCAL-02, FR-004-LOCAL-03, FR-004-LOCAL-05; AC-004-2A/B/C.
- **004.3**: дополнительные требования ниже; FR-004-LOCAL-04, FR-004-LOCAL-06, FR-004-LOCAL-07, FR-004-LOCAL-08; AC-004-3A/B/C.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-004-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-004-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-004-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-004-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.


Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».

## UI-компоненты и приёмка (003.4)

Обязательны [библиотека C01–C30](../003-design-system/component-library.md) и [общий контракт применения](../003-design-system/contracts/feature-adoption.md). C ID задаёт семейство готовых элементов, а не новый backend scope. C01 (токены), C02 (действия), C10–C12 (статусы/сообщения/состояния) и C17 (каркас страницы) применяются там, где соответствующая UI-композиция уже требуется этим пакетом.

| Композиция этого пакета | Готовые элементы | Данные, состояния и ограничения |
| --- | --- | --- |
| Профили, добавление и подключение | C02, C03, C04, C06, C07, C13, C14, C17, C24 | Устойчивый ID, имя/адрес и статус подключения; save-only, save-and-connect, доверие и отказ доступа сохраняют свои guards. |
| Карточка сервера и история | C09, C10, C11, C18, C21, C22 | CPU/RAM/root disk с единицами, source/time, gap/stale/expired и textual values; согласованная компактная геометрия 004 сохраняется. |
| ПО и связанный журнал | C05, C06, C07, C08, C16, C18, C20 | Имя/версия/тип/состояние ПО, поиск и разрешённая порция; переход в журнал сохраняет выбранную службу и цель, unknown association не подменяет службу. |

- **FR-UI-004-01**: Объявленные композиции MUST использовать перечисленные семейства и их применимые варианты; поля/действия сохраняют предметный смысл таблицы. Общая разметка, токены и поведение не копируются в отдельную реализацию экрана. Отсутствующий вариант сначала расширяется в 003 по общему контракту.
- **FR-UI-004-02**: Данные, callbacks, validation, поддерживаемая порция/сортировка и разрешённые эффекты MUST принадлежать owner этого пакета через действующий контракт 001; компонент не выполняет собственные запросы, retries или выдачу полномочий. Loading/empty/no-results/error/unavailable/stale/partial/unknown применяются по смыслу полученного результата.
- **FR-UI-004-03**: План и задачи MUST содержать mapping «композиция → C ID/вариант → данные/событие owner → критерий проверки». UI-работы ограничены объявленными здесь сценариями; существующая история задач сохраняется, реализация будущих backend возможностей приёмкой 003 не подтверждается.

**Проверяемая приёмка UI:**

- **AC-UI-004-01**: Для каждой строки таблицы сопоставлены её данные/действия и C IDs в плане/задачах; новый экран собирается из готовых элементов. Предметные последствия и ограничения строки видны пользователю, без копирования palette/spacing правил из 003.
- **AC-UI-004-02**: В утверждённом gate данного этапа проверены применимые normal/failure/boundary состояния, точная цель/ревизия и отсутствие запрещённого callback. Утрата readiness/authority не оставляет приватный draft или применимые поздние результаты; неизвестный исход записи не запускает повтор. N/A с причиной фиксируется в mapping.
- **AC-UI-004-03**: При UI-приёмке применяются матрица размеров/тем/масштабов, keyboard/focus/semantics и сохранение всех полей из 003. Существующий unit-only или иной ограниченный gate пакета не расширяется этой поправкой: непроведённые UI/native проверки записываются pending с их будущим gate, без заявления UI-готовности.
