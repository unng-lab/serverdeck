# Выпуск по Git-тегу

Действующий [контракт](contracts/versioning.md) и конституция4.1.0 требуют только
автоматическую публикацию GitHub Actions при push тега `vMAJOR.MINOR.PATCH`.
Ручная публикация и workflow_dispatch не используются.

1. Указать обычную версию без плюса в pubspec и добавить
   `release/notes/<version>.md`. Выполнить обязательные проверки до выпуска.
2. Закоммитить изменения, создать соответствующий тег (следующий `v0.1.1`) и
   отправить его в origin. Workflow `.github/workflows/release.yml` проверит
   совпадение версии, соберёт/audits полный установщик и автоматически выпустит
   GitHub Release с `ServerDeckSetup.exe` и `serverdeck-update-catalog.txt`.
3. Для работы подписи в repository Actions secrets должен быть
   `SERVERDECK_UPDATE_SIGNING_KEY`: исходный P256 PEM, соответствующий public policy.
   Секрет не печатается, не коммитится и не включается в artifacts. При его отсутствии
   workflow останавливается. Локальный оригинал хранится вне репозитория в
   LocalApplicationData/ServerDeckPublisher/keys с прежними ACL.

Первый новый catalog0.1.1 формируется без старых `0.1.0+N`: пользователь выбрал
чистую установку, обратная совместимость не поддерживается. Последующие выпуски
сохраняют неизменённые разрешённые records из previous signed catalog. Новая версия
всегда больше предыдущей, повторная публикация того же тега запрещена.

Локальный `tools/build-release.ps1` разрешён для проверки сборки/ресурсов;
`prepare-release.ps1` и signer остаются внутренними инструментами workflow, сами
ничего не загружают. Тесты публикации и пробные релизы не выполняются.

При сбое загрузки может остаться только непубличный draft; удалить его перед rerun.
Не изменять опубликованные assets: исправления выпускаются новым тегом.
