# Feature Specification: Регистрация существующего ПО

**Feature**: `007-software-adoption`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Осмотр существующей установки (Priority: P1)

Пользователь отдельно выбирает регистрацию и видит пакет, бинарную версию, службу и доступность приложения.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-007-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Осмотр существующей установки», **Then** Остановленная служба остаётся остановленной; несколько кластеров или нестандартная установка не выбираются автоматически.
2. **AC-007-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-007-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

2. **AC-007-3B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

## Requirements

### Scope и зависимости

Обязательные предшественники: [001](../001-service-foundation/spec.md), [002](../002-security-storage/spec.md), [003](../003-design-system/spec.md), [004](../004-server-workspace/spec.md), [006](../006-software-installation/spec.md).

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

### Место в сервисе и ответственность

**Расширяемые компоненты**: read-only SSH адаптеры и registry locald, UI регистрации.

Читает доказательства существующей установки, сохраняет локальную связь через тот же защищённый владелец состояния. Host-side installer не нужен; никакой запуск/repair/изменение ПО не добавляется в inspection.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-048**: Регистрация читает существующую установку и сохраняет локальную связь. Остановленная служба не запускается ради проверки; недостаток доказательств объясняется отдельно.
- **FR-007-LOCAL-01**: Исходная регистрация поддерживает package-managed PostgreSQL 18 с одним стандартным main cluster, local port 5432; ClickHouse 25.6+ с local port 9000 и стандартным data directory; Ubuntu 24.04 amd64/systemd. Actual patch version сохраняется без принудительного совпадения с fresh-install pin.
- **FR-007-LOCAL-02**: Inspection использует ограниченные read actions и уже подтверждённый SSH-доступ. Installer/helper не требуется; установка, изменение прав, запуск остановленной службы и repair запрещены. SQL metadata read может породить обычные server logs.
- **FR-007-LOCAL-03**: Доказательства package/binary/service должны согласоваться. Running service требует подтверждённой SQL server version; stopped допускает регистрацию как stopped с SQL skipped. Denied SQL не превращается в здоровое состояние.
- **FR-007-LOCAL-04**: Несколько PostgreSQL clusters, неоднозначный экземпляр, custom endpoint либо incomplete package state отклонены с причиной. Система не выбирает первый подходящий экземпляр.
- **FR-007-LOCAL-05**: Review действует пять минут, привязан к connection fields, fingerprint, credential revision и installation identity. Перед save повторяется inspection, сравнение и атомарное создание связи.
- **FR-007-LOCAL-06**: Одна связь на profile/program, повтор review confirmation идемпотентен. Active/unknown physical-host writer либо конкурентное изменение доступа блокируют регистрацию.
- **FR-007-LOCAL-07**: Registry хранится независимо от inventory; failure recheck сохраняет original identity/error. Инвентарь stale после пяти минут; старое состояние не подменяет current health.
- **FR-007-LOCAL-08**: Изменение подключения скрывает старую связь и инвалидирует reviews, пока пользователь явно не перепроверит цель. Удаление локальной связи/профиля не меняет удалённые пакеты, конфигурацию, permissions, службы и данные.
- **FR-007-LOCAL-09**: Disposable-server приёмка проверяет сохранность sentinel rows/config hashes и отсутствие write actions во всех successful/rejected inspections; на 360/390/1100 widths обеих тем inspection/registration достижимы максимум за три действия после выбора.

### Приёмка требований

Все перечисленные FR применимы к назначенному ниже этапу; AC соответствующего этапа проверяет весь этот состав, включая отрицательные случаи. Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

- **007.1**: FR-048; FR-007-LOCAL-01, FR-007-LOCAL-02, FR-007-LOCAL-03, FR-007-LOCAL-04; AC-007-1A/B/C.
- **007.2**: дополнительные требования ниже; FR-007-LOCAL-05, FR-007-LOCAL-06; AC-007-2A/B/C.
- **007.3**: дополнительные требования ниже; FR-007-LOCAL-07, FR-007-LOCAL-08, FR-007-LOCAL-09; AC-007-3A/B/C.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-007-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-007-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-007-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-007-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.

- **SC-007-LOCAL-05**: Пользователь достигает плана/осмотра максимум за три действия после выбора ПО; disposable приёмка обеих программ подтверждает фактическое состояние и сохранность соседних данных.

Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».
