# Feature Specification: Резервные копии и восстановление

**Feature**: `012-backup-recovery`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Разовая согласованная копия с пробным восстановлением (Priority: P1)

Пользователь получает достоверный обзор выбранного ресурса и выполняет только явно входящие в этот этап действия.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-012-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Разовая согласованная копия с пробным восстановлением», **Then** Фактический результат различает успешное чтение, пустоту, отказ прав, неполноту и несовместимость; цель и время наблюдения видны.
2. **AC-012-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-012-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 2 — Восстановление в отдельную цель (Priority: P2)

Пользователь выбирает поддержанный объект, читает последствия и подтверждает только объявленные изменения.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-012-2A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «Восстановление в отдельную цель», **Then** До записи проверены права и условия; результат подтверждён наблюдением, соседние ресурсы и данные сохранены.
2. **AC-012-2B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-012-2C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 3 — Расписание и политика хранения (Priority: P2)

Пользователь настраивает серверное расписание копирования данных выбранного приложения/ресурса в выбранное хранилище. После подтверждённого включения сервер выполняет его без открытого клиента и без работающего locald; клиент впоследствии получает фактические результаты.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-012-3A Given** подготовленный серверный runtime и проверенная схема копирования, **When** пользователь подтверждает расписание и политику хранения, закрывает все окна и завершает locald либо выключает клиентское устройство, **Then** сервер самостоятельно выполняет следующие запуски; повторное открытие клиента читает серверные идентичности запусков, время, состав и проверяемые результаты. Перезапуск сервера сохраняет расписание; пропущенные во время остановки моменты не создают очередь копий и не запускаются сразу после старта. Следующий запуск происходит в следующий обычный момент. Политика не удаляет последнюю подтверждённую пригодную копию.
2. **AC-012-3B Given** нет подготовленного runtime, разрешения, доступа к источнику/хранилищу либо условия стали недействительны, **When** настраивается расписание или наступает очередной момент, **Then** неподдержанная настройка блокируется без скрытой установки; существующее расписание не выполняет небезопасное действие и фиксирует причину пропуска/ошибки. В отдельном варианте отзыв разрешения на сервере подтверждён повторным чтением: новые запуски не начинаются, уже активный запуск остаётся видимым и отменяется только отдельным действием по правилам заданий. Изменение local SSH credentials/доверия лишь прекращает управление по 001 и не объявляет удалённое расписание остановленным.
3. **AC-012-3C Given** потеря ответа после изменения расписания, конкурирующая правка, отключённый клиент либо занятый/unknown writer на хосте, **When** пользователь возвращается или наступает очередной момент, **Then** повторный запрос сверяет прежнюю идентичность и ревизию без второго расписания, конфликт правок виден, следующий запуск не пересекает конфликтующую запись и не повторяет unknown попытку. При недоступном сервере UI показывает прежнее наблюдение и неподтверждённое состояние, а не успех отключения. Проверены пропуск при остановленном сервере, смена часового пояса и переходы летнего времени: повторённый момент выполняется один раз, отсутствующий момент пропускается без догоняющего запуска.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

### Место в сервисе и ответственность

**Расширяемые компоненты**: управление расписанием и метаданные locald, серверный планировщик/ограниченный executor и поддержанные инструменты хоста, выбранное хранилище копий.

Копируются выбранные данные управляемого сервера, а не данные локального клиента. Копии и восстановленные данные находятся в явно выбранной цели, не в основной БД. locald владеет защищёнными metadata/key references и заданиями изменения настройки; само расписание и результаты фоновых запусков принадлежат серверному runtime. Закрытие клиента, завершение locald и отключение клиентского устройства не прекращают установленное расписание. Не вводится общий непрерывный сборщик или полное DR машины.

### Серверное расписание: полномочия и жизненный цикл

- Установка, изменение, отключение и отзыв расписания — подтверждаемые серверные изменения через coordinator 001 и executor с gates 006/010. Первоначальный review действует пять минут и разрешает только установку показанной конфигурации; после установки будущие моменты исполняются по отдельному долговечному серверному разрешению, а не по истёкшему client review.
- Разрешение ограничено идентичностью сервера, источником, хранилищем, способом согласованности, версией поддержанного рецепта, расписанием и политикой хранения. Оно допускает только объявленное копирование и разрешённое удаление копий по политике; восстановление, другой источник/хранилище или произвольные команды не разрешены. Изменение этого состава требует нового review, согласия и серверной ревизии. Фоновый запуск не расширяет разрешение и не обновляет рецепт автоматически.
- Сервер имеет отдельно подготовленные ограниченные права и credentials к хранилищу; SSH credentials клиента туда не передаются. До каждого запуска проверяются действующее серверное разрешение, фактическая идентичность/ревизия конфигурации, доступ, ёмкость и условия согласованности. Их отказ фиксирует ошибку/пропуск без открытого fallback, скрытого grant или копирования другого объекта. Runtime и credentials provisioned администратором; неизвестная подготовка блокирует настройку.
- Локальное изменение SSH-доступа, отзыв host trust либо удаление профиля не отзывают уже установленное серверное разрешение. Клиент заранее объясняет эту границу; для остановки нужно подтверждённо отключить расписание на сервере либо отозвать его серверное разрешение. Удаление локального профиля не удаляет серверную конфигурацию/копии. При потере доступа UI не обещает удалённый отзыв; администратор может выполнить его на сервере независимо от клиента.
- Отключение/отзыв, подтверждённые сервером, запрещают новые запуски с этой ревизией. Уже активное задание не объявляется отменённым: его состояние и отдельная отмена подчиняются правилам 001/006. Отложенные запуски при выключенном сервере, отсутствующий момент при переходе времени и момент при конфликтующем active/unknown writer пропускаются; очередь догоняющих записей не создаётся. При переводе часов назад один логический момент с той же идентичностью не выполняется второй раз. После возобновления используется следующий обычный момент в сохранённом часовом поясе.
- Серверные расписание/разрешение и квитанции запусков долговечны при перезапуске хоста. Идентичность расписания, ревизия и логический момент дают одну попытку; повторы чтения/потеря ответа не создают второго расписания или эффекта. Для любого writer действуют идентичность физического хоста, удалённая блокировка и reconciliation из 001/006; unknown не снимается из-за нового момента. Фоновый запуск имеет собственную серверную квитанцию и не притворяется незавершённым client job, требующим живого locald.
- При подключении locald читает конфигурацию, ближайший доступный момент и результаты с сервера. Когда сервер недоступен, локальные метаданные остаются последним наблюдением с временем и stale/unknown, не доказательством текущего исполнения. Расписание само по себе не удерживает locald после закрытия последнего окна; его настройка и локальное отслеживание active/unknown управляющего задания сохраняют lifecycle 001.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-108**: План копирования определяет набор, место хранения, согласование с приложением и исключения. Доступ к месту хранения не становится открытым параметром плана.
- **FR-109**: Копия содержит состав, время, объём и результат проверки доступности. Обещание согласованности соответствует выполненной проверке, а не факту создания файла.
- **FR-110**: Расписание выполняется на управляемом сервере независимо от клиента/locald. Оно показывает часовой пояс, следующий доступный момент, пропущенные моменты, последнее успешное копирование и последнюю ошибку. Действуют серверное ограниченное разрешение, правила отзыва, отсутствие автоматического догоняющего запуска, проверка условий и долговечная идентичность попытки из раздела «Серверное расписание: полномочия и жизненный цикл»; AC-012-3A/B/C проверяют этот полный состав.
- **FR-111**: Политика хранения показывает сохраняемые и удаляемые копии. Последняя подтверждённая пригодная копия не удаляется автоматически.
- **FR-112**: Восстановление требует выбранной копии и цели, списка заменяемых данных и возможности сохранить текущее состояние. Открытие списка копий не начинает восстановление.
- **FR-113**: Пробное восстановление в отдельную цель проверяет состав и читаемость, а работоспособность приложения — только если такая гарантия заявлена для этого типа копии.
- **FR-114**: Недоступный ключ, повреждение и несовместимость блокируют восстановление без удаления исходных данных. Полное аварийное восстановление сервера требует отдельной спецификации.
- **FR-012-LOCAL-01**: Начальная схема резервирования имеет проверенный destination, доступ, ёмкость, consistency mode и ссылку защищённого ключа до копирования. Этот preflight входит сюда и не зависит от будущего UI управления дисками 015.
- **FR-012-LOCAL-02**: Каждая новая схема копирования проходит пробное восстановление в независимую цель до merge этапа копирования. Создание копии без restore test не закрывает приёмку первого этапа; во втором развивается пользовательский интерфейс восстановления в отдельную цель. Перезапись исходной работающей установки в этот этап не входит.

### Приёмка требований

Все перечисленные FR применимы к назначенному ниже этапу; AC соответствующего этапа проверяет весь этот состав, включая отрицательные случаи. Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

- **012.1**: FR-108, FR-109, FR-113, FR-114; FR-012-LOCAL-01, FR-012-LOCAL-02; AC-012-1A/B/C.
- **012.2**: FR-112; AC-012-2A/B/C.
- **012.3**: FR-110, FR-111; AC-012-3A/B/C.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-012-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-012-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-012-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-012-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.


Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».
