# Feature Specification: Безопасность и чувствительная диагностика

**Feature**: `018-security-controls`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — События и версионированные политики (Priority: P1)

Пользователь читает события и результат проверки выбранной версии политики.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-018-1A Given** поддержанная цель и выполненные условия, **When** пользователь проходит «События и версионированные политики», **Then** Нарушение объяснено с доказательством; проверка политики ничего не исправляет автоматически.
2. **AC-018-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-018-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 3 — Запись сессий и диагностика сбоев (Priority: P2)

2. **AC-018-3B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

## Requirements

### Scope и зависимости

Обязательные предшественники: [001](../001-service-foundation/spec.md), [009](../009-observability/spec.md), [011](../011-access-management/spec.md), [013](../013-files-diagnostics/spec.md), [016](../016-network-management/spec.md), [017](../017-compute-management/spec.md).

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

Этапы выполняются по порядку. Один MR — один этап либо его согласованная меньшая часть; число спецификаций от этого не растёт. Сценарии, проверки и supporting assets одного этапа остаются вместе. Нельзя мерджить все три этапа одним большим MR. Неизвестная совместимость нового варианта блокирует его включение, но не уже принятые независимые функции.

### Место в сервисе и ответственность

**Расширяемые компоненты**: сбор security evidence и policy evaluation locald, отдельно разрешённый executor исправлений.

Проверка политики read-only; remediation — отдельное согласие/job. Чувствительный сбор объявляет место, права, срок и lifecycle; backend ничего не получает автоматически.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

- **FR-117**: Событие безопасности, объяснение и предлагаемое исправление различаются. Просмотр события сам не применяет исправление и не отключает защиту.
- **FR-118**: Проверка соответствия называет политику и версию, область, успешные, нарушенные и непроверенные правила. Непроверенное правило не включается в процент успешных.
- **FR-119**: Исправление нарушения и смена режима защиты имеют отдельный план и повторную проверку. Кнопка сбора диагностики не даёт согласие на эти действия.
- **FR-120**: Запись административной сессии и диагностика сбоев ядра включаются отдельно с указанной областью, доступом, местом хранения и сроком хранения данных.

### Приёмка требований

Все перечисленные FR применимы к назначенному ниже этапу; AC соответствующего этапа проверяет весь этот состав, включая отрицательные случаи. Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

- **018.1**: FR-117, FR-118; AC-018-1A/B/C.
- **018.2**: FR-119; AC-018-2A/B/C.
- **018.3**: FR-120; AC-018-3A/B/C.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-018-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-018-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-018-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-018-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.


Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».


## Дизайн и функциональность одного пакета — 2026-10-28

Это актуальное распределение работы по прямому указанию пользователя: сначала 003 переносит точный дизайн базового клиента с существующими функциями; затем этот существующий пакет реализует свои функции **вместе с их дизайном**. Отдельный Core, новая спецификация для того же модуля и перенос реализации всех сервисов в 003 не вводятся. Полная [карта 98 ID](../design-delivery.md) сохраняет обязательство всех экранов; [канонический реестр](../../docs/design/screens.json) и [атлас](../../docs/design/ServerDeck-design.html) задают поля, вкладки, действия и композиции.

Основные будущие ID этого пакета: `76-security-events`, `77-security-policy`, `78-security-remediation`, `79-sensitive-diagnostics`. Связанные ID и общие действия: `76-security-events`, `77-security-policy`, `78-security-remediation`, `79-sensitive-diagnostics`. Shared ID не даёт права дублировать владельца соседнего сервиса.

До начала соответствующих implementation tasks собственные Plan, модели/контракты и Tasks этого пакета обязаны закрепить цепочку requirement→decision→contract→production UI/service→task→acceptance для всех назначенных полей, вкладок и действий: источник/цель/время/качество данных, реальные обработчики, права/credentials/trust, конкуренцию/CAS/idempotency, deadlines/retry/unknown reconciliation, prerequisites, лимиты/defaults и миграции/состав выпуска. Каждый этап включает каноническую визуальную композицию обеих тем/четырёх frames/100% и 200% текста, нормальные и отказные состояния и meaningful unit/widget проверки тех же production-компонентов. Generic unsupported, demo rows/results и test-only gallery отсутствующую функцию не закрывают.

Предложенный набор runtime/provider choices **не принят пользователем**; произвольные defaults поставщиков, policy rules и условий подписок этим текстом не вводятся. Нужные обязательные решения фиксируются в owning Plan до затронутых задач. **Готовность к реализации дополненного scope пока не установлена:** одного Specify и этой передачи недостаточно. Прежние FR/AC, этапы и выполненная история не переписаны; новая готовность требует собственных обязательных артефактов, checks и независимого review/fix loop. Текущие проверки ограничены static/unit/widget; native/integration workload не разрешён этим разделом, не запускается и не становится успешным по unit-результату. Отложенная квалификация учитывается отдельно от реализации и дизайна.
