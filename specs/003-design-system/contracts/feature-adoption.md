# Применение готовых UI-компонентов в профильных пакетах

**Дата**: 2026-11-01. **Scope**: нормативная UI-поправка к 001–021, кроме самого 003. Она связывает объявленные пользовательские композиции с [C01–C30](../component-library.md) и [контрактом библиотеки](component-library.md). Готовность библиотеки не означает реализацию сервиса или приёмку его будущих экранов.

## Источники требований и границы

1. Предметные данные, действия, полномочия, версии, лимиты, сроки и recovery определяет соответствующая feature spec и действующий контракт 001. Эта поправка не добавляет действий, API, прав или автоматических повторов. Она не пересматривает принятый direct SSH/embedded lifecycle.
2. C ID обозначает готовое семейство. Обязателен применимый вариант из таблицы feature spec; наличие варианта в библиотеке не требует включать все возможности элемента. Например, C06 не включает selection или sort без предметного требования, C08 не создаёт paging API, C24 не добавляет remote write, C28 не становится планировщиком. Новый batch action не возникает из наличия C29.
3. Общие визуальные правила, tokens, targets, layouts и состояния определены в 003 и не копируются в feature spec. Конкретный блок экрана собирается из библиотечных элементов; новые самостоятельные реализации того же поведения не допускаются. Стандартные Material controls с BrandTheme допустимы по контракту C01–C30.
4. Недостающий вариант оформляется дополнением существующего семейства в 003: назначение, входы/события, применимые состояния/N/A, пример и проверки; после его приёмки подключается feature adapter. Эта поправка не разрешает обходить недостающий вариант локальной копией разметки. Уникальное предметное содержимое остаётся в adapter своего раздела.

## Владельцы данных и событий

Runtime-композиции располагаются в feature presentation adapters клиента. Действующий engine/gateway остаётся владельцем storage, SSH, trust/credentials, authorization, jobs и recovery; контроллер feature передаёт готовые projections и допустимые callbacks в Deck/Material. Пути публичного импорта и текущих adapters перечислены в [инструкции](../../../docs/design/components/README.md) и [реестре](../../../docs/design/components/registry.json). Для нового раздела имена локальных Dart-классов/файлов — деталь реализации; новая система владельцев/протоколов этой поправкой не вводится.

Общий элемент сообщает намерение через свой существующий callback (выбор ID, sort, page/query, validate/submit/cancel, copy разрешённого значения). Feature owner проверяет актуальные identity/revision/readiness и вызывает существующий сервисный контракт; разрешённость не выводится из видимости или enabled кнопки. Внутри элементов нет I/O, собственного polling, credential storage или service retry. Синтетические owners из `tool/component_catalog/` и HTML не импортируются в runtime.

Коллекции получают стабильные ID и переданную порцию. Сортировка/фильтрация/selection/paging opt-in, принадлежат owner и сохраняют все поля/действия в узкой композиции. Смена query/page size сбрасывает страницу по контракту C08; неизвестное total не заменяется вычисленным из одной порции. Допустимые page sizes и service bounds берутся из feature/gateway, а не из демонстрационных defaults каталога. Конфликтующие экземпляры с одинаковым именем различаются ID/контекстом.

Формы получают owner controller/validator и current draft. Theme/resize сохраняют введённое, выбранную цель, query/selection и фокус в пределах того же owner. Смена identity, отзыв полномочий и потеря readiness прекращают использование приватного контекста по действующим правилам 001; late completion не возвращает отозванные данные и не подтверждает эффект. Секретные поля скрыты; обычные C18/C26 copy/export не получают secrets. Возможность C26 редактировать текст не разрешает выполнить его как команду.

Pending блокирует повтор той же отправки, сохраняя независимую допустимую навигацию. Unknown после возможного эффекта показывает причину и только существующий путь установления исхода; component callback не создаёт новый job и не обходит lock. План C24 сохраняет видимые цель, эффекты, scope/ограничения и срок вне необязательного expander; отмена/Escape не дают согласия. При изменении привязки/срока согласие теряет силу по сервисному контракту.

## Состояния и проверяемое соответствие

Каждая композиция показывает только применимые состояния: первое чтение/loading, успешная пустота, query no-results, error, unsupported/denied/unavailable, прежние stale/partial данные и unknown. Различаются ошибка обновления и отсутствие прежних данных; previous snapshot не заменяется фиктивным. Источник/время/качество принадлежат наблюдению. Null/unknown не отображаются успехом или нулём, gap не дорисовывается. Причина недоступности и допустимый следующий шаг доступны текстом, а не только цветом/tooltip.

Строка mapping в плане/задаче содержит: композицию из feature UI-таблицы → C ID/вариант → семантические поля/действия feature owner → state/N/A → AC-UI-xxx критерий. Это трассировка UI в существующую feature, не отдельное проектирование её backend. Для трёх уже версионируемых plan/tasks (001/006/021) добавлены очереди UI-интеграции; для остальных UI-раздел spec нормативен при создании/уточнении их plan/tasks. Неопубликованные планы параллельных работ не включаются в эту поправку.

UI-приёмка использует матрицу 003: обе темы × 1100×760, 800×600, 390×800, 360×800 × 100%/200%, keyboard/focus/semantics/reduced motion и применимые long/null/error/concurrency/privacy границы. Промежуточные размеры не теряют поля и действия; готовый атлас не заменяет тестов feature callbacks. Для security/mutation сценариев проверяются и разрешённое действие, и отсутствие запрещённого эффекта, включая double submit/cancel/identity retirement/late result.

Текущий разрешённый validation scope каждого этапа сохраняется. При unit-only режиме проверяются доступные model/owner решения; widget/visual/native проверки этой поправкой не запускаются и не выдаются за пройденные. Соответствующий UI gate остаётся pending до разрешённой UI-квалификации; код/UI не объявляются готовыми только по ссылке на принятый каталог. После фактической UI-реализации обязательны применимые проверки AGENTS.md и independent review/fix loop. Никакие старые task/evidence записи не стираются.
