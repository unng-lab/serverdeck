# Feature Specification: Аудит защиты секретов доступа и восстановление

**Feature**: `002-security-storage`
**Created**: 2026-10-10
**Status**: Specify — требования для новой реализации; реализация не начата этим документом.

## User Scenarios & Testing

### User Story 1 — Аудит защиты секретов доступа (Priority: P1)

Пользователь работает с сервисом 001. Проверяется полный охват защиты приватных SSH-ключей, паролей и passphrase, атомарность замены целого набора доступа и отсутствие открытых копий секретов. Обычные поля профилей, настройки, наблюдения, история и индексы сохраняются без шифрования приложения. Первоначальная защита секретов и bootstrap уже обязательны в 001.

**Why this priority**: Это первый самостоятельный результат направления.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-001-1A Given** поддержанная среда и сохранённый доступ, **When** выполняется аудит защиты секретов, **Then** после перезапуска того же пользователя доступ восстанавливается; другой пользователь ОС и копия файлов без полномочий владельца не раскрывают пароль, приватный ключ и passphrase. Адрес, имя и другие обычные метаданные допускаются в открытом виде в базе.
2. **AC-001-1B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-001-1C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 2 — Привязки, целостность и recovery секретов (Priority: P2)

Пользователь получает понятную блокировку при отказе защиты ОС, повреждении credential blob, нарушении привязки или неизвестном формате. Исходные файлы сохраняются для разбора; данные не сбрасываются автоматически.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-001-2A Given** повреждённый blob, привязка или отказ ОС, **When** запрошен доступ к пространству, **Then** обычные запросы блокируются, исходные файлы сохраняются; отказ не создаёт нового доступа, пустой базы или открытой копии секрета.
2. **AC-001-2B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-001-2C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### User Story 3 — Расширенная платформенная приёмка (Priority: P2)

Пользователь проверяет доступ после перезагрузки и понимает ограничения переноса на другой компьютер.

**Why this priority**: Это отдельное развитие уже принятого результата без расширения предыдущего MR.

**Independent Test**: Подготовленный совместимый стенд, принятые зависимости и отдельный отказной вариант; будущие этапы не требуются. Для задания нужна изолированная цель, для backend — test account; реальные пользовательские серверы не используются автоматически.

**Acceptance Scenarios**:

1. **AC-001-3A Given** сохранённые секреты доступа, **When** выполняется платформенная приёмка, **Then** на Windows проверены reboot, другой пользователь, повреждение blob и отказ защиты ОС; копирование базы на другой компьютер не считается переносом секретов, их расшифровка без доступного контекста защиты владельца не обещается.
2. **AC-001-3B Given** отсутствие обязательных прав/доверия либо неподдержанная среда, **When** запрошен этот сценарий, **Then** причина и допустимое следующее действие показаны; запрещённые эффекты не выполняются.
3. **AC-001-3C Given** прерывание запроса, **When** пользователь возвращается к прежнему объекту, **Then** исходный контекст и сохранённые данные остаются; неподтверждённый результат явно неизвестен, запись не повторяется автоматически.

### Edge Cases

- Изменение host key, credential revision либо connection fields после просмотра: прежнее approval недействительно; отдельная проверка цели.
- Отказ защищённого хранения, повреждение, неизвестный формат: fail closed без удаления или открытой копии.
- Потеря сети, частичный результат, пустой successful result и отказ прав различаются; данные другого сервера не подставляются.
- Повтор действия и конкурентный доступ: идемпотентный результат либо явный конфликт, без двойного эффекта.
- Чрезмерный объём, длинные строки и отсутствующий компонент: предел и понятное ограничение без скрытой установки.

### Scope и зависимости

Обязательные предшественники: [001](../001-service-foundation/spec.md).

Каждый пакет описывает требования к новой реализации. Старые выполненные задачи, планы, контракты, evidence и MR не дают ему статуса готовности и не являются обязательными зависимостями. Переиспользование кода допустимо только после проверки против новых требований.

Переход — **hard cutover**: первый запуск пустой, отдельная область данных и доверия; нет импорта старого ServerDeck, migration bridge, совместимости с его API или fallback на старый сервис. Эта политика не разрешает удалять данные старого сервиса или данные приложений на управляемых серверах.

Ко всем действиям применяются [общие бизнес-требования](../business-requirements.md) и [основа сервиса 001](../001-service-foundation/spec.md): один locald и владелец состояния, авторизованный Local API, защита до первой записи, доверие, честные наблюдения и устойчивые планы/задания. Чтение не даёт права изменять сервер. 002 расширяет защищённое хранение этой основы. NetBird и его клиенты защищены. Unknown/unsupported/denied/stale/dropped/incomplete не заменяются успехом или нулём. Для серверной записи обязательны FR-035–044; для чтения — наблюдение с источником/временем, лимиты и отсутствие скрытых изменений.

Это **Specify, этап 1**. Готовность к реализации не заявлена: до Tasks обязательны собственные Plan, модели/контракты, platform/runtime prerequisites, лимиты, failure semantics и приёмка выбранного этапа. Детали реализации здесь не наследуются от старого кода.

### Место в сервисе и ответственность

**Расширяемые компоненты**: locald, защищённое хранилище и provider защиты ОС.

Основной владелец данных уже создан в 001. Этот пакет расширяет аудит защиты секретов доступа, проверку их привязок, recovery и платформенные failure gates; UI получает безопасный статус, но не сохранённый секрет. SSH, executor и backend для проверки хранения не нужны.

Данные и жизненный цикл подчиняются 001; новый модуль не создаёт параллельный основной store, прямой UI→SSH канал или обход coordinator. Перед своим этапом Plan фиксирует конкретные интерфейсы этого расширения; сама основа уже существует по gate 001.

### Functional Requirements

FR-121–123 принадлежат 001 и действуют до первой записи. Этот пакет не переносит их включение на более поздний срок; он расширяет работающий механизм защиты и проверяет его против полной модели угроз.

- **FR-001-LOCAL-01**: Секреты доступа включают пароль SSH, полный приватный SSH-ключ и passphrase. Они сохраняются средствами ОС текущего пользователя; обычный профиль хранит непрозрачную ссылку. Сохранение, замена и удаление относятся к целому набору одного доступа, без частичного обновления. Технические токены локальной авторизации и токены других функций также не сохраняются открыто; их lifecycle определяется контрактом соответствующей функции.
- **FR-001-LOCAL-02**: Имена, адреса, порты, SSH-пользователи, теги, fingerprints, ссылки, настройки, наблюдения, регистрации, планы, задания, события, даты и поисковые индексы — обычные данные без шифрования приложения. Права ОС ограничивают доступ к рабочим файлам. Новое поле, содержащее секрет доступа, обязано использовать credentials provider; новые метаданные не требуют шифрования по умолчанию.
- **FR-001-LOCAL-03**: Защита секретов принадлежит текущему пользователю ОС и работает офлайн без дополнительного пароля приложения. Общий ключ шифрования базы не создаётся. Сохранённые секреты не передаются обычному API чтения, backend, экспорту или диагностике.
- **FR-001-LOCAL-04**: Чтение, поиск, уникальность, порядок событий и блокировки используют обычные записи базы. Атомарное сохранение охватывает профиль, ссылку, защищённый набор доступа и результат операции. Отказ защиты или записи не отображается как успешное сохранение.
- **FR-001-LOCAL-05**: Повреждение защищённого blob, подмена его владельца или перенос между профилями должны обнаруживаться до использования секрета. Отсутствующий blob, dangling reference, дублированные идентификаторы и несогласованные ревизии блокируют доступ. Криптографическая защита обычных метаданных и обнаружение согласованной подмены либо отката всей базы не обещаются.
- **FR-001-LOCAL-06**: Модель угроз для секретов: копия файлов без полномочий владельца, другой пользователь ОС, повреждение и нарушение привязки blob. Обычные метаданные читаемы из скопированной базы. Активный вредоносный процесс с полномочиями вошедшего пользователя, память, SSD remanence и согласованная подмена/откат всей базы вне гарантий.
- **FR-001-LOCAL-07**: Секреты допустимы временно в памяти для ввода и разрешённого действия; обычное чтение профиля их не возвращает. Backup, temporary files, логи и стандартный экспорт не создают открытых копий секретов. Обычные метаданные могут сохраняться без шифрования и включаться в явно выбранный пользователем экспорт.
- **FR-001-LOCAL-08**: Недоступность контекста защиты ОС или повреждение credential blob блокируют обычные запросы без сброса и подмены доступа. Пользователь может явно создать отдельное новое пустое пространство после предупреждения; старое сохраняется. Восстановление секретов без доступной защиты владельца не обещается; обычные метаданные не нуждаются в ключе расшифровки.
- **FR-001-LOCAL-09**: Перед первой эксплуатацией Windows проверяются сохранение доступа после reboot, запрет другому пользователю, отсутствие открытых маркеров пароля/приватного ключа/passphrase в постоянных файлах, отказ защиты и повреждение blob. Читаемость обычных метаданных в базе не считается утечкой секрета. Остальные платформы требуют собственной приёмки.
- **FR-001-LOCAL-10**: Hard cutover не читает и не импортирует старые хранилища/credential targets/демонстрационные профили. Обновления новой реализации сохраняют её данные, ссылки и защищённые секреты; не заменяют их автоматически новым пространством.

### Приёмка требований

Все перечисленные FR применимы к назначенному ниже этапу; AC соответствующего этапа проверяет весь этот состав, включая отрицательные случаи. Общие защитные требования действуют до первого использования, а не откладываются в последний этап. В Plan каждая строка раскрывается в проверки и задачи; отметка Specify не заменяет их исполнения.

- **002.2**: FR-001-LOCAL-05, FR-001-LOCAL-06, FR-001-LOCAL-08; AC-001-2A, AC-001-2B, AC-001-2C.

Дополнительные LOCAL требования, указывающие конкретный сценарий (создание, отказ, обновление, регистрация и т. п.), принимаются в этапе с этим сценарием; запреты/защита действуют во всех этапах. Зависимые этапы не могут включить функцию до выполнения её полного gate.

### Key Entities

- **Цель**: профиль и подтверждённая идентичность сервера либо явно выбранное локальное пространство/клиентская платформа; не меняется при навигации.
- **Наблюдение**: источник, время, значение, полнота, ошибка и состояние актуальности; отсутствие сведений не равно отрицательному факту.
- **Поддержанная возможность**: среда, версия, права, подготовка и проверенный сценарий; неподтверждённая матрица не разрешает исполнение.
- **План и результат**: неизменные входы, эффекты, согласие, этапы и проверяемый итог; серверные записи используют общую модель 001.

## Success Criteria

### Measurable Outcomes

- **SC-001-LOCAL-01**: Все AC трёх этапов проходят на совместимом стенде и на перечисленных отказных вариантах; результат фиксируется отдельно от планируемой проверки.
- **SC-001-LOCAL-02**: Во всех сценариях отказа нет скрытых серверных эффектов, подмены цели, plaintext fallback или автоматического повтора неизвестной записи.
- **SC-001-LOCAL-03**: Сценарии доступны в обеих темах при 1100×760, 800×600, 360×800 и 390×800, без перекрытия основных действий; информация графиков доступна текстом.
- **SC-001-LOCAL-04**: После каждого этапа проходят ранее принятые сценарии новой реализации; merge требует проверки применимых требований этого этапа и независимого ревью.

- **SC-001-LOCAL-05**: Синтетические маркеры пароля, приватного ключа и passphrase отсутствуют в открытом виде в постоянных файлах, индексах, логах и стандартном экспорте; обычные поля профиля сохраняются без шифрования приложения. Отказ защиты и повреждение блокируют обычные запросы без reset; нативные Windows reboot и other-user проверки выполнены.

Дополнительно применяются относящиеся к сценарию SC-001–018 [общих требований](../business-requirements.md), включая нулевую утечку секретов, отсутствие двойных эффектов и независимую платформенную приёмку.

## Assumptions

- Создаётся новая реализация; прежний код не считается принятым или обязательным. Старые MR просмотрены как источник пожеланий, но их merge, task checkmarks и evidence не служат gate.
- Windows — первая платформа SSH; управляемые изменения сначала Ubuntu 24.04 amd64/systemd. Остальные среды объявляются по функции и только после собственной проверки.
- Техническая базовая линия проекта находится в конституции; выбор новых контрактов/моделей и исполнения выполняется через Plan, без неявного копирования прежней архитектуры конкретного пакета.
- Проверки используют synthetic data и disposable targets. Документы не разрешают соединяться с реальными профилями, менять серверы, публиковать пакеты или объединять MR.
- После первого cutover будущие обновления новой реализации обязаны сохранять уже созданные в ней данные; active/unknown задания не очищаются как «история».


## Дизайн и функциональность одного пакета — 2026-10-28

Полная [карта 98 ID](../design-delivery.md) сохраняет обязательство всех экранов; [канонический реестр](../../docs/design/screens.json) и [атлас](../../docs/design/ServerDeck-design.html) задают поля, вкладки, действия и композиции.

Основные будущие ID этого пакета: `89-new-workspace-recovery`. Связанные ID и общие действия: `89-new-workspace-recovery`. Shared ID не даёт права дублировать владельца соседнего сервиса.

До начала соответствующих implementation tasks собственные Plan, модели/контракты и Tasks этого пакета обязаны закрепить цепочку requirement→decision→contract→production UI/service→task→acceptance для всех назначенных полей, вкладок и действий: источник/цель/время/качество данных, реальные обработчики, права/credentials/trust, конкуренцию/CAS/idempotency, deadlines/retry/unknown reconciliation, prerequisites, лимиты/defaults и миграции/состав выпуска. Каждый этап включает каноническую визуальную композицию обеих тем/четырёх frames/100% и 200% текста, нормальные и отказные состояния и meaningful unit/widget проверки тех же production-компонентов. Generic unsupported, demo rows/results и test-only gallery отсутствующую функцию не закрывают.

Предложенный набор runtime/provider choices **не принят пользователем**; произвольные defaults поставщиков, policy rules и условий подписок этим текстом не вводятся. Нужные обязательные решения фиксируются в owning Plan до затронутых задач. **Готовность к реализации дополненного scope пока не установлена:** одного Specify и этой передачи недостаточно. Прежние FR/AC, этапы и выполненная история не переписаны; новая готовность требует собственных обязательных артефактов, checks и независимого review/fix loop. Текущие проверки ограничены static/unit/widget; native/integration workload не разрешён этим разделом, не запускается и не становится успешным по unit-результату. Отложенная квалификация учитывается отдельно от реализации и дизайна.
