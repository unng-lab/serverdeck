# ServerDeck Constitution

## Core Principles

### I. Публичные репозитории и границы компонентов

Клиент ServerDeck на Flutter/Dart и отдельный серверный backend развиваются
в публичных репозиториях. Код, тесты, документация и артефакты MUST учитывать
публичность исходников. Изменения клиента и backend допустимы в рамках задачи
пользователя; ограничение записи только клиентским репозиторием не применяется.

Локальные SSH-инвентарь и журнал MUST работать без облачного backend или API
провайдера. Flutter UI, локальный Dart-сервис и отдельный backend MUST иметь
описанные обязанности и границы. UI MUST обращаться к данным локального сервиса
через его контракт. Каждая функция MUST указывать компоненты и место реализации.

### II. Минимальные полномочия и явное согласие

Адаптеры чтения MUST NOT изменять удалённый хост. Установка, удаление и действия
со службами MUST иметь отдельный путь исполнения с явным согласием на цель
и изменения. Просмотр, подключение и синхронизация MUST NOT разрешать запись.
После неопределённой записи запрещены автоматические повтор, сброс, удаление
и downgrade до установления безопасного состояния.

NetBird и его клиенты MUST оставаться защищёнными от изменений, пока пользователь
прямо не изменит эту границу. Проверки MUST использовать изолированные fixtures;
реальные серверы MUST NOT использоваться для тестов без явного разрешения.

### III. Защита credentials, приватных данных и доверия

Пароли, SSH-ключи, токены и ключи шифрования MUST храниться под защитой ОС
с ограничением доступа. Git, preferences, синхронизация, обычная БД,
диагностика и публичные артефакты MUST NOT содержать открытые секреты.
Приватные данные хостов MUST исключаться из публичных материалов;
fixtures MUST использовать синтетические данные.

Секреты доступа — приватные SSH-ключи, пароли и passphrase — MUST защищаться
средствами ОС. Обычные метаданные профилей, настройки, наблюдения, история
и индексы MUST храниться без шифрования приложения с ограничением доступа
по правам ОС. Конфиденциальность скопированной базы метаданных не обещается.
Спецификация MUST определять охват защиты, доступ к ключам,
восстановление и ограничения. Для новой реализации действует hard cutover:
импорт старых БД и секретов, миграция старого сервиса и plaintext bridge исключены.
Будущие обновления новой реализации MUST сохранять её собственные данные.
Недоступность защиты MUST блокировать доступ
с сохранением данных, без plaintext fallback, скрытого сброса и замены ключа.

Неизвестный SSH host key MUST проходить явное подтверждение; изменённый ключ
MUST блокировать соединение до восстановления доверия. Интерфейсы доступа
MUST определять выдачу, проверку, отзыв и сроки доверия, где это применимо.
Backend MUST самостоятельно проверять полномочия. CI credentials и ключи подписи
MUST поступать из защищённых хранилищ с минимальными правами, вне публичных логов.

### IV. Достоверные наблюдения и ограниченные ресурсы

Unknown, unsupported, denied, stale, dropped и incomplete MUST отличаться
от успешного пустого результата или нуля в контрактах, UI и диагностике.
Тестовые данные MUST NOT подменять реальные наблюдения в обычном запуске.
Очереди, история, polling и внешние запросы MUST иметь описанные defaults,
пределы, сроки, отмену и поведение при превышении. Ошибки MUST содержать
безопасную категорию и следующий шаг без раскрытия приватных значений.

### V. Надёжные операции и совместимые контракты

До реальных заданий MUST быть определены неизменяемые входы, версия рецепта,
один писатель на хост, идемпотентность, порядок событий, отмена и восстановление
после сбоя. Неопределённый исход MUST сохранять защиту от конфликтующей записи
до reconciliation. Успех Ansible MUST NOT заменять проверку требуемых версии,
состояния службы и работоспособности результата.

Межкомпонентные интерфейсы MUST описывать протокол, схемы, версии и ошибки.
Изменения контрактов и хранения внутри новой реализации MUST определять
совместимость и миграции. Совместимость с заменяемым сервисом не требуется.
Несовместимые версии MUST отклоняться явно, без скрытой потери данных.
Контракты MUST определять конкуренцию, повторы и восстановление, где применимо.

### VI. Полнота спецификаций и новая исходная точка

Каждая обязательная функция MUST иметь прослеживаемую цепочку:
требование → проектное решение → контракт → задача → критерий приёмки.
Компоненты, зависимости, требования к среде и состав поставки MUST определяться
до зависящих от них задач. TBD, draft и будущая задача не заменяют решение.

Набор спецификаций пересоздаётся под новую реализацию по явному указанию
пользователя. Старые планы, контракты, задачи и результаты не являются её
основанием; отдельный архив документов не требуется. Их удаление из рабочего
набора не означает изменение приложения, удалённых серверов или пользовательских данных.
После принятия новой исходной точки её идентификаторы MUST сохраняться;
завершённые задачи MUST NOT обнуляться при обычных исправлениях. Исправления
MUST добавляться новыми задачами с причиной и связью с требованием.
Галочка не доказывает текущую корректность.
История кода и документов MUST сохраняться в Git; переписывание опубликованной
истории требует отдельного явного указания пользователя.

Разработчик вправе выбирать детали, не меняющие согласованное поведение,
контракты и ограничения. Недостающие продуктовые и архитектурные решения
MUST NOT выдумываться. Конкретные серверы, namespace и production rollout
MUST NOT требоваться вне согласованного scope.

### VII. Автоматические проверки и независимое ревью

Flutter-изменения MUST проходить `dart format --output=none --set-exit-if-changed .`,
`flutter analyze` и `flutter test`. Изменения спецификаций MUST проходить
`lychee "specs/**/*.md"`. Изменения locald и backend MUST проходить проверки
затронутых компонентов в пределах действующего этапа проверки.

Текущий этап разработки, согласованный 2026-10-27, MUST использовать локально
и в автоматическом GitHub CI только unit/widget-тесты и статические проверки.
Unit-тесты MUST использовать подмены внешних зависимостей: запуск реальных служб,
native/FFI/DPAPI fixtures, integration, контейнеров, реальных SSH-соединений
и cold qualification в этот gate не входит. Полные платформенные проверки
MUST сохраняться отдельным ручным профилем будущей квалификации и MUST NOT
запускаться без отдельного указания пользователя. Пропущенные проверки MUST
фиксироваться как невыполненные, без заявления полной платформенной приёмки.
Сборка, проверка состава и хешей артефакта и разрешённая локальная установка
являются действиями поставки; они не разрешают запуск интеграционных тестов.
Смена этого этапа MUST быть явно согласована и закреплена в правилах и CI.

GitHub Actions MUST выполнять применимые автоматизированные проверки PR и релизов.
Неуспешные обязательные checks MUST блокировать merge или выпуск.
Доступ, контракты, миграции и задания MUST проверяться на нормальную работу,
отказы и границы. Подтверждённые баги поведения MUST иметь воспроизводимую
проверку, предотвращающую повторение.

После обязательных проверок изменения кода и пакетов спецификаций MUST проходить
цикл AGENTS.md: отдельный субагент без истории (`fork_turns="none"`) и нового
пользовательского чата, ожидание отчёта, исправление подтверждённых замечаний,
повтор проверок и свежее ревью. Проверяемые файлы MUST NOT меняться во время ревью.
Незавершённый или неопределённый отчёт MUST NOT считаться успешным.

Выполненные тесты, симуляции и планы MUST фиксироваться раздельно с фактическими
результатами и scope. Готовность MUST обосновываться полнотой обязательных
решений и доказательствами. Ограничения проверки MUST сообщаться явно.

### VIII. Воспроизводимые релизы GitHub и правомерное использование

GitHub MUST использоваться для исходников, CI и релизной истории.
Desktop-релизы MUST поставляться через GitHub Releases; Android сохраняет RuStore.
Версии клиента и backend MUST иметь явные правила совместимости;
одинаковые номера версий не обязательны.

Релиз MUST связывать версию, тег, commit, проверенные артефакты и release notes.
SDK, зависимости и инструменты MUST быть зафиксированы для повторяемой сборки.
Пакеты MUST включать необходимые runtime-компоненты и описывать prerequisites
и миграции. Review/test-сборки MUST отличаться от production-пакетов.

Публичные пакеты MUST проходить проверки установки, обновления и подписи,
предусмотренные платформой и спецификацией. Хеши MUST соответствовать окончательным
артефактам и MUST NOT заменять подпись издателя. Черновик не является публикацией;
публикация требует разрешения пользователя либо ранее разрешённого процесса.

Публичность стороннего кода MUST NOT считаться лицензией. Заимствование MUST иметь
лицензионное основание и сохранять notices. Код Logs MUST NOT использоваться
без установленной лицензии. Лицензия проекта выбирается явно;
эта конституция её не назначает.

## Technology and Security Constraints

- Клиент использует Flutter/Dart; Local API связывает UI и Dart locald,
  который владеет основной Isar БД. Изменение этих решений MUST оформляться
  в плане; нарушение принципов требует поправки к конституции.
- Backend находится в отдельном публичном репозитории. Его стек, требования
  к среде и роль в конкретных функциях MUST определяться соответствующей спекой.
- Windows — первая платформа локальных SSH-функций. Поддержка macOS, Linux
  и Android MUST заявляться по проверенным функциям и механизмам защиты,
  без переноса доказательств между платформами.
- Этот файл действует в клиентском репозитории. Общие правила для backend
  MUST быть отдельно приняты в его репозитории; эта поправка не изменяет его файлы.

## Development and Delivery Workflow

1. Определить scope, репозитории и зависимости. Для согласованного hard cutover
   создать новый набор Specify без наследования выполненных задач старого сервиса.
   Изменения прочих файлов и опубликованной Git-истории в этот scope не входят.
2. Согласовать спецификацию и решения; проверить цепочку до приёмки.
   Незакрытое обязательное решение блокирует соответствующие задачи.
3. Реализовать согласованные задачи, сохранив границы чтения, fixtures
   и разрешённых реальных операций.
4. Выполнить обязательные проверки и независимый цикл ревью AGENTS.md.
   Неразрешимый пробел передать пользователю с конкретным сценарием.
5. Перед merge подтвердить checks GitHub и приёмку scope. Перед выпуском
   проверить артефакты, совместимость, миграции и платформенные gates.
6. Подготовить release notes и черновик; публиковать по разрешённому процессу.
   Сообщить фактические результаты и непроверенные сценарии.

Новая последовательность определяется `specs/README.md`. Перед реализацией
каждый пакет MUST отдельно пройти Plan и Tasks; Specify не доказывает
архитектурную готовность. Старые MR не являются обязательными зависимостями
и не дают новой реализации статуса готовности.

## Governance

Спецификации, планы, задачи и ревью MUST проверяться на соответствие конституции.
Явные инструкции пользователя определяют scope и имеют приоритет;
устойчивое изменение принципа MUST оформляться поправкой.

Поправка MUST фиксировать причину, изменённые принципы, затронутые пакеты
и переходные действия. Существующие спеки MUST проверяться при следующей ревизии;
новая конституция не доказывает их соответствие или готовность кода.
Статусы готовности MUST NOT проставляться задним числом без проверки.

Версионирование SemVer: MAJOR для удаления или несовместимого переопределения
принципов, MINOR для новых обязательных правил, PATCH для уточнений без изменения
обязанностей. Первоначальная дата принятия сохраняется; дата поправки обновляется.
Временный Sync Impact Report удаляется перед commit после проверки поправки.
